# 📚 데이터베이스 보안 공부 로드맵

## 한 줄 요약
"DB가 털리면?"이라는 질문은 사실 **DB 자체의 문제가 아니라 "비밀을 어떻게 저장하고 키를 어디에 두느냐"의 문제**다. 그래서 공부 순서도 SQL 인젝션이 아니라 **키 관리 → 위협 모델링 → 데이터 수명주기 → 접근통제** 순이 맞다.

## 왜 이걸 공부하게 됐나
OAuth 토큰(access/refresh)을 DB 컬럼에 평문으로 넣어둔 코드를 보고 "이거 괜찮나?" 싶었던 게 출발점.
생각을 정리해보니 막연히 "불안하다"가 아니라 아래처럼 쪼개야 답이 나왔다.

1. 공격자가 **무엇을 얻나** (DB 덤프 = 토큰 문자열)
2. 그걸로 **뭘 할 수 있나** (토큰에 붙은 scope만큼 — 메일 발송 권한이면 사칭 메일)
3. **다른 조각도 필요한가** (refresh token은 client_id/secret이 같이 있어야 씀)
4. **무엇은 여전히 안전한가** (개인키가 OS 키체인에 있으면 암호문 본체는 안 풀림)

👉 이 1~4를 체계화한 게 **위협 모델링**이고, 그래서 아래 3단계에 넣었다.

## 핵심 내용

### 1단계. "암호화했다"는 답이 아니다 — 키 관리 (→ [[암호화 솔루션]] · [[환경 변수]])
공부의 8할이 여기다. **암호문이 어디 있느냐보다 키가 어디 있느냐가 전부.**

- **봉투 암호화(envelope encryption)** — 데이터키로 데이터를 암호화하고, 그 데이터키를 마스터키로 다시 암호화. 키 로테이션이 싸진다.
- **키를 DB 밖에 둔다** — 환경변수 / 시크릿 스토어 / KMS. DB 덤프·백업·리플리카가 새도 단독으로는 무용지물이 된다.
- **방어 범위를 정확히 알 것** — 앱 레이어 암호화는 *DB 유출 한정* 방어다. 앱 서버가 털리면 키도 같이 털린다. 그래도 제일 흔한 유출 경로(백업·덤프)는 막는다.
- ⚠️ **DB 내장 암호화 함수(`pgcrypto` 등)의 함정** — DB 안에서 암복호화하면 키가 SQL 문·쿼리 로그·세션 뷰(`pg_stat_activity`)에 흘러서, 정작 막으려던 "DB 털림" 시나리오에 무력해질 수 있다. 앱 레이어에서 하는 게 보통 맞다.

### 2단계. 위협 모델링 (STRIDE)
"DB 털리면 어떡하지?"를 **직감이 아니라 표로** 던지는 방법.

| 던지는 질문 | 예시 답 |
|---|---|
| 누가(공격자) | DB 백업 파일을 주운 외부인 |
| 무엇을 얻나 | 토큰 문자열, 이메일 목록 |
| 그래서 뭘 하나 | 사내 구성원 사칭 메일 → 스피어피싱 |
| 무엇은 못 하나 | 개인키가 없어 암호문 복호화는 불가 |
| 킬스위치는 | OAuth client secret 교체 → 발급된 refresh token 전부 무효화 |

**킬스위치(대응 수단)를 미리 아는 것**이 특히 중요. 사고 터진 뒤에 찾으면 늦다.

### 3단계. 데이터 수명주기 — 가장 싼 방어는 "안 갖고 있는 것"
- **최소 수집** — scope·컬럼을 실제로 쓰는 것만. 안 쓰는 권한은 유출 시 피해 면적이다.
- **최소 보관** — 장기 미사용 계정의 토큰은 주기적으로 비우기.
- **파기** — 삭제 ≠ 파기. 백업·로컬·휴지통까지 포함해서 복구 불가로.
- 설계를 바꿔 **아예 저장하지 않는 길**이 있는지 먼저 본다 (예: 사용자별 토큰 대신 서비스 계정 1개).

### 4단계. 접근통제·감사 (→ [[RBAC]] · [[인증과 인가]])
1~3보다 덜 급하지만 운영이 길어지면 반드시 온다.

- DB 계정 분리 — 앱용 / 마이그레이션용 / 사람용, 각각 최소권한
- 전송 구간 TLS, `pg_hba.conf` 로 접속 출처 제한
- 감사 로그 — 누가 언제 무엇을 읽었나
- 그리고 기본기: 파라미터라이즈드 쿼리 / ORM 으로 SQL 인젝션 차단 (→ [[ORM]] · [[관계형 데이터베이스와 SQL]])

## 자료

### 🌐 사이트 (무료 · 우선순위 순)
| 자료 | 성격 | 메모 |
|---|---|---|
| **OWASP Cheat Sheet Series** `cheatsheetseries.owasp.org` | "어떻게" | 짧고 결론부터. *Cryptographic Storage* · *Secrets Management* · *Key Management* · *SQL Injection Prevention* 4장이 핵심 |
| **OWASP ASVS** | "다 했는지 세는 체크리스트" | ⭐ 제일 추천. 개인 서비스는 **Level 2** 기준. 매번 직감으로 판단하지 않게 해주는 도구 |
| **Latacora — Cryptographic Right Answers** | "뭘 쓰면 되냐" 단정 | 30분이면 읽음. 선택 장애 제거용 |
| **PostgreSQL 공식 문서** | 운영 | *Client Authentication* · *Database Roles* · *Secure TCP/IP Connections* 챕터 |
| **CIS PostgreSQL Benchmark** | 하드닝 목록 | 가입 시 무료 PDF. 전부 적용 말고 "축 파악" 지도로 |

### 📖 책
| 책 | 쓸모 |
|---|---|
| **Serious Cryptography** (Aumasson) | ⭐ 첫 책. 암호 primitive를 "쓰는 사람" 눈높이로, 수식 최소 |
| **Cryptography Engineering** (Ferguson·Schneier·Kohno) | 키 관리·시스템 설계 사고방식. 오래됐지만 사고법은 안 낡음 |
| **Security Engineering** (Ross Anderson, 3판) | 저자 사이트 PDF 무료. 암호보다 **위협 모델·시스템 전체**. 두꺼우니 발췌로 |
| **Web Application Security** (Andrew Hoffman) | 공격→방어 쌍으로 실무 감각 |

### 🇰🇷 국내 맥락 (개인정보 다루면 법·인증이 걸림)
- **KISA 개인정보보호 포털** — *개인정보의 안전성 확보조치 기준* 해설서. "법적으로 뭘 암호화해야 하는지"의 근거가 여기 있다. 직감 말고 근거가 필요할 때.
- **ISMS-P 인증기준 안내서** — 접근통제·로그·파기 항목. 심사 받는 조직이면 어차피 보게 됨.

## 기억할 문장 / 핵심 포인트
> "**암호화했다**는 답이 아니다. **키가 어디 있냐**가 답이다."
> "가장 싼 방어는 **애초에 안 갖고 있는 것**." — 수집 최소화가 어떤 암호화보다 세다.
> "앱 레이어 암호화는 *DB 유출 한정* 방어. 방어 범위를 과장해서 안심하지 말 것."
> "유출 시 **킬스위치가 뭔지 미리 알아둘 것**. 토큰은 발급자 쪽에서 한 번에 무효화할 수 있다."

## 내 생각 / 적용할 점
- 투자 대비 효과 1등은 **치트시트 2장(합쳐 1시간) 읽고 직접 구현해보기**. 손으로 해보면 그다음 책이 훨씬 잘 읽힌다.
- 책부터 사면 안 읽는다. **문제 → 치트시트 → 구현 → 책** 순서로.
- 체크리스트(ASVS)를 갖는 것 자체가 실력이다. 매번 "이거 괜찮나?"를 직감으로 판단하는 걸 그만두게 해준다.
