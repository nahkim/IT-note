# 기술부채 (Technical Debt)

**한 줄 뜻**: 지금 빠르게 가려고 **"나중에 고치기로 하고 미뤄둔 것"** 이 쌓여, 앞으로의 모든 변경을 느리게 만드는 상태. 금융 부채처럼 **원금**(고치는 비용)과 **이자**(고치지 않은 채로 개발을 계속할 때마다 매번 더 드는 비용)로 비유한다.

**부연**:
- **유래** — **Ward Cunningham, 1992년 OOPSLA** 리포트. 요지는 *"처음 짠 코드를 출시하는 것은 빚을 지는 것과 같다. 약간의 빚은 개발을 빠르게 한다 — **제때 리라이트로 갚는 한**. 위험은 빚을 갚지 않을 때 생긴다."*
- ⚠️ **가장 흔한 오해 — 기술부채 ≠ 엉망인 코드.** 커닝햄이 2009년 영상에서 직접 정정했다: *"나는 코드를 형편없이 쓰는 데 찬성한 적이 없다. 다만 이해가 부분적일지라도 **지금의 이해를 반영해** 쓰는 데는 찬성한다."*
  - 원래 뜻은 **도메인 이해가 자란 뒤에도 코드 구조를 그에 맞게 통합(consolidate)하지 못한 격차**다. "일부러 대충 짜고 나중에 고친다"의 알리바이가 아니다.
  - 그래서 **그냥 실력·주의 부족으로 나쁘게 쓴 코드는 부채가 아니라 손실**이다. 갚을 계획이 있어야 부채다.
- **이자가 핵심이다** — 원금(리팩터링 비용)만 보면 "지금은 바쁘니 나중에"가 늘 합리적으로 보인다. 실제로 아픈 쪽은 이자다: 기능 하나 추가할 때마다 더 드는 시간, 늘어나는 버그, 길어지는 온보딩, 손대기 무서워서 아무도 안 건드리는 영역. **이자가 원금을 넘기면 파산** — 즉 전면 재작성 논의가 시작된다.
- **Fowler의 기술부채 사분면 (2009)** — "부채는 다 나쁘다"고 뭉뚱그리면 우선순위를 못 정한다. 두 축으로 쪼갠다.

| | **무모한 (reckless)** | **신중한 (prudent)** |
|---|---|---|
| **의도적 (deliberate)** | "설계할 시간 없어" | "지금 출시하고 대가는 감당한다" |
| **우발적 (inadvertent)** | "레이어링이 뭐죠?" | "이제야 어떻게 했어야 하는지 알겠다" |

  - **신중한-의도적**은 정상적인 사업 판단이다(→ [[트레이드오프]]). **신중한-우발적**은 잘해도 피할 수 없는, 배움의 부산물 — 커닝햄이 말한 원래의 부채가 여기다.
  - 실제 문제는 **무모한** 두 칸. 특히 "레이어링이 뭐죠?"는 부채가 아니라 **역량·리뷰 문제**로 다뤄야 한다.
- **종류** — 코드·설계 / **아키텍처**(경계를 잘못 그음) / **테스트**(커버리지 없어 손을 못 댐 → [[플레이키 테스트]] · [[회귀]]) / **문서** / **의존성·인프라**(버전을 못 올려 계속 밀리는 것) / **데이터·스키마**(마이그레이션 미룸).
- **측정** — **SQALE**(J.L. Letouzey) 방법론이 SonarQube 등에 들어가 있다. **기술부채 비율 = 개선 비용 ÷ 개발 비용**(코드 1줄 개발을 0.06일로 환산) → "이 코드를 만든 노력의 몇 %를 들이면 유지보수 이슈를 다 고칠 수 있나". **절대값을 진리로 믿을 수는 없지만 추세를 보는 데는 쓸 만하다.**
- **실무에서 갚는 법**
  - **티켓으로 만들어라.** 안 보이는 부채는 안 갚는다 — "나중에"라고 말로만 남긴 것이 부채의 주 유입 경로다 → [[f-u|f/u]]
  - **왜 이 부채를 졌는지 남겨라.** 의도적 부채는 [[ADR]]에 근거·상환 조건까지 기록해야 나중에 "이건 왜 이래?"가 되지 않는다.
  - **이자율이 높은 곳부터.** 전면 정리보다, **자주 바뀌는 파일**(변경 빈도 × 복잡도)을 먼저 갚는 편이 남는다.
  - **보이스카우트 규칙 / 상환 예산** — 손댄 자리는 조금 더 깨끗하게, 그리고 스프린트마다 일정 비율을 상환에 고정 배정한다.
- **혼동하기 쉬운 것들**
  - **레거시 코드** — 오래됐고 이해가 어려운 코드. 부채와 겹치지만 같지 않다(잘 돌고 안 건드릴 코드는 부채가 아니다).
  - **버그** — 부채는 "지금 잘못 동작한다"가 아니라 "**앞으로 바꾸기 어렵다**"의 문제다.
  - **[[워커라운드]]** — 개별 우회책. 그것을 방치해 쌓인 결과가 부채.

> ✅ 교차검증 — **Ward Cunningham이 1992년 OOPSLA 리포트에서 부채 비유를 처음 제시**했고 원문 취지가 *"first time code 출시는 빚을 지는 것 — 즉시 리라이트로 갚는 한 개발이 빨라지고, 갚지 않을 때 위험해진다"* 임을 확인. **2009년 영상에서 커닝햄 본인이 "나는 코드를 형편없이 쓰는 데 찬성한 적 없다 / 부분적이어도 현재의 이해를 반영해 쓰는 것에 찬성한다"고 정정**하며, 부채의 본질이 **엉망인 코드가 아니라 도메인 이해와 코드 구조 사이의 미통합 격차(failure to consolidate)** 임을 분명히 한 점도 확인. **Martin Fowler의 기술부채 사분면(2009)**이 **의도적/우발적 × 무모한/신중한** 4칸이며 각 칸의 대표 대사("설계할 시간 없어" / "지금 출시하고 대가는 감당한다" / "레이어링이 뭐죠?" / "이제야 어떻게 했어야 하는지 알겠다")와 "모든 부채를 동등하게 나쁘다고 보면 우선순위를 못 정한다"는 도입 배경을 확인. 측정 쪽은 **SQALE(J.L. Letouzey) 방법론**과 SonarQube의 **기술부채 비율 = remediation cost ÷ development cost(라인당 0.06일 환산)** 정의를 Sonar 공식 문서로 확인.
