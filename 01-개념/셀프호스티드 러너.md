# 셀프호스티드 러너 (Self-hosted Runner)

## 한 줄 정의
**CI/CD 작업을 서비스 제공자의 공용 머신이 아니라 "내가 준비한 머신"에서 돌리는 실행기.** GitHub Actions·GitLab CI 같은 [[CI-CD]] 플랫폼은 *언제 무엇을 돌릴지*만 관리하고, 실제 빌드·테스트·배포는 내 서버·노트북·쿠버네티스 파드 위의 **러너 프로세스**가 수행한다. 사내망 접근과 특수 하드웨어를 얻는 대신, **그 머신의 보안과 수명 관리가 통째로 내 책임**이 된다.

## 자세히

### 어떻게 연결되나 — 인바운드 포트를 열지 않는다
```
[내 머신 / 내 VPC 안]                      [GitHub·GitLab]
  러너 프로세스
     │  ① outbound HTTPS(443)로 롱폴링 "일 있어요?"
     ├─────────────────────────────────────▶
     │  ② 잡(워크플로 job) 배정 + 단기 토큰
     ◀─────────────────────────────────────┤
     │  ③ 내 머신에서 실제 실행 (빌드·테스트·배포)
     │  ④ 로그·결과 업로드
     └─────────────────────────────────────▶
```
- **바깥에서 들어오는 연결이 없다** → 방화벽에 인바운드 구멍을 뚫을 필요가 없다. 러너가 **먼저 말을 거는** 구조.
- 그래서 러너는 **사내망 깊숙한 곳**(운영 DB, 온프레미스 아티팩트 서버, 폐쇄망 게이트웨이 근처)에 둘 수 있다. → [[온프레미스]]
- 요구사항은 소박하다: 443 아웃바운드와 GitHub 도메인 접근, 수십 kbps 수준의 대역폭, 그리고 **워크로드가 요구하는 만큼의 CPU·RAM·디스크**(러너 앱 자체는 가볍다).

### 등록 단위와 잡 배정
- **등록 레벨** — 저장소 / 조직(그룹) / 엔터프라이즈. 위로 갈수록 여러 저장소가 공유한다.
- **러너 그룹** — 어떤 저장소·워크플로가 어떤 러너를 쓸 수 있는지 나누는 경계. **PR 검증용 러너와 배포용 러너를 분리**하는 핵심 장치.
- **라벨 매칭** — 워크플로가 `runs-on: [self-hosted, linux, gpu]`처럼 요구하면, 그 라벨을 가진 러너에 배정된다.
- **한 러너에 한 번에 한 잡**. 동시 실행을 늘리려면 러너 대수를 늘린다.

### 상주형 vs 일회용 — 이 노트에서 제일 중요한 구분
| | **상주형(persistent)** | **일회용(ephemeral)** |
|---|---|---|
| 수명 | 머신이 계속 살아 있고 잡을 연달아 받음 | **잡 하나 끝나면 러너 등록 해제·머신 폐기** |
| 장점 | 캐시·의존성이 남아 **빌드가 빠름** | 매 잡이 **깨끗한 상태**에서 시작 |
| 위험 | 이전 잡의 잔여물(캐시·자격증명·심어둔 스크립트)이 **다음 잡으로 새어 나간다** | 캐시를 외부(레지스트리·캐시 서비스)로 빼야 함, 부팅 시간 |
| 권장 | 개인 실험·단일 팀 폐쇄 환경 | **사실상 프로덕션 표준**(GitHub 권장) |

> 상주형 러너에서 악성 잡이 한 번 돌면, 그 머신은 **그 이후 모든 잡의 소스코드·시크릿·배포 권한**을 들여다볼 수 있는 자리에 앉게 된다. 일회용 러너는 이 연결고리를 끊는 장치다.

### 오토스케일 — 일회용을 실용적으로 만드는 방법
- **ARC (Actions Runner Controller)** — GitHub의 **러너 스케일셋 API 공식 구현**. [[쿠버네티스]] 위에서 **잡이 들어오면 러너 파드를 만들고, 끝나면 지운다.** 네임스페이스·네트워크 정책·서비스 어카운트로 격리할 수 있어 현재 가장 권장되는 형태(단, 쿠버네티스 운영 역량이 전제).
- **클라우드 VM 오토스케일러** — 잡 큐 길이에 따라 EC2/GCE 인스턴스를 띄우고 잡 후 종료. 쿠버네티스가 없을 때의 선택지.
- **컨테이너 단위 격리** — 잡을 컨테이너 안에서 돌려 호스트를 보호. → [[컨테이너와 Docker]]

### ⚠️ 보안 — 이 주제의 절반은 보안이다
**① 공개 저장소에는 붙이지 않는다.** GitHub 문서가 명시적으로 경고하는 항목이다. 누구나 저장소를 포크해 워크플로를 수정한 PR을 열 수 있고, 그 순간 **임의의 코드가 내 인프라에서 실행**된다. 공개 저장소는 관리형(호스티드) 러너를 쓴다.

**② 비공개 저장소라고 안전한 게 아니다.** 계정 하나만 탈취되면 워크플로 파일 수정 = 내 러너에서의 코드 실행이다. 공격 기법으로는 **PPE(Poisoned Pipeline Execution)**, 포크 PR을 특권 컨텍스트에서 돌리게 만드는 **pwn request** 등이 정리돼 있다.

**③ 러너 자체가 백도어가 된 실제 사례 — Shai-Hulud(2025~2026).** npm 생태계를 휩쓴 자가복제 공급망 웜은 2차 단계에서 **탈취한 GitHub 토큰으로 공격자 머신을 피해 조직의 셀프호스티드 러너로 등록**(러너 이름 `SHA1HULUD`)하고, `discussion.yaml` 워크플로를 심어 **GitHub 디스커션 글을 여는 것만으로 원격 명령을 실행**했다. 함께 심긴 워크플로는 `toJSON(secrets)`로 **저장소 시크릿 전체를 유출**했다. 2.0 파동에서만 2만 5천 개 이상의 저장소가 영향을 받았다. → CI 인프라가 **C2(명령·제어) 채널**로 쓰인 것.

**실무 통제 목록**
- **일회용 러너 + 자동 등록 해제** (`--ephemeral`), 잡 간 상태 공유 금지
- **러너 그룹 분리** — 포크/PR 검증용(무권한) ↔ 배포용(권한 보유)을 **다른 머신·다른 네트워크**로
- **이그레스(나가는 트래픽) 제한** — 빌드 단계가 털려도 데이터가 빠져나갈 길을 막는다
- **장기 자격증명 금지** — 러너에 클라우드 액세스 키를 심지 말고 **OIDC 기반 단기 토큰**으로. → [[인증과 인가]]
- **비특권 사용자로 실행**, 호스트와의 공유 마운트 최소화, 운영 네트워크와 분리된 서브넷
- **액션·이미지 버전을 커밋 SHA로 고정**(태그는 옮겨 달릴 수 있다) → [[Git 태그]]
- 포크 PR에 대해 **승인 후 실행** 설정, 워크플로 변경에 대한 코드 리뷰 강제
- 러너 등록 목록을 **주기적으로 감사** — 모르는 러너가 붙어 있는지가 곧 침해 지표다

### 언제 쓸 만한가 — 그리고 비용 얘기
**정당한 이유**
- **네트워크 접근** — 인터넷에 열 수 없는 사내 DB·아티팩트 서버·스테이징에 붙어야 할 때 (가장 흔한 진짜 이유)
- **특수 하드웨어** — GPU 빌드·모델 테스트, ARM·특정 macOS 버전, 대용량 메모리 → [[GPU vs CPU]]
- **커스텀 이미지·무거운 툴체인** — 매번 설치하면 10분씩 날아가는 환경 → [[툴체인]]
- **규제·데이터 주권** — 소스·데이터를 외부 클라우드에서 처리할 수 없는 경우
- **거대 저장소의 캐시 지역성** — 수 GB 체크아웃·빌드 캐시를 가까이 두고 재사용

**비용은 생각보다 애매하다 (2026년 기준)**
- GitHub은 **2026-01-01부터 호스티드 러너 가격을 최대 39% 인하**했다(Linux 2코어 x64 $0.006/분, Linux arm64 $0.005/분, Windows $0.010/분, macOS 표준 $0.062/분). 큰 사양(larger runner)은 별도 과금이라 포함 분(minutes)이 적용되지 않는다.
- 같은 발표(2025-12-16)에 **셀프호스티드 러너에도 분당 $0.002의 플랫폼 요금**을 매기겠다는 계획이 들어 있었으나, 커뮤니티 반발로 **48시간 안에 "연기"**로 물러섰다(철회가 아니라 **재검토 중 연기**). 현재는 셀프호스티드 사용에 플랫폼 요금이 붙지 않는다.
- 셀프호스티드의 실제 원가에는 **VM·스토리지 요금 + 이미지 관리 + 패치 + 보안 사고 대응 인건비**가 들어간다. **"싸서 쓴다"는 논거는 대개 빈약하고**, 위에 적은 접근성·하드웨어·규제가 진짜 이유다.
- 중간 선택지로 **관리형 서드파티 러너**(Blacksmith·Depot·WarpBuild·Namespace·Ubicloud 등)가 있다 — 내 계정에 붙지만 인프라는 업체가 관리.

### 다른 CI 플랫폼에서의 같은 개념
| 플랫폼 | 이름 | 특징 |
|---|---|---|
| GitHub Actions | self-hosted runner | 라벨·러너 그룹, ARC로 쿠버네티스 오토스케일 |
| GitLab CI | **GitLab Runner** | executor 선택(shell·docker·kubernetes), 공유/그룹/프로젝트 러너 |
| Jenkins | **에이전트(구 slave)** | 컨트롤러-에이전트 구조, 노드 라벨 |
| Buildkite | agent | 설계 자체가 "컨트롤 플레인만 SaaS, 실행은 내 인프라" |

용어만 다를 뿐 구조는 같다: **컨트롤 플레인은 SaaS, 실행 평면은 내 것.**

## 왜 중요한가
- **CI 러너는 조직에서 가장 강한 권한을 가진 머신 중 하나다.** 소스 전체를 읽고, 시크릿을 받고, 프로덕션에 배포한다. 그런데 "빌드 서버"라는 이름 때문에 서버 보안 기준에서 자주 빠진다.
- **최근 공급망 공격의 표적이 라이브러리에서 파이프라인으로 옮겨왔다.** Shai-Hulud처럼 **러너를 등록해 상주하는** 수법이 나온 이상, 러너 목록 감사와 일회용화는 선택이 아니다.
- **"사내망에 붙어야 한다"는 요구는 대체 수단이 거의 없다.** 셀프호스티드 러너는 폐쇄망 조직이 현대적 CI/CD를 쓰는 사실상 유일한 통로다.
- **비용 논거는 계속 흔들린다.** 2026년 가격 인하와 셀프호스티드 과금 시도가 보여주듯, *요금표가 아니라 요구사항으로* 결정해야 흔들리지 않는다.
- 호스티드/셀프호스티드는 양자택일이 아니다. **공개 저장소·일반 빌드는 호스티드, 내부망·GPU 잡만 셀프호스티드**로 나누는 혼합이 가장 흔한 정답이다.
