# 낙관적 락과 비관적 락 (Optimistic / Pessimistic)

## 한 줄 정의
같은 데이터를 여럿이 동시에 건드릴 때의 두 가지 태도. **비관적** = "충돌은 **날 것이다**" → 미리 **잠그고** 시작한다. **낙관적** = "충돌은 **드물다**" → 일단 진행하고 **끝날 때 검사**해서, 어긋났으면 실패시키고 다시 한다.

핵심 트레이드오프는 한 문장이다 — **기다리게 할 것인가(비관적), 다시 하게 할 것인가(낙관적).**

## 자세히

### 두 흐름 비교
```
[비관적]  잠금 획득 → (다른 사람은 대기) → 읽기 → 수정 → 쓰기 → 잠금 해제
[낙관적]  읽기(버전 기억) → 수정 → 쓸 때 "버전 그대로냐?" 확인
                                     ├ 그대로 → 성공
                                     └ 바뀜   → 실패 → 재시도 or 사용자에게 알림
```

비관적은 **충돌을 예방**하고, 낙관적은 **충돌을 탐지**한다. 낙관적은 락을 안 잡을 뿐 **검사를 안 하는 게 아니다** — "낙관적 = 대충 한다"가 아니라 "검사 시점을 뒤로 미룬다"는 뜻.

### 1) 데이터베이스 — 가장 흔한 용례

**비관적 락** — 읽는 순간 행을 잠근다.
```sql
BEGIN;
SELECT * FROM item WHERE id = 1 FOR UPDATE;  -- 여기서 잠금, 다른 트랜잭션은 대기
UPDATE item SET qty = qty - 1 WHERE id = 1;
COMMIT;                                       -- 여기서 해제
```
- `FOR UPDATE NOWAIT` — 기다리지 말고 **즉시 에러**.
- `FOR UPDATE SKIP LOCKED` — 잠긴 행은 **건너뛴다**. 워커 여러 개가 큐 테이블에서 서로 안 부딪히며 작업을 집어 갈 때 쓰는 패턴. → [[메시지 큐]]

**낙관적 락** — 잠그지 않고 `version` 컬럼으로 검사한다.
```sql
-- 읽을 때 version = 3 이었다면
UPDATE item SET qty = 9, version = 4
 WHERE id = 1 AND version = 3;
-- 영향받은 행이 0 → 그 사이 누가 먼저 고쳤다 → 충돌
```
- JPA/Hibernate의 `@Version`, Django의 `select_for_update()` 반대편이 이것이다.
- **MVCC와 헷갈리지 말 것** — PostgreSQL·MySQL(InnoDB)의 [[트랜잭션과 ACID|MVCC]]는 "읽는 쪽과 쓰는 쪽이 서로 안 막게" 버전을 여러 벌 두는 **엔진 내부 장치**다. 낙관적 락은 그 위에서 **애플리케이션이 직접** 버전을 비교하는 것. 이름이 비슷할 뿐 층이 다르다.

### 2) HTTP — REST에도 낙관적 동시성 제어가 있다
- 서버가 응답에 **`ETag`**(리소스 버전 식별자)를 실어 보낸다.
- 클라이언트는 수정 요청에 **`If-Match: <그 ETag>`** 를 붙인다.
- 그 사이 리소스가 바뀌었으면 서버가 **412 Precondition Failed**로 거절한다.
→ 락 없이 "덮어쓰기 사고(lost update)"를 막는 표준 방식. → [[HTTP 헤더]] · [[REST API]]

### 3) 프론트엔드 — 낙관적 UI 업데이트
- **비관적 UI** — 서버 응답이 **온 뒤에** 화면을 바꾼다. 안전하지만 느리게 느껴진다.
- **낙관적 UI** — **먼저 화면을 바꾸고** 요청을 보낸다. 실패하면 되돌린다(롤백). 좋아요·체크박스가 즉시 반응하는 이유.
- 대가는 **롤백 UX**다. 이미 바뀐 화면을 되돌리며 "실패했습니다"를 자연스럽게 보여주는 게 생각보다 어렵다. 중복 전송 방지는 별도로 필요하다. → [[in-flight 플래그]]

### 4) 형상관리
- **비관적** = 파일을 **잠그고** 나만 편집(구식 SVN lock, 바이너리 파일에는 지금도 유효).
- **낙관적** = 각자 고치고 나중에 **머지**, 충돌하면 그때 해결. → [[Git]]

### 5) 사촌 — CAS
`compareAndSet(기대값, 새값)` 같은 원자적 연산도 **낙관적 계열**이다. 락 없이 "내가 읽은 값이 그대로면 바꿔라"를 시도하고, 실패하면 다시 읽고 재시도한다. → [[동시성 문제]]

## 선택 기준
| 기준 | 비관적 | 낙관적 |
|---|---|---|
| 전제 | 충돌이 **잦다** | 충돌이 **드물다** |
| 유리한 부하 | 쓰기 경합이 심함 | 읽기 위주·처리량 중요 |
| 실패했을 때 | 애초에 실패가 없다(대기) | **작업이 날아간다** → 재시도 필요 |
| 대표 사례 | 재고 1개 남은 상품, 좌석·티켓 선점, 계좌 이체 | 게시글 수정, 프로필 편집, 문서 협업 |
| 대가 | 대기 지연, **데드락**, 확장성 저하 | 재시도 비용, 사용자 입력 유실 위험 |

- **충돌이 잦은데 낙관적을 쓰면** 재시도만 반복하다 오히려 더 느려진다(최악의 경우 [[라이브락]]).
- **충돌이 드문데 비관적을 쓰면** 아무도 안 다투는 자원을 붙잡고 줄을 세워 처리량만 깎는다.

## 실무에서 밟는 지뢰
- **락을 잡은 채 외부 호출 금지.** 트랜잭션 안에서 결제 API·메일 발송 같은 걸 부르면, 상대가 느려지는 만큼 내 락이 길어지고 커넥션 풀이 마른다. → [[타임아웃]] · [[풀링]]
- **락 획득 순서를 통일하라.** A→B와 B→A로 잡는 코드가 공존하면 [[데드락]]이 난다. 락 대기에도 타임아웃을 걸어야 한다.
- **낙관적 재시도에는 백오프를 붙여라.** 즉시 재시도를 반복하면 경합이 더 심해진다. → [[재시도와 백오프]]
- **재시도해도 되는 작업인지 먼저 확인.** 같은 요청을 두 번 보내도 결과가 같아야 안전하다. → [[멱등성]]
- **애초에 락이 필요 없는지 보라.** "재고 1 감소" 같은 건 락 논쟁 전에 **원자적 UPDATE 한 방**이 제일 낫다:
  ```sql
  UPDATE item SET qty = qty - 1 WHERE id = 1 AND qty > 0;  -- 0건이면 품절
  ```
  읽고→계산하고→쓰는 순간 [[레이스 컨디션]]이 생긴다. **DB에게 계산까지 맡기면** 그 틈이 사라진다.
- **분산 환경에서는 DB 락이 안 닿는 곳이 있다.** 서버가 여러 대면 프로세스 안의 [[in-flight 플래그]]로는 못 막는다. DB 제약(UNIQUE)·분산 락·[[멱등성]] 키 중 하나가 필요하다.

## 왜 중요한가
- **"둘이 동시에 눌렀을 때"** 는 테스트에서 잘 안 잡히고 운영에서 터진다. 재고 초과 판매, 좌석 이중 배정, 잔액 음수는 전부 이 선택을 안 해서 생긴다.
- **성능과 정확성을 맞바꾸는 지점이 여기다.** 락을 늘리면 안전해지고 느려진다. 어느 쪽으로 얼마나 갈지는 **충돌 빈도**라는 사실 하나로 결정할 수 있다 — 취향이 아니라 측정의 문제.
- **DB·HTTP·UI·형상관리에서 같은 구조가 반복된다.** 한 번 이해하면 `ETag`·`@Version`·`FOR UPDATE`·낙관적 UI·Git 머지가 전부 같은 아이디어의 변주로 보인다.
