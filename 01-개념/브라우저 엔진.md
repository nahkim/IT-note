# 브라우저 엔진 (Browser / Rendering Engine)

## 한 줄 정의
HTML·CSS를 해석해 **화면으로 바꾸는 렌더링 엔진**과, JavaScript를 실행하는 **JS 엔진**의 조합 — 브라우저의 심장.

## 자세히

### 3대 렌더링 엔진 (2026 기준)
| 엔진 | 만든 곳 | 쓰는 브라우저 | 대략 점유 |
|---|---|---|---|
| **Blink** | Google (WebKit에서 2013년 분기) | Chrome, Edge, Opera, Brave, Samsung Internet, Arc… | 약 78% |
| **WebKit** | Apple (KHTML에서 분기) | Safari, **iOS의 모든 브라우저** | 약 19% |
| **Gecko** | Mozilla | Firefox | 약 3% |

> 📌 **iOS의 특수성**: 오래도록 애플이 iOS 앱에 자체 엔진 사용을 금지해, iOS의 Chrome·Firefox도 **속은 WebKit**이었다. EU DMA 등 규제로 대체 엔진의 문이 열리는 중이지만, 실무에선 여전히 "iOS = WebKit"을 전제로 테스트한다.

### 렌더링 엔진 vs JS 엔진 (혼동 주의)
같은 브라우저 안에 **역할이 다른 두 엔진**이 있다.
- **렌더링(브라우저) 엔진** — HTML/CSS 파싱, [[DOM]]·CSSOM, 레이아웃·페인트 ([[브라우저 렌더링 과정]]).
- **JS 엔진** — JavaScript 파싱·컴파일·실행.
  - **V8** (Chrome/Edge/Node.js/Deno) · **JavaScriptCore/Nitro** (Safari/Bun) · **SpiderMonkey** (Firefox).
  - 현대 JS 엔진은 인터프리터로 시작해 **JIT(Just-In-Time) 컴파일**로 뜨거운 코드를 기계어로 바꾼다 → [[컴파일러와 인터프리터]]의 중간 형태.
  - V8은 브라우저 밖으로도 나가 **Node.js·Electron** 생태계를 만들었다 → 같은 엔진이 서버에서도 돈다.

### 엔진 다양성이 왜 논쟁거리인가
- Chromium(Blink) 쏠림은 **"Blink에서 되면 됐다"** 는 개발 관행을 만든다 → 사실상 한 회사가 웹 표준의 방향을 정하게 됨(과거 IE 시절의 재현 우려).
- 반대로 엔진이 줄어 **호환성 문제는 크게 감소**했다. 벤더 프리픽스 지옥·`-webkit-` 잔재는 그 시절의 유물.
- Mozilla 등은 "독립 엔진이 있어야 경쟁과 혁신이 유지된다"고 주장한다.

### 실무에서 부딪히는 지점
- **크로스 브라우저 테스트**는 사실상 **Blink / WebKit / Gecko 3종**으로 압축된다.
- 새 CSS·JS 기능은 **Baseline**(3대 엔진 모두 지원되는 상태)을 기준으로 판단하고, MDN·caniuse로 확인.
- 데스크톱 앱을 만들 때 **Chromium 동봉(Electron)** 이냐 **OS 웹뷰 사용([[Tauri]]·[[Wails]])** 이냐가 곧 "어떤 엔진에서 도느냐" 선택이다 — 후자는 가볍지만 OS마다 엔진이 달라진다.

## 왜 중요한가
- 버그가 **내 코드 문제인지 엔진 차이인지** 구분하려면 이 지도가 필요하다("Safari에서만 안 돼요"의 정체).
- 브라우저 이름이 아니라 **엔진 단위로 세상을 보면** 호환성 판단이 단순해진다(Edge 버그 ≈ Chrome 버그).
