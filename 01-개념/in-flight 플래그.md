# in-flight 플래그

## 한 줄 정의
"요청을 보냈는데 아직 응답이 안 왔다"는 상태를 표시해 두는 **불리언 변수**. 그 사이에 들어온 **같은 작업 요청을 무시(또는 대기)** 시켜서 중복 실행을 막는, 비동기 코드의 가장 단순한 잠금장치다.

## 자세히

### 이름의 뜻
- **in-flight = 이륙했지만 아직 착륙 전**. 비행기에서 온 말로, 시스템에서는 **"출발했지만 아직 완료되지 않은 것"** 을 가리킨다.
- 같은 어휘가 여러 계층에서 쓰인다: TCP의 *in-flight bytes*(보냈지만 ACK 안 온 바이트), 서버의 *in-flight requests*(처리 중인 요청 수), LLM 서빙의 *in-flight batching*(진행 중인 배치에 새 요청을 끼워 넣기).
- 그중 이 노트는 **애플리케이션 코드에서 직접 들고 있는 플래그 한 개**를 말한다.

### 기본 형태
```js
let inFlight = false;

async function refresh() {
  if (inFlight) return;        // 이미 날고 있으면 그냥 버린다
  inFlight = true;
  try {
    await fetchData();
  } finally {
    inFlight = false;          // ⚠️ 반드시 finally에서 내린다
  }
}
```
핵심은 세 줄이다. **① 켜져 있으면 나간다 → ② 켠다 → ③ 무슨 일이 있어도 끈다.**

### 겹친 요청을 어떻게 처리할지 — 세 가지 선택
| 전략 | 동작 | 어울리는 곳 |
|---|---|---|
| **drop (버리기)** | 진행 중이면 새 호출을 그냥 무시 | 폴링 틱, 새로고침 버튼 |
| **coalesce (합치기)** | 진행 중이면 "끝나고 한 번 더" 예약만 해 둠(trailing) | 자동 저장, 검색어 입력 |
| **queue (줄 세우기)** | 순서대로 하나씩 실행 | 순서가 의미 있는 쓰기 작업 |

### 플래그의 확장판
- **진행 중 Promise를 저장** — `true/false` 대신 실행 중인 Promise 자체를 들고 있다가, 나중에 온 호출에 **같은 Promise를 돌려준다**. 호출자 전원이 결과를 받으면서 실제 요청은 1번(= 요청 중복 제거, dedupe). Go의 `singleflight`, TanStack Query(React Query)의 요청 중복 제거가 이 방식이다.
- **불리언 → 카운터** — 0/1이 아니라 "동시에 N개까지"로 늘리면 세마포어가 된다. 서버의 *max in-flight requests* 제한, 커넥션 풀([[풀링]]), 백프레셔가 전부 같은 아이디어의 확대판이다.
- **취소 붙이기** — 새 요청이 오면 이전 것을 `AbortController`로 끊고 새로 보내는 방식(last-wins). 검색 자동완성처럼 **최신 결과만 의미 있는** 경우.

### 흔한 함정
- **`finally` 누락 → 영구 정지.** 중간에 예외가 나면 플래그가 `true`인 채로 남고, 그 뒤 모든 호출이 조용히 무시된다. "어느 순간부터 버튼이 아무 반응이 없다"는 버그의 단골 원인.
- **[[타임아웃]] 없는 요청과 함께 쓰면 위험.** 응답이 영영 안 오면 플래그도 영영 안 내려간다. 플래그를 쓸 거면 요청 쪽에 타임아웃이 있어야 한다.
- **멀티스레드에서는 이대로 안전하지 않다.** `if (inFlight)` 확인과 `inFlight = true` 사이에 다른 스레드가 끼어들 수 있다([[레이스 컨디션]]). 원자적 연산(CAS)이나 락이 필요하다. JS처럼 단일 스레드 이벤트 루프에서는 `await` 이전까지 끊기지 않으므로 이 단순한 형태로 충분하다.
- **React에서는 `useState`가 아니라 `useRef`.** state 갱신은 다음 렌더에 반영되므로, 같은 틱에 두 번 눌린 클릭을 못 막는다. 즉시 반영돼야 하는 가드는 ref에 둔다(화면에 스피너를 보여줄 목적이면 state를 따로 하나 더 둔다).
- **스코프를 잘못 잡기.** 플래그 하나로 "모든 요청"을 막으면 서로 다른 항목의 요청까지 서로를 막는다. 보통은 **키(예: 사용자 ID, URL)별로** 들고 있어야 한다.

### 디바운스·스로틀과 뭐가 다른가
- **디바운스/스로틀은 시계 기준** — "몇 ms 안에는 다시 안 한다".
- **in-flight 플래그는 완료 기준** — "앞의 게 끝나기 전에는 다시 안 한다". 서버가 느려지면 자동으로 간격이 늘어난다는 점에서 더 정직하다.
- 실무에서는 둘을 겹쳐 쓴다: 입력은 디바운스로 줄이고, 실제 호출은 in-flight로 겹치지 않게.

## 왜 중요한가 — 중복 요청은 부하보다 데이터가 더 문제다
- **응답 순서가 뒤바뀐다.** 요청 A(느림)와 A'(빠름)가 겹치면 나중에 보낸 게 먼저 도착하고, **오래된 응답이 최신 화면을 덮어쓴다.** 눈에 잘 안 띄고 재현도 어려운 종류의 버그다.
- **[[멱등성]]이 없는 요청이면 실제로 중복 생성된다.** 결제 두 번, 댓글 두 개, 주문 두 건. 더블 클릭 방지가 곧 데이터 정합성 방어인 이유.
- **[[폴링]] 루프가 눈덩이처럼 불어난다.** 5초마다 요청하는데 응답이 8초 걸리기 시작하면, 겹친 요청이 계속 쌓여 느려진 서버를 더 때린다. 틱마다 in-flight를 확인하는 것만으로 이 악순환이 끊긴다.
- **비용이 거의 0이다.** 변수 하나와 `try/finally` 한 쌍으로, 큐·락·분산 락 없이 대부분의 중복을 없앤다. 단, **한 프로세스 안에서만** 유효하다는 한계는 분명히 알고 써야 한다 — 서버가 여러 대면 [[멱등성]] 키나 분산 락이 따로 필요하다.
