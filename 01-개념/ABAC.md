# ABAC (속성 기반 접근 제어, Attribute-Based Access Control)

## 한 줄 정의
"이 사람이 **어떤 역할**인가"가 아니라 **"지금 이 조건이 맞는가"** 로 접근을 결정하는 인가 방식. 사용자·자원·행위·환경의 **속성(attribute)** 을 정책 규칙에 넣고 **요청이 올 때마다 계산**한다.

## 자세히

### 정책은 "문장"으로 쓰인다
> **재무팀 소속**(주체)이고 **자기 부서 문서**(자원)를 **업무시간에**(환경) **사내망에서**(환경) **읽으려 할 때**(행위) 허용한다.

[[RBAC]]이 `사용자 → 역할 → 권한` 이라는 **미리 만들어 둔 표**를 조회하는 것이라면, ABAC은 이런 **규칙(문장)을 그 자리에서 평가**한다. 권한을 미리 나열하지 않는다는 것이 결정적 차이다.

### 속성 네 갈래 (NIST SP 800-162)
| 갈래 | 무엇 | 예 |
|---|---|---|
| **주체(Subject)** | 요청하는 사람 | 부서, 직급, 소속 프로젝트, 인증 강도(MFA 여부), 보안등급 |
| **자원(Object/Resource)** | 접근 대상 | 문서 분류등급(대외비), 소유자, 태그, 프로젝트 ID |
| **행위(Action)** | 하려는 일 | read / write / delete / approve |
| **환경(Environment)** | 요청 맥락 | 시각, 위치·IP, 기기 상태, 네트워크, 현재 위협 수준 |

**환경 속성이 있다는 점**이 ABAC의 정체성이다. 역할은 어제와 오늘이 같지만, "지금 새벽 3시, 해외 IP, 미등록 기기"는 매 요청 달라진다.

### 동작 구조 — PEP / PDP / PIP / PAP
```
사용자 요청 → [PEP] 관문에서 가로챔
                ↓ "허용해도 되나?"
             [PDP] 정책 평가 ← [PIP] 부족한 속성 조회(HR DB·디렉터리·기기 상태)
                ↓ 허용/거부                ↑
             [PEP] 집행                 [PAP] 정책 작성·관리
```
- **PEP(Policy Enforcement Point)** — 실제로 막거나 통과시키는 곳([[API 게이트웨이]], 미들웨어).
- **PDP(Policy Decision Point)** — 정책을 평가해 **허용/거부만** 답하는 두뇌.
- **PIP(Policy Information Point)** — 판단에 필요한 속성을 가져다주는 공급처.
- **PAP(Policy Administration Point)** — 정책을 만들고 관리하는 콘솔.

이 네 개를 분리하는 것 자체가 ABAC의 큰 이점이다. **인가 로직이 애플리케이션 코드에서 빠져나와** 정책으로 외부화된다.

### 정책 언어·엔진
- **XACML** — OASIS 표준. ABAC의 원조 격이지만 XML이라 장황해 요즘 신규 도입은 드물다.
- **OPA / Rego** — 현재 ABAC 계열의 사실상 표준 엔진. 쿠버네티스·마이크로서비스 인가에 널리 쓰인다.
- **Cedar (AWS)** — Rego보다 읽기 쉽게 설계된 정책 언어. RBAC·ABAC·ReBAC를 함께 표현할 수 있다.
- **클라우드 실물** — AWS IAM의 `Condition` + **태그 기반 ABAC**(사용자 태그 == 리소스 태그면 허용), Azure의 RBAC 역할 할당에 붙이는 **ABAC 조건**.

### 사촌 모델
- **ReBAC(관계 기반)** — "속성"이 아니라 **관계 그래프**를 따라간다("이 문서 폴더의 편집자인가"). Google **Zanzibar** 논문 계열(OpenFGA, SpiceDB)이 대표. 문서·폴더·조직처럼 **소유·공유 구조가 깊은** 서비스에 강하다.
- **PBAC(정책 기반)** — ABAC을 조직 정책·규제 언어로 감싼 상위 개념. 실무에서 ABAC과 거의 섞여 쓰인다.
- **ACL** — 자원마다 "누가 뭘 할 수 있다"를 직접 나열하는 가장 원시적인 방식. 규모가 커지면 관리가 무너진다.

## 왜 중요한가
- **역할 폭발(role explosion)을 피한다.** RBAC에서 예외 조건이 늘 때마다 `재무팀-읽기전용-야간제외-서울` 같은 역할이 증식한다. ABAC은 조건을 **정책 한 줄**로 표현해 역할 개수를 폭발시키지 않는다.
- **제로 트러스트의 실행 수단.** "한 번 인증했으니 계속 신뢰"가 아니라 **매 요청마다 맥락을 다시 평가**한다. 기기·위치·시간·위협 수준을 반영하는 접근 통제는 사실상 ABAC 없이는 못 만든다.
- **사용자가 늘어도 정책은 그대로.** 신입이 들어와도 HR 속성(부서·직급)만 정확하면 정책 수정 없이 곧바로 올바른 권한이 적용된다.
- **데이터 등급별 통제에 맞는다.** 개인정보·대외비 같은 **자원 속성**을 기준으로 삼으면, 자원이 늘어나도 규칙이 따라 늘지 않는다. → [[ISMS]]·규제 대응

### 대가 — 공짜가 아니다
- **"누가 무엇에 접근할 수 있나"를 미리 못 뽑는다.** 결정이 실행 시점에 계산되므로, 감사자가 원하는 **사전(before-the-fact) 권한 목록**을 만들기 어렵다. RBAC의 최대 강점을 잃는 지점.
- **디버깅이 어렵다.** "왜 403인가"를 답하려면 정책·속성·환경을 모두 재현해야 한다. → [[인증과 인가|403 Forbidden]]
- **속성 품질에 전부 걸려 있다.** HR 시스템의 부서 정보가 6개월 밀려 있으면 권한도 6개월 틀린다. 쓰레기가 들어가면 쓰레기 권한이 나온다.
- **성능·의존성.** 매 요청 정책 평가 + 속성 조회 → 캐싱과 PDP 이중화가 필요하다.
