# KV 캐시 (KV Cache)

## 한 줄 정의
[[Transformer]]가 토큰을 하나씩 뽑을 때, **앞 토큰들의 Key/Value 벡터를 저장해 두고 재사용하는** 것. **연산을 메모리와 맞바꾼 거래**다. 그래서 [[LLM]] 추론의 병목은 계산이 아니라 **메모리**가 되었고, 흔히 말하는 "KV 캐시 기법"은 대부분 **그 메모리 청구서를 깎는 방법**들이다.

> 캐시 자체는 발명이 아니라 **당연한 최적화**다. 진짜 주제는 "그다음" — 이 캐시가 너무 커서 생긴 문제들을 어떻게 다루는가.

## 자세히

### 왜 캐시가 필요한가 — 자기회귀 생성의 낭비
LLM은 토큰을 **한 개씩** 만든다. 캐시가 없다면 매 스텝마다 *지금까지의 문장 전체*를 다시 어텐션에 통과시켜야 한다.

```
캐시 없음:  "나는" → "나는 오늘" → "나는 오늘 밥을" → …   ← 매번 처음부터 다시 계산
캐시 있음:  이미 만든 토큰들의 K,V는 그대로 남는다
            새 토큰의 Q만 계산해 → 쌓여 있는 K,V 전체와 어텐션
```

핵심은 **인과적(causal) 어텐션에서 과거 토큰의 K·V는 미래에 영향받지 않는다**는 점. 값이 절대 안 바뀌므로 안심하고 캐시할 수 있다. 문장 길이 n 생성에 O(n³)이던 총 연산이 O(n²)로 내려간다.

이 구조 때문에 추론은 성격이 다른 **두 단계**로 갈린다.

| 단계 | 하는 일 | 병목 | 관련 지표 |
|---|---|---|---|
| **Prefill** | 입력 프롬프트를 한 번에 통과시켜 **캐시를 채운다** | **연산(compute)** — GPU를 꽉 채워 쓴다 | **TTFT** (첫 토큰까지) |
| **Decode** | 토큰 1개씩 생성, 쌓인 캐시를 **읽어** 어텐션 | **메모리 대역폭** — 계산은 한가한데 읽을 게 많다 | **TPOT** (토큰 간 지연) |

**실제로 얼마나 빨라지나** — Hugging Face의 입문 글([참고](#참고-자료))이 T4 GPU에서 SmolLM2-1.7B로 측정한 값: 캐시를 끄면 **1분 1초**, 켜면 **11.7초** → **약 5.2배**. 짧은 생성에서도 이 정도 차이가 난다.

**코드에서는 이미 켜져 있다** — `transformers`는 `use_cache=True`가 **기본값**이라 `model.generate()`를 그냥 부르면 KV 캐시를 쓴다. 끄고 비교해 보려면 `use_cache=False`, 캐시 구현을 바꾸려면 `cache_implementation`(정적 캐시·오프로딩 등)을 넘긴다. 직접 짠다면 매 스텝 새 K·V를 기존 텐서에 **concat**하는 게 전부다.

> 💡 디코드가 **대역폭 병목**이라는 사실이 모든 것을 설명한다. GPU 코어는 놀고 있고, HBM에서 캐시를 퍼오는 속도가 생성 속도를 정한다. 그래서 "**캐시를 작게 만들면 그냥 빨라진다**" — 메모리를 아끼는 기법이 동시에 속도 기법인 이유.

### 비용 계산 — 공식과 실감
```
KV 캐시 바이트 = 2(K와 V) × 레이어 수 × KV 헤드 수 × head_dim × dtype 바이트 × 토큰 수 × 배치
```

**Llama 3.1 70B** (80 레이어, KV 헤드 8, head_dim 128, BF16) 기준:
- 토큰 1개당 `2 × 80 × 8 × 128 × 2` = **약 320 KB**
- 128K 컨텍스트를 **한 사람**이 쓰면 → **약 42 GB**

모델 가중치(70B×2B ≈ 140GB)만 문제가 아니다. **사용자 몇 명이 긴 대화를 하면 캐시가 가중치만큼 커진다.** 그리고 이 값은 **배치 × 컨텍스트 길이에 선형 비례**한다 — 즉 **동시 사용자 수를 늘리는 일은 캐시 예산을 쪼개는 일**이고, 컨텍스트 창을 늘려 파는 일에는 실제 원가가 붙는다.

### 기법 지도 — 네 개의 축
어떤 기법이든 결국 이 넷 중 하나다. **누가 언제 결정하는가**로 나누면 안 헷갈린다.

#### ① 모델 구조로 애초에 적게 만든다 (학습 시점에 확정)
헤드마다 K·V를 따로 두는 대신 **공유**한다. 서빙에서 켜고 끌 수 있는 게 아니라, **모델을 그렇게 학습시켜야** 한다.

| 기법 | 방식 | 효과 |
|---|---|---|
| **MHA** (기본) | 쿼리 헤드마다 K·V 한 벌 | 기준점 |
| **MQA** | 모든 쿼리 헤드가 **K·V 한 벌**을 공유 | 극단적 절감, 품질 저하 위험 |
| **GQA** | 쿼리 헤드를 **그룹**으로 묶어 그룹당 K·V 한 벌 | **현재의 사실상 표준.** Llama 3.1 70B은 쿼리 64 : KV 8 → **8배 절감** |
| **MLA** | K·V를 **저차원 latent 벡터로 압축**해 그것만 캐시(+RoPE 부분만 분리 보관) | DeepSeek-V3 기준 **토큰당 ~70KB**, GQA 계열(192~328KB) 대비 **2.7~4.7배** 절감 |

**레이어 간 공유**(cross-layer KV sharing), 그리고 어텐션 레이어 자체를 줄이는 **하이브리드 구조**(Mamba/SSM 혼합)도 같은 축이다 — SSM 블록은 KV 캐시가 아예 없다.

#### ② 있는 메모리를 낭비하지 않는다 (서빙 런타임, **무손실**)
- **PagedAttention** — 캐시를 **고정 크기 블록**(vLLM 기본 16토큰)으로 쪼개 비연속 할당하고 페이지 테이블로 매핑. OS 가상메모리의 페이징을 그대로 가져온 것. "생성 길이를 몰라 크게 잡아두고 남기는" 내부 단편화를 없앤다 → [[vLLM]]
- **프리픽스 캐싱 (Automatic Prefix Caching)** — 블록을 **(부모 해시 + 토큰들)** 로 해싱해, 앞부분이 같은 요청끼리 **계산된 블록을 그대로 공유**한다. 시스템 프롬프트·긴 문서·멀티턴 대화 앞부분이 공짜가 된다. vLLM V1에서는 **기본 활성**이고, 여유 블록은 **LRU**로 축출한다. SGLang의 **RadixAttention**은 같은 목표를 radix tree로 푼 사촌.

> 이 축만은 **정확도를 1비트도 잃지 않는다.** 손실을 감수하는 건 다음 축부터다. 순서를 지켜야 한다 — ②를 다 쓰기 전에 ③으로 넘어가지 말 것.

#### ③ 정밀도를 낮추거나, 일부를 버린다 (런타임, **손실 허용**)
- **양자화** — BF16 캐시를 **FP8**(vLLM `--kv-cache-dtype fp8`)이나 INT4로. FP8은 실무에서 거의 무손실로 통용되는 편. K와 V의 통계가 다르다는 점을 이용해 **K는 채널 단위, V는 토큰 단위**로 나눠 양자화하는 KIVI 계열, 이상치(outlier)를 회전으로 흩는 기법 등이 연구 축.
- **축출(eviction)** — 덜 중요한 토큰의 K·V를 **버린다**. 누적 어텐션 점수가 높은 "heavy hitter"만 남기는 **H2O**, 프롬프트를 요약해 남기는 **SnapKV** 등. 싸지만 **"나중에 그 토큰이 필요해지면 복구 불가"** 라는 위험을 품는다.
- **슬라이딩 윈도 + 어텐션 싱크** — 각 토큰이 **최근 W개만** 본다(윈도 밖 캐시는 폐기). 여기에 **StreamingLLM**의 발견 — 맨 앞 **4개 토큰(attention sink)** 만 끝까지 붙잡고 있으면 무한 스트리밍에서도 품질이 무너지지 않는다.
  - 최신 모델은 이걸 **구조로 내장**한다: **Gemma 3**는 로컬(윈도 1024) : 글로벌 = **5:1**로 레이어를 교차, **gpt-oss**는 윈도 128 레이어와 글로벌 레이어를 번갈아 쌓는다. 전 레이어 글로벌 어텐션 대비 캐시가 극적으로 줄어든다.

#### ④ 자리를 옮긴다 (계층화·분산)
- **오프로딩** — GPU HBM → CPU RAM → NVMe → 오브젝트 스토리지로 **캐시 계층**을 만든다. **LMCache**가 대표. 필요한 부분만 골라 되올리는 기법(InfiniGen 등)과 함께 쓴다.
- **PD 분리 (Prefill–Decode Disaggregation)** — 성격이 다른 두 단계를 **다른 GPU**에 나눠 붙이고, KV 캐시를 **RDMA로 전송**한다(NVIDIA **NIXL**이 사실상 표준 전송 계층, **Dynamo**·vLLM·SGLang이 지원). Moonshot의 **Mooncake**는 여기서 더 나아가 **KV 캐시 중심의 분산 메모리 풀**을 둔다.
- **KV-aware 라우팅** — "**이미 이 프리픽스를 캐시하고 있는 노드**"로 요청을 보낸다. 로드밸런싱의 기준이 CPU 부하가 아니라 **캐시 지역성**으로 바뀌는 것 → [[로드 밸런서]] · [[일관성 해싱]]

### API 사용자가 만나는 KV 캐시 — 프롬프트 캐싱
직접 서빙하지 않아도 **과금 항목**으로 만난다. ②의 프리픽스 캐싱이 상품화된 형태다. Claude API 기준:

| 항목 | 기본 입력 대비 |
|---|---|
| 캐시 **쓰기** (TTL 5분) | **1.25배** |
| 캐시 **쓰기** (TTL 1시간) | **2배** |
| 캐시 **읽기** | **0.1배** (90% 절감) |

TTL은 **접근할 때마다 갱신**된다. 실전 규칙은 캐시의 원리에서 그대로 나온다:

- **고정된 것을 앞에, 변하는 것을 뒤에.** 시스템 프롬프트 → 툴 정의 → 참조 문서 → 대화 이력 → 이번 질문.
- **앞에서 한 토큰만 달라지면 그 뒤 전부 미스**다(프리픽스 = 접두사). 프롬프트 앞에 타임스탬프나 랜덤 ID를 넣는 습관은 캐시를 통째로 날린다.
- 캐시 히트는 **prefill만** 줄인다 → **TTFT는 극적으로 좋아지지만 생성 속도(TPOT)는 그대로**다.

→ [[프롬프트 엔지니어링]]

### ⚠️ 흔한 오해와 함정
- **"캐시니까 정확도에 영향 없겠지"** — KV 캐시 **자체**는 무손실이다. 하지만 양자화·축출·슬라이딩 윈도는 **모델 출력을 바꾼다.** 벤치마크 점수는 그대로인데 특정 롱컨텍스트 과제만 무너지는 식으로 나타나기 쉽다.
- **"캐시를 켰는데 왜 안 빨라지나"** — 프리픽스가 실제로 겹치는지 확인해야 한다. 접두사만 유효하며, **중간이 같아도 소용없다.**
- **"컨텍스트 100만 토큰 지원"의 원가** — 지원한다는 말과 **동시에 여러 명이 그렇게 쓸 수 있다**는 말은 다르다. 롱컨텍스트 서빙의 실질은 캐시 예산 문제다.
- **블록 공유는 격리 경계를 넘는다** — 여러 사용자가 프리픽스 블록을 공유하면, 캐시 히트 여부가 **타이밍으로 관측**될 수 있다(다른 사용자가 무엇을 보냈는지 추측하는 사이드채널). vLLM의 **cache salt**처럼 테넌트별로 해시를 분리하는 장치가 있다 → [[멀티테넌시]]
- **캐시 히트율은 트래픽 패턴의 함수**다. 같은 시스템 프롬프트를 쓰는 챗봇은 히트율이 높고, 매번 다른 문서를 넣는 [[RAG]]는 낮다. 기법 선택은 **워크로드를 보고** 해야 한다.

## 왜 중요한가
- **LLM 추론 비용·속도 이야기의 90%가 여기서 결정된다.** "서빙의 본질은 메모리와 배칭 싸움"이라는 말이 나오는 근거가 KV 캐시다 → [[AI 모델 서빙 프레임워크]]
- **모델 카드를 읽는 눈이 달라진다.** GQA·MLA·슬라이딩 윈도 같은 표기가 "이 모델을 실제로 굴릴 때 GPU가 몇 장 필요한가"로 번역되기 시작한다 → [[LLM 모델 이름 읽는 법]]
- **프롬프트 설계가 곧 비용 설계**임을 이해하게 된다. 순서만 바꿔 입력비를 90% 줄이는 일이 실제로 가능하다.
- **컴퓨터 시스템 지식이 그대로 재활용되는 현장**이다. 페이징·LRU·캐시 계층·지역성 기반 라우팅 — [[캐시]]와 [[가비지 컬렉션과 메모리]]에서 배운 것이 이름만 바꿔 등장한다.

> ✅ **웹 교차검증 완료** — KV 캐시의 원리(인과적 어텐션에서 과거 K·V가 불변이므로 재계산 회피)와 **prefill=연산 병목 / decode=메모리 대역폭 병목** 구분, 캐시 크기 공식 `2 × 레이어 × KV헤드 × head_dim × dtype × 토큰 × 배치`와 **Llama 3.1 70B(80레이어·KV헤드 8·head_dim 128·BF16) = 토큰당 약 320KB, 128K 컨텍스트 ≈ 42GB**를 복수 사이징 가이드로 확인. 구조 축은 **MQA→GQA(Llama 3.1 70B 쿼리 64 : KV 8 → 8배 절감)→MLA(저차원 latent 압축 + decoupled RoPE)** 계보와 **DeepSeek-V3 토큰당 ~70KB, GQA 계열 192~328KB 대비 2.7~4.7배 절감**을 DeepSeek-V3 기술 보고서·KV 캐시 관리 서베이로 확인. 런타임 축은 vLLM 공식 문서로 **KV 블록 기본 16토큰**, 프리픽스 캐싱이 **(부모 해시 + 블록 토큰) 해싱(기본 SHA256)·LRU 축출·V1에서 기본 활성**, `--kv-cache-dtype`가 **fp8(e4m3)/fp8_e5m2** 지원임을 확인(SGLang RadixAttention은 동일 목표의 radix tree 구현). 손실 허용 축은 **KIVI(K는 채널별·V는 토큰별 양자화)**, **H2O(누적 어텐션 기반 heavy hitter 선별)·SnapKV** 등 축출 계열, **StreamingLLM의 어텐션 싱크(초기 4토큰) + 롤링 윈도**, **Gemma 3의 로컬(윈도 1024):글로벌 5:1 교차**와 **gpt-oss의 윈도 128 로컬·글로벌 교차**를 각 논문·기술 보고서로 확인. 분산 축은 **PD 분리가 2026년 현재 주요 서빙 프레임워크의 표준 구성**이며 **NIXL(RDMA/TCP)이 vLLM·NVIDIA Dynamo 공통 KV 전송 계층**, **LMCache**의 KV 오프로딩·공유, **Mooncake**의 KV 캐시 중심 분산 메모리 풀, **Dynamo의 KV-aware 라우팅**을 NVIDIA Dynamo 문서·LMCache 공식 블로그로 확인. 프롬프트 캐싱 요율은 Claude 공식 문서 기준 **쓰기 1.25배(5분 TTL)·2배(1시간 TTL), 읽기 0.1배, 접근 시 TTL 갱신**을 확인. 공유 KV 블록의 **타이밍 사이드채널 위험과 cache salt류 테넌트 분리**도 관련 연구·vLLM 문서로 확인. 캐시 On/Off 체감 수치(**T4 + SmolLM2-1.7B: 1분 1초 → 11.7초, 약 5.2배**)와 `transformers`의 **`use_cache=True` 기본값·`cache_implementation` 파라미터**는 Hugging Face 블로그(Not Lain, [참고 자료](#참고-자료))에서 확인 — 측정 환경이 단일 모델·단일 GPU이므로 **절대 배수는 모델·길이·하드웨어에 따라 크게 달라진다**는 점만 감안할 것.
