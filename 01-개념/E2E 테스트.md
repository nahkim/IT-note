# E2E 테스트 (End-to-End)

## 한 줄 정의
실제 사용자 관점에서 **UI → 백엔드 → DB → 외부 연동까지 전체 흐름을 처음부터 끝까지** 검증하는 테스트. [[소프트웨어 테스트|테스트 피라미드]]의 **꼭대기**.

## 자세히

### 무엇을 검증하나
- 실제 사용자처럼 **버튼 클릭·폼 입력·페이지 이동**을 하며, **통합된 전체 시스템이 진짜 동작**하는지 본다.
- 단위(unit)가 다 통과해도 **합쳐 놓으면 깨질 수 있다** → E2E가 그 틈을 잡는다.

### 3계층의 질문 (피라미드)
- **단위(Unit)** — "이 함수가 되나?" (많이·빠름·쌈, 바닥)
- **통합(Integration)** — "이 컴포넌트들이 함께 되나?" (중간)
- **E2E** — "이 **사용자 흐름**이 실제로 되나?" (적게·느림·비쌈, 꼭대기)
- 대략 비율 **70 / 20 / 10**. E2E는 보통 **핵심 흐름(critical path)만 50~100개**.

### 도구
- **Playwright** — 신형, 빠르고 크로스브라우저·API 테스트 내장(요즘 선호).
- **Cypress** — SPA에 강한 개발자 친화형.
- **Selenium** — 업계 표준, 브라우저 커버리지 최다. (모바일은 **Appium**)

### 장점 / 단점
- **장점** — **최고 신뢰도**(진짜 사용자 시나리오), 배포 전 회귀([[회귀]]) 방지.
- **단점** — **느림**(테스트당 2~30초), 유지보수 비쌈, **깨지기 쉬움(flaky)** → [[플레이키 테스트]]. 실패 원인 특정이 어렵다.

### 실무 원칙
- **핵심 흐름만 소수 E2E**, 나머지는 하위 레벨(unit/integration)로 내린다(피라미드 뒤집으면 느리고 불안정).
- [[CI-CD]]에서 자동 실행하고, [[무중단 배포]] 전 스모크/핵심 시나리오 검증에 쓴다.

## 왜 중요한가
- 유닛·통합이 다 초록불이어도 **"사용자가 실제로 쓸 때 되는가"**는 별개 — E2E가 그걸 보장한다.
- 다만 **남발하면 릴리즈가 느려지고 flaky해진다** — 계층을 흐리는 게 느린 배포·유령 실패의 주범([[트레이드오프]]).
