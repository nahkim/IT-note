# TOCTOU (Time-Of-Check to Time-Of-Use)

## 한 줄 정의
**"검사한 순간"과 "실제로 쓰는 순간" 사이의 틈**을 공격자가 파고들어, 검사 결과를 무의미하게 만드는 [[동시성 문제|레이스 컨디션]] 취약점. 표준 분류로는 **CWE-367**.

## 자세히

### 무엇이 문제인가
검사(check)와 사용(use)이 **원자적(atomic)이지 않으면**, 그 사이에 대상이 바뀔 수 있다.

```c
// 취약: setuid 프로그램의 고전적 패턴
if (access("/tmp/file", W_OK) == 0) {   // ① 검사: "이 사용자가 쓸 수 있나?"
    // ← 여기서 공격자가 /tmp/file 을 /etc/passwd 심볼릭 링크로 바꿔치기
    fd = open("/tmp/file", O_WRONLY);   // ② 사용: 이제 /etc/passwd 를 연다
    write(fd, ...);
}
```

- `access()`는 **실제 UID**로, `open()`은 **유효(effective) UID**로 권한을 본다. setuid-root 프로그램에서 이 조합이 특히 위험하다.
- 핵심은 **경로 문자열(path)로 두 번 접근**했다는 것. 경로는 이름일 뿐이고, 그 이름이 가리키는 실체는 언제든 바뀐다.

### 왜 "겨우 몇 마이크로초"가 뚫리나
- 공격자는 **계속 재시도**하면 된다. 성공 확률이 0.1%여도 초당 수천 번 시도하면 뚫린다.
- 스케줄러를 이용해 창(window)을 인위적으로 넓힐 수도 있다 — 디스크 I/O 유도, CPU 부하, 큰 디렉터리 탐색 등으로 검사와 사용 사이를 늘린다.

### 파일시스템만의 문제가 아니다
| 층위 | 취약한 패턴 | 실제 사고 |
|---|---|---|
| 파일시스템 | `access()` → `open()`, `stat()` → `open()` | setuid 심볼릭 링크 공격 |
| 컨테이너 | 컨테이너 안에서 경로 검증 → 호스트에서 사용 | **CVE-2018-15664** (`docker cp` 심볼릭 링크 교환, CVSS 8.7) |
| 애플리케이션 | `SELECT` 잔액 확인 → `UPDATE` 차감 | 쿠폰·포인트 **중복 사용**, 재고 초과 판매 |
| 인증 | 토큰 유효성 검사 → 이후 권한 사용 | 검사 후 폐기된 토큰으로 계속 접근 |
| 임시 파일 | `/tmp/앱이름.tmp` 처럼 **예측 가능한 이름** 사용 | 미리 심어둔 링크로 파일 덮어쓰기 |

애플리케이션 층의 "잔액 확인 → 차감"은 웹 개발자가 가장 자주 만드는 TOCTOU다. 결제·쿠폰 API에 동시 요청 100개를 쏘는 것만으로 재현되는 경우가 많다.

### 막는 법 — "검사하지 말고, 원자적으로 실행하라"
가장 근본적인 조언은 **검사와 사용을 하나의 원자적 연산으로 합치는 것**이다.

- **파일시스템**
  - `access()` 쓰지 말고 **그냥 `open()` 하고 실패를 처리**한다. 권한 강등이 필요하면 프로세스 권한 자체를 낮춘다.
  - 경로 대신 **파일 디스크립터**로 다룬다: `open()` 뒤엔 `stat()`이 아니라 **`fstat()`**.
  - **`openat()` / `openat2()`**(Linux 5.6+)로 디렉터리 FD에 경로 해석을 묶고, **`O_NOFOLLOW`**로 심볼릭 링크 추적을 차단한다.
  - 임시 파일은 **`mkstemp()` / `mkdtemp()`** 로 예측 불가능한 이름 + 권한 `0600`으로 생성한다.
  - 협조적 잠금이 필요하면 `flock()` / `fcntl(F_SETLK)`.
- **데이터베이스**
  - `SELECT` 후 `UPDATE` 대신 **조건부 원자 갱신**: `UPDATE wallet SET balance = balance - 100 WHERE id = ? AND balance >= 100` → 영향 행 수가 0이면 실패 처리.
  - 또는 [[낙관적 락과 비관적 락|비관적 락]](`SELECT ... FOR UPDATE`) / [[낙관적 락과 비관적 락|낙관적 락]](버전 컬럼 + 재시도).
  - **UNIQUE 제약**으로 중복을 DB가 막게 한다 — 애플리케이션의 "있나 확인 후 INSERT"보다 훨씬 안전하다.
- **분산 환경**: 단일 서버 락으로는 부족하다. Redis 등 **분산 락**이나 [[멱등성|멱등성 키]]로 재실행을 안전하게 만든다.
- **테스트**: 동시 요청을 실제로 쏴 본다. 순차 테스트로는 절대 안 잡힌다.

## 왜 중요한가
- **재현이 어려워 QA를 통과한다.** 평소엔 멀쩡하고 공격 상황에서만 터지므로, 코드 리뷰 단계에서 "검사 → 사용" 패턴을 눈으로 잡아내는 게 사실상 유일한 방어선이다.
- 권한 상승(Privilege Escalation)으로 직결된다. 파일 하나 덮어쓰기가 root 획득으로 이어지는 경로가 흔하다.
- 웹 서비스에서는 곧 **돈**이다. 쿠폰 중복 적용, 마이너스 잔액, 재고 초과 판매 대부분이 이 구조다.
- AI 에이전트·자동화 도구처럼 "파일 검사 후 실행"을 반복하는 프로그램이 늘면서 다시 주목받는 오래된 취약점이다.
