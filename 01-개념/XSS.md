# XSS (Cross-Site Scripting, 크로스 사이트 스크립팅)

## 한 줄 정의
공격자가 **남의 사이트 페이지에 자기 JavaScript를 심어**, 그 페이지를 보는 사용자의 브라우저에서 **그 사이트의 권한으로** 실행시키는 공격.

## 자세히

### 왜 위험한가 — "출처를 훔치는" 공격
심어진 스크립트는 [[동일 출처 정책]]상 **그 사이트의 정식 스크립트와 동일한 권한**을 갖는다. 그래서:
- 세션 쿠키·토큰 탈취 → 계정 탈취 ([[쿠키 세션 JWT]])
- 사용자 몰래 요청 전송(글쓰기·송금·설정 변경)
- 화면 위조(가짜 로그인 폼) → 자격증명 수집
- 키로깅, 카메라·클립보드 접근 유도

### 세 가지 유형
| 유형 | 악성 코드가 사는 곳 | 예시 |
|---|---|---|
| **저장형(Stored / Persistent)** | 서버 DB에 저장 → 보는 사람 **전원**에게 실행 | 게시글·댓글·프로필에 `<script>` 삽입. 가장 파급 큼 |
| **반사형(Reflected)** | 저장되지 않고 **요청 → 응답에 그대로 되돌아옴** | `?q=<script>…` 검색어가 결과 화면에 그대로 출력. 피싱 링크로 유도 |
| **DOM 기반(DOM-based, type-0)** | **서버 응답은 멀쩡**, 클라이언트 JS가 위험하게 처리 | `location.hash` 값을 `innerHTML`에 넣음. 서버 로그엔 흔적이 안 남을 수 있음 |

> 저장형·반사형은 **서버 사이드** 출력 문제, DOM 기반은 **클라이언트 사이드** 문제. 그래서 서버만 고치면 DOM XSS는 안 잡힌다.

### 막는 법 (순서대로 중요)
1. **출력 인코딩(escaping)** — 근본 방어. 사용자 입력을 화면에 낼 때 **컨텍스트에 맞게** 이스케이프(HTML 본문 / 속성 / JS / URL / CSS가 각각 다름).
2. **안전한 DOM API** — `innerHTML` 대신 **`textContent`**, `eval`·`document.write` 금지. (DOM XSS 방어의 핵심)
3. **[[CSP]]** — 뚫렸을 때의 피해를 줄이는 2차 방어선. `nonce` + `strict-dynamic`.
4. **입력 검증(allowlist)** — 보조. 검증만으로는 못 막는다(우회 무궁무진).
5. **HTML을 허용해야 하면 새니타이저** — DOMPurify 등 검증된 라이브러리로 정제. 직접 정규식으로 거르지 말 것.
6. **쿠키에 `HttpOnly`** — JS가 세션 쿠키를 못 읽게. (탈취 경로 하나를 줄이는 것이지 XSS 자체를 막진 않음)

> ⚠️ 현대 프레임워크(React·Vue·Angular)는 기본 이스케이프를 해주지만, `dangerouslySetInnerHTML`·`v-html`·`bypassSecurityTrust*` 같은 **탈출구**를 쓰는 순간 원점이다.

### 헷갈리는 이웃들
- **[[CSRF]]** — XSS는 "**내 코드가 남의 사이트에서 실행**", CSRF는 "**남의 사이트가 내 이름으로 요청 전송**". XSS가 있으면 CSRF 방어(토큰)도 무력화된다.
- **[[Self-XSS]]** — 사이트 취약점이 아니라 **사용자를 속여 콘솔에 붙여넣게** 하는 사회공학.

## 왜 중요한가
- 20년 넘게 [[OWASP Top 10]] 상위를 지키는 **웹 취약점의 대표주자**. "입력은 불신, 출력은 인코딩"이라는 웹 보안 제1원칙이 여기서 나온다.
- 프론트엔드가 두꺼워질수록 **DOM 기반 XSS**의 비중이 커진다 → 서버 담당자만의 문제가 아니다.
