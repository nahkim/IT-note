# 리플로우 (Reflow)

## 한 줄 정의
브라우저가 DOM·CSS 변경 때문에 **요소들의 위치·크기(기하 정보)를 다시 계산**하는 과정. "레이아웃(Layout)"이라고도 부르며, 화면을 다시 그리기만 하는 **리페인트(Repaint)보다 훨씬 비싸다.**

## 자세히

### 브라우저 렌더링 파이프라인에서의 위치
브라우저가 화면을 그리는 순서는 대략 이렇다:
1. **DOM + CSSOM** 생성 → 2. **Render Tree** (보이는 요소 + 스타일) → 3. **Layout(=Reflow)** 각 요소의 정확한 위치·크기 계산 → 4. **Paint** 픽셀 색칠 → 5. **Composite** 레이어 합성.

- **리플로우(Reflow / Layout)** — 3단계. 요소의 **기하 정보(위치·크기)를 다시 계산**. 한 요소가 바뀌면 그 주변·자식·때론 문서 전체에 영향이 번진다 → **가장 비쌈**.
- **리페인트(Repaint)** — 4단계. 기하 변화 없이 **색·배경·visibility 등 겉모습만** 다시 그림. 리플로우보다 쌈.
- **컴포지트(Composite)** — 5단계. `transform`·`opacity`처럼 레이아웃·페인트를 건너뛰고 **GPU에서 레이어만 재배치** → 가장 저렴. 애니메이션은 이걸 노려야 한다.

> ⚠️ **리플로우는 반드시 리페인트를 유발한다** (위치가 바뀌면 다시 그려야 하니까). 반대로 리페인트가 항상 리플로우를 부르지는 않는다.

### 무엇이 리플로우를 일으키나
- **DOM 변경** — 요소 추가·삭제, 텍스트 내용 변경.
- **기하에 영향을 주는 스타일 변경** — `width`, `height`, `margin`, `padding`, `top/left`, `display`, `font-size` 등.
- **창 크기 변경(resize)**, 폰트 로드, 스크롤 등.
- **레이아웃 속성을 "읽는" 행위** — 아래 강제 동기 레이아웃 참고.

### 강제 동기 레이아웃 & 레이아웃 스래싱 (핵심 함정)
브라우저는 원래 여러 변경을 **모아뒀다가(batch) 한 번에** 레이아웃을 계산하려 한다. 그런데 JS가 **방금 스타일을 바꾼 직후** `offsetHeight`, `offsetTop`, `getBoundingClientRect()`, `getComputedStyle()` 같은 **레이아웃 값을 읽으면**, 브라우저는 정확한 값을 주려고 **그 자리에서 즉시 레이아웃을 강제 계산**한다 → **강제 동기 레이아웃(Forced Synchronous Layout)**.

이 "쓰기 → 읽기"를 반복문 안에서 여러 번 하면 매 반복마다 리플로우가 터진다 → **레이아웃 스래싱(Layout Thrashing)**. 대표적 성능 병목.

```js
// ❌ 나쁨: 읽기·쓰기가 섞여 매 반복마다 강제 리플로우 (스래싱)
for (const el of boxes) {
  el.style.width = box.offsetWidth + 10 + 'px'; // 읽고 → 쓰고
}

// ✅ 좋음: 읽기를 먼저 몰아서, 쓰기를 나중에 몰아서
const widths = boxes.map(el => el.offsetWidth); // 읽기 배치
boxes.forEach((el, i) => el.style.width = widths[i] + 10 + 'px'); // 쓰기 배치
```

### 리플로우를 줄이는 법
- **읽기와 쓰기를 분리(batch)** — 레이아웃 읽기를 한꺼번에, 쓰기를 한꺼번에. (`requestAnimationFrame`으로 쓰기 타이밍 정렬)
- **스타일은 한 번에** — 속성을 하나씩 바꾸지 말고 **클래스 하나를 토글**해 한 번에 적용.
- **애니메이션은 `transform`·`opacity`로** — 이 둘은 레이아웃·페인트를 건너뛰고 컴포지트만 → 60fps 유지 쉬움. (`top/left`·`width` 애니메이션은 매 프레임 리플로우)
- **DOM 대량 조작은 오프스크린에서** — `DocumentFragment`에 모아 만든 뒤 한 번에 붙이거나, 요소를 잠시 `display:none` 해두고 조작.
- **레이아웃을 격리** — `will-change`, `contain: layout` 등으로 영향 범위를 가둔다.

## 왜 중요한가
- "스크롤·애니메이션이 버벅인다(jank)"의 흔한 진짜 원인이 **불필요한 리플로우/스래싱**이다.
- 원인(쓰기 직후 읽기 → 강제 동기 레이아웃)과 해법(읽기·쓰기 배치, transform 사용)을 알면 프레임 드랍을 근본적으로 줄일 수 있다. 프론트엔드 성능 최적화의 기본기.
