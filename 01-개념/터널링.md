# 터널링 (Tunneling)

## 한 줄 정의
**어떤 프로토콜의 패킷을 다른 프로토콜의 패킷 안에 통째로 싸서(캡슐화) 보내는 것.** 중간 네트워크는 바깥 포장만 보고 평범한 트래픽으로 취급해 날라주고, 반대편에서 포장을 뜯으면 원래 패킷이 그대로 나온다.

> 비유는 **소포**다. 내용물(원래 패킷)은 손대지 않고 **겉봉투에 새 주소를 적어** 보낸다. 배달부는 겉봉투만 읽고, 수신자만 봉투를 뜯는다. 터널링의 모든 성질 — 우회 능력, 암호화, MTU 문제, 디버깅의 어려움 — 이 "봉투가 하나 더 생겼다"는 사실 하나에서 나온다.

## 자세히

### 그림 하나로

```
터널 없이:   [앱] ── TCP/IP ──▶ [중간 네트워크] ──▶ [목적지]
                                  ▲ 중간이 내용을 보고, 막고, 라우팅한다

터널:        [앱] ─▶ [터널 입구] ══════════════════▶ [터널 출구] ─▶ [목적지]
                       │                                  │
                       └ 원래 패킷을 새 헤더로 감쌈         └ 벗겨서 원래 패킷 복원

             실제 선 위를 흐르는 것:
             ┌─ 바깥 헤더 (IP/UDP, 중간 네트워크가 보는 전부) ─┐
             │  ┌─ 원래 패킷 (IP/TCP/HTTP…) ─┐                │
             │  │   ← 중간은 이걸 못 본다      │                │
             └──┴─────────────────────────────┴────────────────┘
```

**핵심은 "계층을 한 번 접는다"는 것.** L3 패킷이 L4 페이로드가 되고, L2 프레임이 L3 패킷 안에 들어간다. 정상적인 계층 순서(L2→L3→L4→L7)를 어기고 **아래 계층을 위 계층 안에 집어넣기 때문에** 터널이 성립한다. → [[OSI 7계층]]

### 왜 터널을 파나 — 네 가지 동기
터널을 쓰는 이유는 결국 이 넷 중 하나다. **무엇 때문에 파는지 모르면 잘못된 도구를 고른다.**

| 동기 | 하고 싶은 일 | 대표 도구 |
|---|---|---|
| **① 도달성** | 서로 못 닿는 두 곳을 잇는다 (NAT·방화벽 뒤, 사설망) | SSH `-L`/`-R`, WireGuard, Cloudflare Tunnel |
| **② 기밀성** | 신뢰 못 할 구간 위를 안전하게 지난다 | IPsec, WireGuard, TLS, SSH |
| **③ 호환성** | 중간이 모르는 프로토콜을 아는 것으로 감싼다 (IPv6 over IPv4, L2 over L3) | GRE, VXLAN, 6in4 |
| **④ 우회** | 중간의 정책을 피해 간다 | HTTP CONNECT, DNS 터널링, 포트 443 위장 |

⚠️ **①②③은 설계이고 ④는 양날이다.** 같은 기술이 "방화벽을 우회해서 일하기"도 되고 "방화벽을 우회해서 털기"도 된다. 아래 §보안을 반드시 같이 볼 것.

### 계층별 지도 — 무엇을 무엇으로 싸는가
| 터널 | 안에 싣는 것 | 바깥 포장 | 암호화 | 주 용도 |
|---|---|---|---|---|
| **SSH 포트 포워딩** | TCP 스트림 | TCP(22) + SSH | ✅ | 사설망 서비스에 접속, 1회성 |
| **WireGuard** | IP 패킷 | **UDP**(기본 51820) | ✅ | 현대적 VPN, 서버 간 사설망 |
| **IPsec (터널 모드)** | IP 패킷 | ESP(프로토콜 50), NAT 뒤면 UDP 4500 | ✅ | 사내·사이트 간 VPN, 장비 기본 |
| **OpenVPN** | IP/Ethernet | UDP 또는 **TCP** | ✅ | 범용 VPN(TCP 모드는 아래 함정) |
| **GRE** | 거의 아무 L3 | IP 프로토콜 47 | ❌ | 라우팅용 범용 터널(+24B) |
| **VXLAN** | **Ethernet 프레임** | UDP 4789 | ❌ | 데이터센터·컨테이너 오버레이(+50B) |
| **HTTP CONNECT** | TCP 스트림 | HTTP(프록시) | 안쪽 TLS에 의존 | 프록시 너머 HTTPS |
| **MASQUE** | UDP·IP 패킷 | **HTTP/3(QUIC)** | ✅ | iCloud 비공개 릴레이류 신세대 VPN |
| **DNS 터널링** | 아무 데이터 | DNS 질의 | ❌ | 거의 전부 **악용**(C2·유출) |

> 🔑 **읽는 법** — "안에 싣는 것"이 **IP면 네트워크 전체**가 연결되고(VPN), **TCP 스트림이면 포트 하나**만 연결된다(SSH 포워딩). 이 구분이 "VPN을 깔까 SSH 터널을 팔까"의 답이다.

### 방향이 전부다 — 아웃바운드와 리버스
터널 실무에서 가장 중요한 질문은 **"누가 먼저 connect 하는가"** 다. 방화벽·NAT는 대개 **나가는 연결은 허용, 들어오는 연결은 차단**이기 때문이다.

```
① 정방향 (내가 못 가는 곳으로 간다)
   [나] ──connect──▶ [터널 서버] ──▶ [사설망 서비스]
   예: ssh -L, 회사 VPN 접속

② 리버스 (밖에서 못 오는 나에게 오게 한다)
   [내 PC] ──connect(아웃바운드)──▶ [공개 서버] ◀──접속── [외부 사용자]
            └ 내가 먼저 나가서 연결을 "걸어두면", 그 통로로 역방향 트래픽이 들어온다
   예: ssh -R, ngrok, Cloudflare Tunnel(cloudflared), localtunnel
```

**리버스 터널이 강력하고 위험한 이유가 같다** — *포트를 하나도 열지 않고* 내부를 외부에 노출시킨다. 방화벽 입장에선 그냥 평범한 아웃바운드 HTTPS 한 줄이라 막기 어렵다.

### SSH 포트 포워딩 3종 — 손에 가장 자주 잡히는 터널
```bash
# -L 로컬 포워딩: "내 포트 → 저쪽에서 보이는 주소"
ssh -L 5432:db.internal:5432 user@bastion
#      ↑내 포트  ↑bastion 기준 목적지     → localhost:5432 로 사설 DB 접속

# -R 리모트 포워딩: "저쪽 포트 → 내 쪽에서 보이는 주소"
ssh -R 8080:localhost:3000 user@public-server
#      ↑서버 포트  ↑내 기준 목적지        → 서버의 8080 이 내 3000 으로

# -D 다이나믹 포워딩: SOCKS 프록시 (목적지를 고정하지 않음)
ssh -D 1080 user@bastion                   # 브라우저 SOCKS5 → localhost:1080
```

- **`destination_host`는 언제나 "SSH 서버 입장에서" 해석된다.** `-L`에서 `localhost`라고 쓰면 그건 *내 PC*가 아니라 *서버의* localhost다. 초보자 1순위 실수. → [[딥링크와 루프백]]
- **`-R`로 연 포트는 기본적으로 서버의 루프백에만 바인딩된다.** 외부에 열려면 서버 `sshd_config`의 `GatewayPorts`를 바꿔야 하는데(기본 `no`), **켜는 순간 사내 서비스가 인터넷에 열릴 수 있다.** 켜기 전에 두 번 생각할 것.
- **`-N`(명령 실행 안 함) · `-f`(백그라운드)** 를 붙여 터널 전용으로 띄우는 게 관례. 끊김 대비는 `autossh` 또는 systemd. → [[systemd]]
- 중간 경유만 필요하면 포워딩이 아니라 **`-J`(ProxyJump)** 가 정답이다 → [[베스천 서버]]

### ⚠️ 터널이 깨지는 자리 — 실무 함정 모음

**① MTU — 가장 흔하고 가장 안 보이는 범인**
봉투가 하나 늘었으니 **실을 수 있는 내용물이 줄어든다.** WireGuard는 IPv4 기준 **60B**(IP 20 + UDP 8 + WG 32)를 먹어 터널 내부 MTU 기본값이 **1420**이고, VXLAN은 **50B**, GRE는 **24B**를 가져간다.

증상이 악명 높다 — **"ping은 되는데 큰 파일·HTTPS만 멈춘다."** 작은 패킷은 통과하고 큰 패킷만 죽기 때문이다. 원인은 보통 **PMTUD 블랙홀**(경로의 어떤 장비가 ICMP "Fragmentation Needed"를 막아버림).

> 💊 **처방은 MSS 클램핑.** TCP SYN의 MSS 값을 터널에 맞게 깎아 양쪽이 애초에 작게 보내도록 합의시킨다(WG MTU 1420 → MSS 1380). **ICMP가 살아있는지에 의존하지 않아 가장 확실한 해법.** 단, 클램핑은 TCP만 구한다 — UDP·QUIC은 애플리케이션이 알아서 해야 한다.

**② TCP-over-TCP — UDP 터널이 기본값인 이유**
TCP 터널 안에 TCP를 흘리면 **재전송 제어 루프가 두 겹으로 겹친다.** 패킷이 유실되면 바깥 TCP가 재전송하며 지연이 생기고, 안쪽 TCP는 그 지연을 보고 "유실됐나 보다" 하며 **또** 재전송을 쌓는다. 쌓이는 속도가 처리 속도를 넘으면 처리량이 무너진다(**TCP meltdown**).

그래서 WireGuard·IPsec·OpenVPN-UDP가 **UDP를 쓴다** — 바깥이 재전송을 안 하니 안쪽 TCP 혼자만 제어하면 된다. OpenVPN을 TCP 모드로 돌리는 건 *"UDP가 막힌 네트워크"* 라는 명확한 이유가 있을 때만. (⚠️ 손실 없는 망에서는 체감이 거의 없어 "미신"이라는 반론도 있다. 정확히 말하면 **손실률이 올라갈수록 급격히 나빠지는 구조적 약점**이다.)

**③ 터널을 살려두는 것 ≠ 터널 안 연결을 살려두는 것**
NAT·방화벽은 조용한 연결을 **상태 표에서 지운다.** WireGuard `PersistentKeepalive=25`는 **바깥 UDP 매핑**만 지키지, 그 안에 감싸인 TCP 연결은 못 지킨다. 계층이 다르면 **계층마다 keepalive가 따로** 필요하다. → [[TCP Keepalive]] · 실제 장애 사례는 [[긴 요청 응답 유실 (NAT 연결 만료)]]

**④ 라우팅·DNS가 조용히 바뀐다**
VPN이 올라오면 기본 경로가 바뀌어 **엉뚱한 쪽으로 나가거나(스플릿 터널 오설정), 사내 DNS를 못 찾거나, 반대로 모든 질의가 사내로 샌다.** "VPN 켜면 느리다/특정 사이트만 안 된다"의 대부분이 여기. → [[DNS]]

**⑤ 같은 사설 대역 충돌**
양쪽 다 `192.168.0.0/24`를 쓰면 터널을 붙여도 라우팅이 성립하지 않는다. 터널을 설계할 때 **대역부터 겹치지 않게** 잡는다.

**⑥ 이중 암호화의 비용**
터널 암호화 + 안쪽 TLS는 대개 **중복**이다. 보안이 두 배가 되지 않고 CPU와 지연만 두 배가 된다. 안쪽이 이미 TLS면 터널의 역할은 *기밀성*이 아니라 *도달성*임을 분명히 할 것. → [[HTTP와 HTTPS]]

### 🔒 보안 — 터널은 "경계를 뚫는 도구"다
- **방어 측 관점에서 터널은 우회 그 자체다.** CISA의 Akira 랜섬웨어 권고는 공격자가 **ngrok** 같은 터널링 도구로 암호화된 C2 세션을 만들어 경계 모니터링을 회피했다고 적시했고, **Cloudflare Tunnel(특히 무료 TryCloudflare)** 을 악용해 자기 인프라를 감춘 캠페인(SERPENTINE#CLOUD 등)도 계속 보고된다. Splunk 등은 `cloudflared` 실행 인자를 탐지 룰로 운영한다.
- **DNS 터널링**은 거의 순수한 악용 채널이다(MITRE ATT&CK **T1071.004**, 유출은 **T1048**). `iodine`·`dnscat2`·`dns2tcp` 같은 도구가 데이터를 서브도메인에 실어 보낸다 — `aGVsbG8…​.data.attacker.com`. 탐지는 **질의 이름 길이 · 엔트로피 · 한 상위도메인에 몰리는 고유 서브도메인 수** 세 지표로 상당히 잡힌다. → [[허니팟]] · [[오탐]]
- **그래서 CISO들이 개발자 터널을 막는다.** "잠깐 데모용"으로 연 ngrok 하나가 **인증 없는 내부 서비스를 인터넷에 직결**하는 사례가 실제로 반복됐다.

> 🏢 **사내 정책(휴레이)** — ngrok·localtunnel·cloudflared·serveo 같은 **터널링으로의 외부 공유는 금지**. 내부 공유는 **사내망 `IP:Port` 로컬 호스팅**으로 한다. 불가피한 예외는 보안 담당 판단. → [[ISMS]]

### 🔍 터널이 안 될 때 보는 순서
1. **바깥 터널이 서 있나** — WG `wg show`의 latest handshake, SSH는 `-v`. 바깥이 안 서면 안쪽을 볼 필요가 없다.
2. **경로가 터널로 가고 있나** — `ip route get <대상>` / `traceroute`. 터널은 올라왔는데 트래픽이 터널로 안 가는 경우가 흔하다.
3. **방향이 맞나** — `-L`인가 `-R`인가, 목적지 주소를 **누구 기준**으로 썼나.
4. **바인딩 주소 확인** — `ss -tlnp` / `lsof -iTCP -sTCP:LISTEN -P`. `127.0.0.1`인지 `0.0.0.0`인지까지 본다(`GatewayPorts`).
5. **작은 건 되는데 큰 게 안 되면 → MTU.** `ping -M do -s 1400 <대상>`(리눅스) / `ping -D -s 1400`(macOS)으로 통과 크기를 이진 탐색하고 MSS 클램핑.
6. **한참 뒤에 끊기면 → NAT 만료**. 계층마다 keepalive를 건다.
7. **양쪽 사설 대역이 겹치지 않는지** 마지막으로 확인.

## 왜 중요한가
- **현대 인프라는 전부 터널 위에 서 있다.** 사내 VPN, 쿠버네티스 오버레이 네트워크(VXLAN), 클라우드 간 연결, 서비스 메시의 mTLS — 평소에 안 보일 뿐 패킷은 늘 봉투 안에 들어 있다. → [[쿠버네티스]] · [[컨테이너와 Docker]]
- **"왜 ping은 되는데 파일 전송만 멈추지"** 같은 비정상적으로 어려운 장애가 거의 다 터널에서 나온다. MTU·TCP-over-TCP·NAT 만료라는 세 가지 패턴을 알면 며칠 걸릴 문제를 몇 분으로 줄인다.
- **보안 경계를 다시 정의한다.** 방화벽이 지키는 건 "포트"인데 터널은 **포트를 열지 않고도** 경계를 통과한다. 개발 편의를 위해 판 터널이 그대로 침투 경로가 되기 때문에, 쓰는 쪽도 막는 쪽도 원리를 알아야 한다.
- **도구 선택의 기준이 된다.** "IP를 싣나 TCP 스트림을 싣나", "누가 먼저 connect 하나" — 이 두 질문만 명확히 하면 VPN·SSH 터널·리버스 터널 중 무엇이 맞는지 바로 나온다.

> ✅ **웹 교차검증 완료** — SSH 포트 포워딩 3종(`-L` 로컬 / `-R` 리모트 / `-D` 다이나믹 SOCKS)과 **목적지가 SSH 서버 기준으로 해석된다**는 점, **`-R`로 연 포트는 기본적으로 서버 루프백에만 바인딩되며 `sshd_config`의 `GatewayPorts` 기본값이 `no`** 라는 점을 복수 SSH 튜토리얼로 확인. **ProxyJump(`-J`)는 OpenSSH 7.3(2016)에서 도입**되어 `ProxyCommand ssh -W`를 대체했고, **에이전트 포워딩(`ForwardAgent yes`)은 점프 호스트가 털리면 내 키로 인증당할 수 있어 ProxyJump가 더 안전**하다는 점 확인. **WireGuard 오버헤드 IPv4 60B(IP 20 + UDP 8 + WG 32)·기본 MTU 1420·기본 포트 UDP 51820**, **VXLAN은 RFC 7348·UDP 4789·오버헤드 약 50B**, **GRE는 IP 프로토콜 47·약 24B**, **IPsec NAT-T는 UDP 4500**, **MSS 클램핑이 ICMP 가용성에 의존하지 않아 가장 신뢰할 만한 MTU 해법**이라는 점을 WireGuard/VXLAN/MTU 문서로 확인. **TCP meltdown**(바깥·안쪽 TCP 제어 루프 간섭으로 재전송이 중첩되어 처리량 붕괴, UDP 터널이면 회피)은 OpenVPN 공식 FAQ와 SPIE 논문 *Understanding TCP over TCP*로 확인. **HTTP CONNECT는 RFC 9110 §9.3.6**(프록시 대상, 2xx면 터널 모드 전환, 포트 필수, 프록시는 안전한 포트로 제한 SHOULD), **MASQUE는 CONNECT-UDP(RFC 9298)·CONNECT-IP(RFC 9484)** 로 HTTP/3 위에서 UDP·IP를 프록시한다는 점을 RFC 원문으로 확인. 악용 사례는 **CISA Akira 권고(ngrok 등 터널링 유틸로 C2)**, **Securonix SERPENTINE#CLOUD(Cloudflare Tunnel·TryCloudflare 악용)**, **Splunk의 cloudflared 실행 탐지 룰**로 확인. **DNS 터널링은 MITRE ATT&CK T1071.004(DNS C2)·T1048(대체 프로토콜 유출)** 에 매핑되고 iodine·dnscat2·dns2tcp가 대표 도구이며 **질의 길이·엔트로피·고유 서브도메인 수**가 핵심 탐지 지표임을 ATT&CK 및 탐지 룰 문서로 확인.
