# 딥링크와 루프백 (Deep Link & Loopback)

## 한 줄 정의
**브라우저에서 끝난 일(로그인 승인·결제·연동)을, 내 기기에서 돌고 있는 앱에게 되돌려주는 두 가지 배달 경로.** 딥링크는 **OS가 URL을 앱에게 배달**하고, 루프백은 **앱이 자기 기기 안에 임시 웹서버를 열어 브라우저를 그 주소로 보낸다.**

> 두 방식이 답하는 질문은 하나다 — **"응답을 어디로 돌려주지?"** 앱에서 브라우저로 **나가는 길**은 어느 OS에서나 쉽다(그냥 URL을 연다). 어려운 건 늘 **돌아오는 길**이고, 딥링크와 루프백은 그 귀로(歸路)를 만드는 서로 다른 두 가지 방법이다.

## 자세히

### 왜 이 문제가 생기나 — 앱은 브라우저를 "빌려" 쓴다
네이티브 앱이 로그인을 앱 안의 웹뷰로 처리하면 편하다. 그런데 **RFC 8252(OAuth 2.0 for Native Apps)는 그걸 금지한다** — *"native apps MUST NOT use embedded user-agents"*. 이유는 두 가지다.

- **앱이 사용자의 비밀번호를 볼 수 있다.** 웹뷰는 앱의 소유물이라 키 입력·쿠키·DOM을 다 들여다볼 수 있다. "구글로 로그인"의 전제(=구글만 비번을 본다)가 무너진다.
- **기존 로그인 세션을 재사용할 수 없다.** 시스템 브라우저에 이미 로그인돼 있어도 웹뷰는 별도 쿠키 저장소라 매번 처음부터다. → [[쿠키 세션 JWT]]

그래서 흐름은 반드시 **앱 → 시스템 브라우저 → (사용자 승인) → 다시 앱**이 된다. 마지막 화살표를 만드는 방법이 RFC 8252 §7의 세 가지다.

```
§7.1 커스텀 스킴(private-use)   com.example.app:/oauth2redirect   ┐
§7.2 클레임된 https             https://app.example.com/callback  ┘ → 딥링크 (OS가 배달)
§7.3 루프백 인터페이스           http://127.0.0.1:{임의포트}/callback  → 루프백 (내가 받는다)
```

### 두 경로를 그림으로

```
① 딥링크 — OS가 배달한다
   [앱] ──열기──▶ [시스템 브라우저] ──승인──▶ [인가 서버]
                                                │ 302 Location: myapp://callback?code=…
                                                ▼
                                          [   OS   ] ──"이 URL 주인 누구?"──▶ [앱]
   ▲ 서버가 필요 없다. 대신 "그 URL의 주인이 정말 이 앱인가"를 OS가 판정해야 한다.

② 루프백 — 내가 받는다
   [앱] ─ 0번 포트로 bind → OS가 빈 포트(예: 54738) 배정
     │    http://127.0.0.1:54738/callback 로 임시 웹서버 기동
     └──열기──▶ [시스템 브라우저] ──승인──▶ [인가 서버]
                                                │ 302 Location: http://127.0.0.1:54738/callback?code=…
                                                ▼
                                      [브라우저가 그 주소로 이동] ──▶ [앱의 임시 서버]
                                                                        └─ code 받고 서버 즉시 종료
   ▲ OS 등록이 전혀 필요 없다. 대신 "브라우저와 앱이 같은 기기에 있다"가 전제다.
```

`gh auth login`, `gcloud auth login`, `aws sso login`, Claude Code·Cursor의 MCP 로그인 — 터미널에서 로그인하면 브라우저가 열리고 *"이 창을 닫아도 됩니다"* 가 뜨는 그 흐름이 전부 ②다.

### 루프백이란 — 밖으로 나가지 않는 주소
- **IPv4 `127.0.0.0/8` 전체**(관례적으로 `127.0.0.1`), **IPv6 `::1/128`**.
- 물리 랜카드가 아니라 **가상 인터페이스(`lo`)** 다. 패킷이 케이블·와이파이를 타지 않고 **커널이 그대로 되돌린다.** 그래서 랜선을 뽑아도 `ping 127.0.0.1`은 된다. → [[NIC]] · [[TCP-IP]]
- 원래 용도는 **자기 자신과 통신하기** — 로컬 개발 서버(`localhost:3000`), DB 클라이언트, 그리고 이 노트의 주제인 **콜백 수신**.

⚠️ **`localhost`는 주소가 아니라 이름이다.** `127.0.0.1`은 IP 리터럴이고, `localhost`는 **hosts 파일·DNS 해석을 한 번 거치는 호스트명**이다. 그 차이가 실제 사고를 만든다 → 아래 §7.3.

⚠️ **루프백은 "내 기기"라는 경계이지 "내 앱"이라는 경계가 아니다.** 같은 기기에서 도는 **다른 프로세스는 얼마든지 접근할 수 있다.** 루프백에 띄운 서버는 "안전한 곳"이 아니라 "밖에서 못 오는 곳"일 뿐이다.

### 비교표
| | **딥링크** | **루프백** |
|---|---|---|
| 되돌아오는 방식 | OS가 URL을 앱에 전달 | 브라우저가 앱의 임시 서버에 HTTP 요청 |
| 사전 준비 | OS 등록(스킴) 또는 도메인 소유권 검증(AASA·assetlinks) | 없음. 실행 시 포트만 잡으면 끝 |
| 서버 필요 | ❌ | ✅ (앱 내부, 수초간) |
| 전제 조건 | 앱이 **설치**돼 있어야 | 브라우저와 앱이 **같은 기기**에 있어야 |
| 주 무대 | **모바일**(iOS·Android), 데스크톱 GUI 앱 | **데스크톱·CLI**, 개발 도구 |
| 스킴 | `myapp://` 또는 `https://` | `http://` (TLS 없이) |
| 가로채기 위험 | 커스텀 스킴은 **다른 앱이 같은 스킴 선점** 가능 | 같은 기기의 **다른 프로세스가 포트 선점** 가능 |
| 대표적 실패 | 검증 실패 → 조용히 브라우저로 감 | 원격·컨테이너 환경에서 127.0.0.1이 서로 다른 기기 |
| 공통 방어 | **[[PKCE]] + `state`** | **[[PKCE]] + `state`** |

> 두 방식의 위험이 대칭인 게 핵심이다. 딥링크는 *"이 URL의 주인이 정말 이 앱인가"*, 루프백은 *"이 포트를 잡은 게 정말 그 앱인가"* — **둘 다 OS가 보증해 주지 않는다.** 그래서 어느 쪽을 쓰든 **PKCE가 선택이 아니라 필수**다(RFC 8252 §6: 퍼블릭 네이티브 클라이언트는 PKCE를 **MUST** 구현).

### 루프백 리다이렉트의 규칙 — 여기서 대부분 깨진다

**① 포트는 실행할 때마다 달라진다 (§7.3)**
> *"The authorization server **MUST** allow any port to be specified at the time of the request for loopback IP redirect URIs."*

앱은 OS에게 **임시 포트(ephemeral port)** 를 받아 쓴다(포트 0으로 bind). 고정 포트를 쓰면 이미 다른 프로그램이 점유했을 때 로그인이 통째로 막히기 때문이다. 그래서 **인가 서버는 등록된 리다이렉트 URI와 포트가 달라도 통과시켜야 한다.**

**② 그 예외는 `127.0.0.1`·`::1`에만 적용된다 (§8.3)**
> *"the use of `localhost` is NOT RECOMMENDED"* — ⓐ 다른 인터페이스에 잘못 바인딩될 위험을 피하고, ⓑ 클라이언트 방화벽·잘못된 호스트명 해석에 더 강하기 때문.

⚠️ **RFC를 충실히 구현한 인가 서버는 포트 유연성을 IP 리터럴에만 준다.** `localhost`는 그냥 호스트명이므로 **문자 그대로 정확히 일치**해야 한다. 그래서 `http://localhost:54738/callback`을 보내면 **`invalid_redirect_uri`로 튕긴다.**

> 📌 **실제 사례** — Claude Code는 등록 메타데이터에 포트 없는 `http://localhost/callback`을 쓰고 실행 시 임시 포트를 붙여 보낸다. Spring Authorization Server처럼 RFC를 엄격히 따르는 사내 IdP에서는 이 조합이 **매번 리다이렉트 검증 실패**로 끝난다(anthropics/claude-code #42765, 열린 이슈). 고칠 방법은 하나 — **`127.0.0.1`로 보낼 것.**

**③ `http`인데 왜 괜찮나**
패킷이 기기 밖으로 나가지 않으므로 네트워크 도청 대상이 아니다. 그래서 루프백은 OAuth에서 **평문 http가 정상적으로 허용되는 거의 유일한 자리**다. 반대로 말하면, **같은 기기 안의 프로세스에는 무방비**라는 뜻이기도 하다. → [[HTTP와 HTTPS]]

**④ 그래서 같이 지켜야 할 것**
- **PKCE** — 코드를 누가 주워가도 `code_verifier` 없이는 토큰으로 못 바꾼다.
- **`state`** — 다른 사이트가 내 루프백 주소로 가짜 콜백을 밀어 넣는 것(로그인 CSRF)을 막는다. → [[CSRF]]
- **코드를 받는 즉시 서버 종료**, 그리고 **받은 요청이 내가 기대한 경로·`state`인지 확인**. 열어 둔 채 방치하면 그게 곧 로컬 공격면이다.

### 딥링크 쪽은 어떻게 다른가 (요약)
- **커스텀 스킴**(`myapp://`)은 **소유권 검증이 없다.** 악성 앱이 같은 스킴을 등록하면 코드가 그쪽으로 간다 — PKCE가 태어난 배경이 정확히 이것.
- **Universal Links(iOS)·App Links(Android)** 는 `.well-known` 파일로 **도메인 소유권을 OS가 검증**한다. RFC 8252도 이쪽(§7.2)을 **우선 권장**한다.
- 자세한 설정·디버깅은 → **[[딥링크]]**

### 언제 무엇을 쓰나
| 상황 | 기본 선택 | 이유 |
|---|---|---|
| 모바일 앱 | **딥링크**(Universal/App Links) | 모바일은 앱이 서버를 여는 게 부자연스럽고 OS 제약도 크다 |
| 데스크톱 GUI 앱 | 딥링크(프로토콜 핸들러) 또는 루프백 | 설치형이라 스킴 등록이 가능. 다만 IdP 호환성은 루프백이 낫다 |
| **CLI·개발 도구** | **루프백** | 등록할 스킴도, 도메인도 없다. 포트만 있으면 된다 |
| 원격 서버·SSH·컨테이너·헤드리스 | **둘 다 불가 → 장치 코드 흐름**(RFC 8628) | 브라우저가 다른 기기에 있다. 코드를 화면에 띄우고 폰으로 승인 |
| 웹앱(SPA 포함) | 평범한 https 리다이렉트 | 애초에 브라우저 안이다 |

### ⚠️ 루프백이 깨지는 자리 모음
- **원격 개발 환경이 1순위 함정.** SSH로 접속한 서버에서 `gh auth login`을 하면, 앱은 **서버의** `127.0.0.1`에 서버를 열고 브라우저는 **내 노트북의** `127.0.0.1`을 연다. 같은 문자열이지만 **다른 기기다.** → `ssh -L 54738:127.0.0.1:54738`로 포워딩하거나, 장치 코드 흐름으로 전환.
- **컨테이너도 같은 문제.** 컨테이너 안의 `localhost`는 **컨테이너 자신**이다. 호스트를 가리키려면 `host.docker.internal`(또는 `--network host`). → [[컨테이너와 Docker]]
- **IPv4/IPv6 엇갈림.** 앱은 `::1`에만 바인딩했는데 브라우저는 `127.0.0.1`로 접속(또는 그 반대) → "연결할 수 없음". 둘 다 바인딩하거나, 보낸 리다이렉트 URI와 **정확히 같은 주소 계열**에 바인딩할 것.
- **포트를 고정으로 등록하라는 IdP.** RFC를 안 따르는 서버가 꽤 있다. 고정 포트를 쓰면 **점유 충돌**과 **다른 프로세스의 선점**을 같이 떠안게 된다.
- **방화벽·보안 제품**이 로컬 리스닝 소켓을 막거나 프롬프트를 띄우는 경우(사내 EDR에서 흔하다).
- **브라우저 정책 변화** — Chrome 142(2025-10)부터 **Local Network Access**로 공개 사이트 → 로컬/루프백 요청에 권한 프롬프트가 붙었다. 다만 초기 적용 대상은 **`fetch()`·서브리소스·서브프레임 내비게이션**이라, **OAuth 콜백처럼 최상위 탐색으로 루프백에 가는 흐름은 그대로 동작한다.** 영향을 받는 건 *"웹페이지가 백그라운드로 로컬 앱을 호출하던"* 패턴 쪽이다(로컬 에이전트·프린터 연동 등).
- **macOS 로컬 네트워크 권한**은 LAN 접근에 프롬프트를 띄우지만 **루프백(`127.0.0.1`·`::1`)은 예외**다 — 기기 밖으로 나가지 않기 때문. LAN MCP 서버는 막히는데 로컬은 되는 이유가 이것.
- **Google 정책의 비대칭** — 루프백 흐름은 **데스크톱 클라이언트에서는 계속 지원**되지만, **iOS·Android·Chrome 앱 클라이언트에는 2022년에 차단**됐다(신규 2022-03-14, 기존 2022-08-31). 별개로 **OOB(복붙) 흐름은 2023-01-31에 완전히 죽었다.** "예제 코드가 오래된 건데 왜 안 되지"의 절반은 여기서 나온다.
- **MCP 생태계의 파편화** — 데스크톱 에이전트는 `claude://`·`cursor://` 같은 커스텀 스킴을, CLI는 루프백을 보낸다. 그런데 *"리다이렉트 URI는 HTTPS이거나 루프백이어야 한다"* 며 커스텀 스킴을 거부하는 MCP 서버가 있어서, **같은 계정인데 CLI는 되고 데스크톱은 안 되는** 상황이 실제로 생긴다. 서버를 만든다면 **두 패턴을 모두 받아주는 쪽**이 안전하다.

### 🔍 안 될 때 보는 순서
1. **브라우저와 앱이 같은 기기인가.** 아니라면 루프백은 애초에 성립하지 않는다(SSH·원격 컨테이너·서버). → 포트 포워딩 또는 장치 코드 흐름.
2. **보낸 `redirect_uri`를 실제로 확인한다.** 브라우저 주소창의 인가 요청 URL에 그대로 들어 있다. `localhost`인가 `127.0.0.1`인가?
3. **에러가 `invalid_redirect_uri` 계열이면 IdP 쪽 매칭 문제.** 등록값과 포트 유연성 정책을 본다(§7.3을 지키는 서버인가).
4. **브라우저는 넘어갔는데 앱이 못 받으면** 리스닝 확인: `lsof -iTCP -sTCP:LISTEN -P | grep <포트>` — 주소가 `127.0.0.1`인지 `[::1]`인지 `*`인지까지 본다.
5. **딥링크 쪽이면** 증상이 완전히 다르다(브라우저에 머문다/에러 페이지). → [[딥링크]]의 진단 순서로.
6. 계속 막히면 **장치 코드 흐름으로 우회**할 수 있는지 확인. 원격·헤드리스에서는 그게 정답인 경우가 많다.

## 왜 중요한가
- **"로그인 창은 떴는데 앱으로 안 돌아온다"** — 개발자가 가장 자주 만나는 인증 장애가 거의 다 이 귀로에서 난다. 원인을 모르면 몇 시간이 날아가고, 구조를 알면 5분이면 어느 쪽이 깨졌는지 좁혀진다.
- **에이전트·CLI 도구가 쏟아지면서 루프백이 다시 최전선이 됐다.** `gh`·`gcloud`·MCP 클라이언트·코딩 에이전트가 전부 이 방식으로 로그인한다. 동시에 그 도구들이 **원격 서버와 컨테이너 안에서** 돌기 때문에 "같은 기기" 전제가 깨지는 일도 같이 늘었다.
- **`localhost`와 `127.0.0.1`은 같은 말이 아니다** — 평소엔 구분할 일이 없다가, 하필 인증 리다이렉트 검증에서 갈린다. 규격 한 줄(§8.3)이 실제 제품 버그가 되는 좋은 예다.
- **보안 경계를 오해하기 쉬운 자리**다. "로컬이니까 안전하다"는 직관은 **네트워크에 대해서만** 맞고, **같은 기기의 다른 프로세스에 대해서는 틀리다.** PKCE와 `state`가 로컬 흐름에도 그대로 필요한 이유다.
