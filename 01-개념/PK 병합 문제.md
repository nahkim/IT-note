# PK 병합 문제 (Auto Increment PK 충돌)

## 한 줄 정의
**각자 1번부터 번호를 매기던 두 테이블(또는 두 DB)의 데이터를 한곳으로 합칠 때, 서로 다른 행이 같은 PK 값을 들고 부딪히는 문제.** 회사 합병·서비스 통합·샤드 병합·테스트→운영 이관에서 반드시 만난다. 그리고 **진짜 난이도는 PK 자체가 아니라, 그 PK를 가리키고 있던 모든 것**(외래키·URL·캐시·로그·외부 연동)을 함께 갈아 끼우는 데 있다.

## 자세히

### 무엇이 부딪히나
```
[A 서비스]                      [B 서비스]
users     id 1..1,000           users     id 1..800
orders    user_id → users.id    orders    user_id → users.id

           ↓ 하나의 DB로 합치면

users.id = 7 이 두 명이 된다.          ← ① 키 값 충돌
같은 사람(kim@x.com)이 양쪽에 있다.     ← ② 개체 중복
합친 뒤 INSERT하면 id 500이 또 나온다. ← ③ 시퀀스 현재값 미보정
orders.user_id = 7 은 누구를 가리키나?  ← ④ 참조 파괴 ★진짜 문제
```

세 가지를 구분해서 다뤄야 한다. **①은 값만 바꾸면 되고, ②는 업무 규칙(누가 진짜인가)이 필요하며, ④는 DB 밖까지 번진다.**

### 해결 전략 네 가지
| 전략 | 방법 | 장점 | 대가 |
|---|---|---|---|
| **① 오프셋 재배치** | B의 모든 id에 `+1,000,000`을 더해 삽입 | 가장 단순, 원래 순서 유지 | 이번만 해결(다음 병합 때 또), 모든 FK·외부 참조 일괄 변경, id가 듬성듬성해짐 |
| **② 매핑 테이블 + 새 채번** ⭐ | B 행을 그냥 INSERT해 **새 id를 받고**, `(원본, 옛 id) → 새 id` 표를 남겨 자식 FK를 치환 | **되돌릴 수 있고 검증·재실행 가능**, 중복 병합과 함께 처리 가능 | 절차가 길다, 부모→자식 순서 관리 |
| **③ 복합키·판별자 추가** | PK를 `(source, id)` 또는 `(tenant_id, id)`로 | 원래 id를 **그대로 보존** | 스키마·모든 쿼리·FK·ORM 매핑 변경 → [[멀티테넌시]] 전환 시에나 정당화됨 |
| **④ 전역 유일 ID로 전환** | UUIDv7·ULID·Snowflake로 PK 교체 | **다음 병합부터 문제 자체가 사라짐** | 전면 마이그레이션 비용, 인덱스 크기 증가 |

실무 기본값은 **②**, 장기적으로 옳은 답은 **④**다. ①은 "한 번 합치고 끝"이 확실할 때만.

### 매핑 테이블 방식 — 실제 절차
```sql
-- 1) 매핑표부터 만든다. 이 표가 전체 작업의 원장(ledger)이자 롤백 근거다.
CREATE TABLE id_map_users (
  src      text   NOT NULL,      -- 'B'
  old_id   bigint NOT NULL,
  new_id   bigint NOT NULL,
  PRIMARY KEY (src, old_id)
);

-- 2) 부모 테이블부터. 삽입하면서 새 id를 받아 매핑에 기록 (PostgreSQL)
WITH ins AS (
  INSERT INTO users (email, name, created_at)
  SELECT email, name, created_at FROM b_users
  ON CONFLICT (email) DO NOTHING          -- 이미 있는 사람은 새로 만들지 않는다
  RETURNING id, email
)
INSERT INTO id_map_users (src, old_id, new_id)
SELECT 'B', b.id, ins.id FROM ins JOIN b_users b USING (email);

-- ⚠️ ON CONFLICT DO NOTHING은 "충돌한 행"을 RETURNING하지 않는다.
--    → 기존 회원과 겹친 건은 별도로 조회해 매핑을 채워야 한다. 빼먹으면 자식이 통째로 유실된다.
INSERT INTO id_map_users (src, old_id, new_id)
SELECT 'B', b.id, u.id FROM b_users b JOIN users u USING (email)
ON CONFLICT DO NOTHING;

-- 3) 자식 테이블은 FK를 매핑으로 치환해 삽입
INSERT INTO orders (user_id, amount, created_at)
SELECT m.new_id, o.amount, o.created_at
FROM b_orders o JOIN id_map_users m ON m.src = 'B' AND m.old_id = o.user_id;

-- 4) 시퀀스 현재값 보정 — 이걸 빼먹으면 다음 INSERT부터 duplicate key 지옥
SELECT setval(pg_get_serial_sequence('users','id'), (SELECT MAX(id) FROM users));
-- MySQL:  ALTER TABLE users AUTO_INCREMENT = <MAX(id)+1>;
```

> ⚠️ PostgreSQL에서 `GENERATED ALWAYS AS IDENTITY` 컬럼에 id를 직접 넣으려면 `INSERT ... OVERRIDING SYSTEM VALUE`가 필요하다. 그리고 **id를 직접 넣은 뒤에는 반드시 `setval` 보정**이 따라와야 한다(4번을 잊는 것이 이 작업의 1등 실수).

### 순서와 제약조건
- **부모 → 자식 순서**로 넣는다. 순서를 지킬 수 없으면 제약을 미룬다: PostgreSQL `SET CONSTRAINTS ALL DEFERRED`(FK가 `DEFERRABLE`이어야 함), MySQL `SET FOREIGN_KEY_CHECKS = 0`.
- ⚠️ 제약을 끄면 **무결성 검증 없이 데이터가 들어간다.** 끝난 뒤 고아 행 검증 쿼리를 반드시 돌릴 것.
- **자기참조**(댓글의 parent_id, 조직의 상위부서)는 한 번에 안 된다 → 먼저 `NULL`로 넣고, 매핑 완성 후 `UPDATE`로 채운다. → [[계층형 데이터 모델링]]
- **다형 참조**(`target_type` + `target_id` 조합처럼 FK를 걸 수 없는 참조)는 **DB가 하나도 안 잡아준다.** 매핑 누락이 가장 많이 나오는 자리.

### 잊기 쉬운 "PK를 가리키던 것들" 체크리스트
DB 안은 SQL로 해결된다. 문제는 **이미 밖으로 나간 id**다.

- [ ] FK가 없는 참조 컬럼, 다형 참조, **JSON·배열 컬럼 안에 박힌 id**
- [ ] 로그·감사 테이블, 이벤트 스트림·큐에 떠 있는 메시지 → [[메시지 큐]]
- [ ] 캐시 키(`user:123`), 검색 인덱스 문서 id, 벡터DB payload → [[캐시]] · [[벡터DB]]
- [ ] **외부 URL**(`/orders/123`), 사용자 북마크, 발송된 이메일 링크 → [[URL 구조]]
- [ ] 스토리지 경로(`s3://bucket/users/123/avatar.png`) → [[S3 Presigned URL]]
- [ ] 모바일 앱 로컬 DB에 캐시된 id, 오프라인 큐
- [ ] 서드파티 연동(결제사 주문번호, 배송사 송장, CRM), 분석 도구·데이터 웨어하우스·BI 대시보드
- [ ] 고객이 엑셀로 내려받아 들고 있는 리포트 ← 회수 불가

**교훈: ID를 바꾸는 비용은 대부분 DB 밖에서 발생한다.** 그래서 구 id → 신 id 매핑표는 작업이 끝나도 **버리지 말고 영구 보존**한다(구 URL 301 리다이렉트, 고객 문의 대응, 사후 추적에 계속 쓰인다).

### 중복 개체 처리 — 병합의 나머지 절반
같은 사람·같은 상품이 양쪽에 있으면 키 충돌과는 별개의 **업무 결정**이 필요하다.

- **동일성 기준(자연키)을 먼저 정한다** — 이메일? 휴대폰? 사업자번호? 이름+생년월일은 거의 항상 부족하다.
- **승자 규칙** — 최신 갱신본, 결제 이력이 있는 쪽, 더 완전한 레코드 중 무엇을 남길지.
- **패자의 자식 데이터는 승자에게 이관**하고, 패자 행은 지우지 말고 `merged_into_id`로 표시해 남긴다(soft merge) → 되돌릴 수 있고, 예전 id로 들어온 요청을 승자에게 넘길 수 있다.
- 자동으로 못 정하는 애매한 건은 **보류 큐**로 빼서 사람이 판단한다. 잘못 합친 두 사람을 다시 떼어내는 비용이 훨씬 크다.

### 안전하게 수행하는 운영 절차
1. **운영 스냅샷 복사본에서 전체 리허설** — 행 수·합계 금액·고아 FK 수를 사전/사후 비교. → [[드라이런]]
2. **스크립트를 멱등하게** — 이미 매핑이 있으면 건너뛰게 짜서 중간 실패 후 재실행이 가능해야 한다. → [[멱등성]]
3. **큰 UPDATE는 청크로** — 수백만 행을 한 트랜잭션에 담으면 락·복제 지연·롤백 시간이 폭발한다. → [[트랜잭션과 ACID]] · [[데이터베이스 복제]]
4. **검증 쿼리를 미리 작성** — 고아 FK 0건, 원본 대비 행 수 일치, 합계·체크섬 일치, 매핑 누락 0건.
5. **컷오버 계획** — 쓰기 차단 창을 짧게 두거나, 병행 기간 동안 신규 데이터를 델타 동기화한 뒤 전환. → [[무중단 배포]]
6. **롤백 시나리오** — 되돌릴 수 없는 작업이므로, "중단 지점까지의 상태"를 복원할 방법을 먼저 확보하고 시작한다.

### 애초에 안 겪는 설계
- **내부 PK와 외부 노출 ID를 분리한다** — 내부는 `bigint` 자동 증가(조인·인덱스에 유리), 외부에는 `public_id`(UUIDv7/ULID/slug)만 노출. 병합 때 **내부 PK는 마음대로 재배치해도 외부 참조가 안 깨진다.** 가성비가 가장 높은 패턴이고, 순차 id 노출로 인한 정보 유출(가입자 수 추정·[[OWASP Top 10|IDOR]])도 함께 막는다.
- **전역 유일 ID를 기본값으로** — **UUIDv7**(RFC 9562, 2024-05 표준화. 앞 48비트가 밀리초 타임스탬프라 **시간순 정렬 + 인덱스 지역성**을 유지. PostgreSQL 18에 `uuidv7()` 내장), **ULID**(Base32 문자열이 사전순=시간순), **Snowflake**(타임스탬프+머신ID+시퀀스). 반면 **UUIDv4는 완전 랜덤이라 인덱스 페이지가 흩어져** 삽입이 느리고 인덱스가 커진다. → [[데이터베이스 인덱스]]
- **채번 영역을 처음부터 나눈다** — MySQL 멀티마스터의 `auto_increment_increment=2` + `auto_increment_offset=1|2`(한쪽은 홀수, 다른 쪽은 짝수), 샤드별 id 범위 할당. → [[데이터베이스 샤딩]]
- **처음부터 `tenant_id`를 키에 포함**시키면 "테넌트 합치기"가 단순 데이터 이동이 된다. → [[멀티테넌시]]

## 왜 중요한가
- **합치는 일은 반드시 온다.** 인수합병, 서비스 통합, 레거시 이관, 샤드 축소, 계정 통합(같은 사람의 두 계정) — 규모만 다를 뿐 같은 문제다.
- **PK는 "그냥 숫자"가 아니라 시스템 전체에 흩뿌려진 참조의 앵커**다. 이 사실을 병합 당일에 깨달으면 이미 늦는다.
- **설계 시점의 5분이 나중의 몇 주를 아낀다.** "외부에는 내부 PK를 노출하지 않는다" 한 줄이면 병합 난이도가 한 단계 내려간다.
- 데이터 마이그레이션은 **되돌릴 수 없는 작업**이라, 리허설·멱등성·검증·매핑 보존이라는 절차 자체가 결과물의 일부다.

> ✅ **웹 교차검증 완료** — 자동 증가 PK를 쓰는 소스들을 합칠 때 키 범위가 겹쳐 충돌한다는 문제 정의와 **매핑 테이블(원본 id → 신규 id) 기반 자식 FK 재작성**이 표준 해법이라는 점, 대안으로 **전역 유일 ID(GUID/UUID) 전환**과 **(DatabaseID, id) 복합키**가 제시된다는 점을 TiDB 샤드 병합 가이드·Microsoft 동기화 문서·실무 해설로 확인. **UUIDv7은 RFC 9562(2024-05)로 표준화**되었고 앞 48비트 Unix 밀리초 타임스탬프 + 74비트 랜덤 구조로 **시간 정렬성과 인덱스 지역성**을 확보하며 **PostgreSQL 18이 `uuidv7()`를 내장**한다는 점, **UUIDv4는 랜덤 분포로 인덱스 페이지가 흩어져 삽입 성능·인덱스 크기에서 불리**하다는 점, **Snowflake ID = 41비트 타임스탬프 + 10비트 머신 + 12비트 시퀀스(밀리초당 4,096개)** 구조를 복수 기술 자료로 확인. PostgreSQL의 **identity 컬럼 직접 삽입 시 `OVERRIDING SYSTEM VALUE`와 임포트 후 `setval(...)` 보정 필요**, MySQL의 **`auto_increment_increment`/`auto_increment_offset`으로 채번 영역 분리**도 문서·실무 자료로 확인.
