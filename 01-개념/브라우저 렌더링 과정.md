# 브라우저 렌더링 과정 (Critical Rendering Path)

## 한 줄 정의
주소창에 URL을 입력한 뒤 **화면에 픽셀이 찍히기까지** 브라우저가 거치는 단계 — 네비게이션 → 파싱 → 렌더 트리 → 레이아웃 → 페인트 → 합성.

## 자세히

### 1) 네비게이션 (요청하기)
1. **URL 해석** — 스킴·호스트·경로 분해 ([[URL 구조]]).
2. **DNS 조회** — 도메인 → IP ([[DNS]]).
3. **TCP 연결 + TLS 핸드셰이크** ([[TCP-IP]], [[HTTP와 HTTPS]]).
4. **HTTP 요청/응답** — 첫 응답은 보통 HTML. (중간에 [[CDN]]·[[리버스 프록시]]·[[캐시]]가 개입)
5. 응답이 HTML이면 **렌더러 프로세스**에 넘겨 파싱 시작 ([[브라우저 프로세스와 사이트 격리]]).

### 2) 파싱 — DOM과 CSSOM
- HTML을 위에서부터 읽어 **[[DOM]] 트리**를 만든다. 도중에 만나는 `<img>`·`<link>`·`<script>`는 **프리로드 스캐너**가 미리 찾아 병렬로 내려받는다.
- CSS는 **CSSOM 트리**로 파싱된다. CSS는 **렌더 차단 리소스**: CSSOM이 완성되기 전에는 화면을 그리지 않는다(스타일 없는 화면의 깜빡임을 막기 위해).
- **`<script>`는 파서를 멈춘다.** 스크립트가 DOM을 바꿀 수 있어서. → `defer`(파싱 끝나고 순서대로 실행) / `async`(받는 대로 즉시 실행)로 해소.

### 3) 렌더 트리 (Style)
DOM + CSSOM을 합쳐 **실제로 보이는 노드**만 스타일과 함께 모은다. `display: none`은 렌더 트리에서 빠지고(`visibility: hidden`은 자리를 차지하므로 남는다).

### 4) 레이아웃(Layout / Reflow)
각 노드의 **정확한 위치·크기**를 계산한다. 뷰포트 크기·폰트·내용에 따라 값이 바뀐다. → 자세한 내용과 성능 함정은 **[[리플로우]]** 노트 참고.

### 5) 페인트(Paint)
색·테두리·그림자·텍스트를 **그리기 명령 목록**으로 변환. 요소들이 겹치는 순서(페인트 순서)도 여기서 결정된다.

### 6) 합성(Composite)
페이지를 **레이어**로 나눠 GPU에서 합친다. `transform`·`opacity`는 레이아웃·페인트를 건너뛰고 합성만 다시 하므로 애니메이션에 유리하다.

```
URL 입력 → DNS → TCP/TLS → HTTP 응답(HTML)
   ↓
HTML 파싱 → DOM ┐
CSS 파싱  → CSSOM ┘→ 렌더 트리 → 레이아웃 → 페인트 → 합성 → 화면
   ↑
JS(파서 차단) — DOM/CSSOM 조작 시 위 단계로 되돌아감
```

### 성능 관점에서 기억할 것
- **첫 화면을 늦추는 3대 요인**: 렌더 차단 CSS, 파서 차단 JS, 느린 서버 응답(TTFB).
- **핵심 웹 지표(Core Web Vitals)** — LCP(가장 큰 콘텐츠가 뜨는 시점), INP(상호작용 반응성), CLS(레이아웃 이동). 각각 위 파이프라인의 어느 지점이 병목인지를 가리킨다.
- JS는 **단일 스레드**([[이벤트 루프]])라 무거운 작업이 렌더링을 통째로 멈춘다.

## 왜 중요한가
- "주소창에 URL을 입력하면 무슨 일이 일어나나요?"는 웹 개발 면접의 고전 질문 — 네트워크·브라우저·렌더링 지식이 한 줄에 꿰인다.
- 어디를 최적화할지(서버 응답? CSS? JS? 애니메이션 방식?)를 **단계로 나눠 생각**할 수 있게 해준다.
