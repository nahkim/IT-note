# Depends와 미들웨어

## 한 줄 정의
**미들웨어**는 모든 요청을 통째로 감싸는 **바깥 껍질**(어느 엔드포인트인지 모름), **Depends**는 엔드포인트 안으로 **값을 주입하는 부품**(경로·파라미터·타입을 다 앎). "**요청 전체에 대한 가로채기**" vs "**이 엔드포인트에 필요한 준비물**".

## 자세히

### 실행 순서 — 누가 바깥이고 누가 안쪽인가
```
uvicorn(ASGI)
 └ ServerErrorMiddleware          ← 최후의 500 방어선
    └ 사용자 미들웨어 (add_middleware)   ← ❶ 라우팅 "전"에 돈다
       └ ExceptionMiddleware      ← @app.exception_handler 가 사는 곳
          └ 라우터 → 경로 매칭     ← ❷ 여기서 비로소 엔드포인트가 정해짐
             └ Depends 해석 + Pydantic 검증  ← ❸
                └ 엔드포인트 함수  ← ❹
```
- **미들웨어는 라우팅보다 바깥**이라, 실행 시점엔 아직 **어떤 엔드포인트인지·경로 파라미터가 뭔지 모른다**. 존재하지 않는 경로(404)·정적 파일 요청까지 전부 통과한다.
- **Depends는 라우팅 이후**라 경로/쿼리/헤더/바디가 **이미 파싱·검증된 상태**에서 돈다.
- `add_middleware`로 여러 개 등록하면 **마지막에 등록한 것이 가장 바깥** → 요청은 바깥→안, 응답은 안→바깥 역순.

### 비교표
| 기준 | 미들웨어 (Middleware) | 의존성 주입 (`Depends`) |
|---|---|---|
| 도는 위치 | **라우팅 전/후** (요청 전체를 감쌈) | **라우팅 후**, 엔드포인트 직전 |
| 적용 범위 | 앱 전역 (경로 선택 불가, 직접 `if`로 걸러야 함) | **엔드포인트 / 라우터 / 앱** 3단계로 선택 |
| 엔드포인트 정보 | 모름 (경로 문자열만 있음) | 다 앎 (경로·쿼리·바디·타입) |
| 값 전달 | `request.state` 에 끼워 넣는 **암묵적** 방식 | **함수 인자로 주입** (타입 힌트 = 명시적 계약) |
| 응답 가공 | **가능** (헤더 추가, 압축, 로깅) | 불가 (요청 쪽 준비만) |
| OpenAPI 문서 | 반영 안 됨 | **자동 반영** (보안 스킴·파라미터까지) |
| 테스트 | 앱 전체를 띄워야 함 | `dependency_overrides` 로 **한 줄 교체** |
| 캐싱 | 없음 | 같은 요청 내 **같은 의존성은 1회만 실행**(`use_cache`) |
| 에러 처리 | `HTTPException` 을 던져도 **핸들러가 안 잡는다** → 500 | `HTTPException` 정상 동작 (401/403 등) |

### 미들웨어가 맞는 일 — "모든 요청에 똑같이"
- **요청/응답 로깅**, 처리 시간 측정 → `X-Process-Time` 같은 **응답 헤더 주입**
- **CORS**, GZip 압축, HTTPS 리다이렉트, 신뢰 호스트 검사 (→ [[CORS]])
- **요청 ID(trace id) 발급**·분산 추적 컨텍스트 주입
- 전역 레이트 리밋, 접근 차단 — 즉, **경로와 무관하게 일괄 적용되는 관심사**

### Depends가 맞는 일 — "이 엔드포인트에 필요한 것"
- **인증·인가** — 토큰 검증 후 `current_user` 를 **반환**해서 쓰게 함 (→ [[인증과 인가]], [[토큰]])
- **DB 세션** — `yield` 로 열고 닫는 리소스 (→ [[트랜잭션과 ACID]])
- 공통 쿼리 파라미터(페이지네이션), 권한 레벨 체크, 기능 플래그
- 값을 **돌려줘야 하거나**, **일부 엔드포인트에만** 걸거나, **문서·테스트에 드러나야 하면** → 무조건 Depends

### 실무에서 걸리는 함정
- **미들웨어 안에서 `HTTPException` 을 던지면 500이 된다.** `@app.exception_handler` 를 담당하는 `ExceptionMiddleware`가 사용자 미들웨어보다 **안쪽**에 있기 때문. 미들웨어에선 예외를 던지지 말고 **`JSONResponse` 를 직접 return** 할 것.
- **미들웨어에서 요청 바디를 읽으면** 하위 스트림이 소진돼 엔드포인트가 바디를 못 받을 수 있다. 바디 검사가 목적이면 Depends 쪽이 안전.
- `@app.middleware("http")` 는 Starlette의 `BaseHTTPMiddleware` 기반이라 **스트리밍 응답·백그라운드 태스크와 미묘하게 얽힌다.** 성능이 중요하면 순수 ASGI 미들웨어로 작성.
- **`yield` 의존성의 정리 코드는 미들웨어보다 "나중"에 돈다.** 그래서 미들웨어로 잰 처리 시간엔 DB 세션 반납 시간이 안 잡힌다. 정리 시점은 버전에 따라 바뀌어 왔고, **FastAPI 0.121.0**부터 `Depends(get_db, scope="function")` 으로 "엔드포인트 끝나자마자(응답 전송 전) 정리"를 명시할 수 있다(기본값은 `scope="request"`).
- **백그라운드 태스크는 모든 미들웨어가 끝난 뒤** 실행된다.

### 한 문장 판별법
> **"응답을 건드려야 하나?" → 미들웨어.**
> **"엔드포인트에 값을 넘겨야 하나?" → Depends.**
> 둘 다면: 미들웨어로 `request.state` 에 심고 Depends로 꺼내 쓰는 조합이 정석.

## 왜 중요한가
- 신입이 가장 많이 하는 실수가 **"전역에 걸고 싶으니까 미들웨어"** — 그런데 인증은 대부분 **Depends(라우터 단위)** 가 정답이다. 미들웨어로 인증을 짜면 문서에 안 뜨고, 테스트에서 못 갈아끼우고, 401이 500으로 새어 나간다.
- 반대로 **로깅·헤더·CORS를 Depends로** 짜면 응답을 못 건드려서 반쪽짜리가 된다.
- 이 경계를 아는 것 = **횡단 관심사(cross-cutting concern)를 어느 레이어에 둘지** 고르는 감각. [[API 게이트웨이]]·[[리버스 프록시]]로 더 바깥에 밀지, 앱 안에 둘지의 판단으로 이어진다.
