# ADR (Architecture Decision Record)

## 한 줄 정의
**아키텍처적으로 중요한 결정 하나**를 "무슨 상황에서 · 무엇을 택했고 · 그래서 무엇을 감수하는지"까지 **짧은 마크다운 문서로 코드 저장소에 남기는 기록**. 이 기록들이 쌓인 것이 **결정 로그(decision log, ADL)**.

## 자세히

### 왜 생겼나 — 코드는 "왜"를 말해주지 않는다
2011년 11월 **Michael Nygard**의 글 *"Documenting Architecture Decisions"* 이 대중화시켰다. 문제의식은 단순하다.

- 코드는 **무엇을(what) · 어떻게(how)** 는 보여주지만 **왜(why)** 는 지운다.
- 6개월 뒤 합류한 사람은 "이거 왜 이렇게 돼 있지?" → 아무도 모름 → **못 건드리거나(공포), 이유 없이 갈아엎거나(재발)** 둘 중 하나.
- 그렇다고 두꺼운 설계 문서를 쓰면 **아무도 안 읽고 금방 낡는다.**

→ 그래서 **결정 하나당 1~2페이지짜리 파일 하나**를, **코드와 같은 저장소에** 둔다.

### 무엇을 ADR로 남기나
"**아키텍처적으로 중요한(architecturally significant)**" 결정만. 판별 기준:

- **되돌리기 비싼가** — 나중에 바꾸려면 마이그레이션·다운타임이 필요한가
- **구조·경계·인터페이스**를 바꾸는가 (서비스 분리, API 규약, 저장소 선택)
- **비기능 요구**(성능·보안·비용·운영)에 영향을 주는가
- **팀 전체가 따라야 하는가**

반대로 개인 취향, 사소한 라이브러리 교체, 언제든 되돌릴 수 있는 것은 ADR 감이 아니다. (남발하면 아무도 안 읽는다.)

### Nygard 템플릿 — 5개 항목이 전부
가장 널리 쓰이는 원형. 오픈소스 저장소 조사에서도 압도적 1위.

```markdown
# 0007. 세션 저장소로 Redis를 쓴다

## Status (상태)
Accepted — 2026-08-18

## Context (맥락)
서버를 2대 이상으로 늘리면서 인메모리 세션이 깨진다.
스티키 세션은 배포 때마다 로그아웃이 발생하고,
DB 세션은 요청마다 쓰기가 생겨 p99가 40ms 늘었다.

## Decision (결정)
세션 저장소를 Redis(단일 클러스터, TTL 30분)로 둔다.

## Consequences (결과)
+ 서버를 무상태로 만들 수 있어 수평 확장·무중단 배포가 쉬워진다.
- Redis가 SPOF가 된다 → 복제 구성과 장애 시 재로그인 정책이 별도 과제.
- 운영 대상이 하나 늘어난다(모니터링·백업).
```

**핵심은 Context와 Consequences다.** 결정문 한 줄은 코드를 보면 알 수 있지만, **그때의 제약**과 **감수하기로 한 손해**는 문서에만 남는다.

### 상태(Status)와 "고치지 않는다"는 규칙
```
Proposed(제안) → Accepted(승인) → Deprecated(폐기) / Superseded by ADR-0012(대체됨)
                      └ Rejected(부결)  ← 부결도 남긴다. 이게 제일 값질 때가 많다.
```
- ⚠️ **한 번 Accepted된 ADR은 내용을 고치지 않는다.** 생각이 바뀌면 **새 ADR을 쓰고**, 옛것의 상태를 `Superseded by ADR-00NN`으로 바꿔 **링크**한다.
- 즉 ADR은 **덮어쓰는 위키가 아니라 append-only 로그**다 — [[Git]] 커밋과 같은 사고방식. "지금 무엇이 맞나"뿐 아니라 **"어떤 경로로 여기까지 왔나"** 가 자산이다.
- 상태를 갱신하지 않으면 그 순간 **죽은 문서**가 된다. ADR 운영의 8할은 이 갱신.

### 어디에 어떻게 두나 (docs-as-code)
- 경로 관례: **`doc/adr/`** 또는 `docs/adr/` (adr-tools 기본값은 `doc/adr`)
- 파일명: **4자리 일련번호 + 슬러그** — `0001-record-architecture-decisions.md`, `0007-use-redis-for-sessions.md`
  - 첫 번째 ADR은 관례적으로 **"ADR을 쓰기로 한 결정"** 자체다.
  - 번호는 **재사용하지 않는다**(부결·폐기된 번호도 비워두지 않고 그대로 둔다).
- **코드와 같은 저장소·같은 PR**에 넣는다 → 결정이 [[형상관리|버전 관리]]되고, **코드 리뷰에서 결정 자체를 리뷰**할 수 있다.

### 템플릿 갈래
| 템플릿 | 특징 | 언제 |
|---|---|---|
| **Nygard** | Status·Context·Decision·Consequences 4항목 | 기본값. 가장 가볍고 가장 많이 쓰임 |
| **MADR** (4.0.0) | + **Considered Options**(후보별 장단점)·Decision Drivers·Confirmation(검증 방법) | 대안 비교가 논점인 결정 |
| **Y-Statement** | 한 문장: "*`<맥락>`에서 `<관심사>`에 직면해, `<품질>`을 얻기 위해 `<옵션>`을 택했고 `<단점>`을 감수한다*" | 초경량. 회의록 한 줄로 남길 때 |
| **arc42 / ISO 42010** | 아키텍처 문서 전체 체계의 일부로 편입 | 규제·대형 조직 문서화 |

### 도구
- **adr-tools** (Nat Pryce) — bash CLI. `adr init`, `adr new "…"`, `adr new -s 7 "…"`(7번을 대체) → 번호·파일명·상태 링크를 자동 처리. 진입 장벽이 가장 낮다.
- **log4brains** — 저장소의 마크다운 ADR을 **검색 가능한 정적 사이트**로 발행. 기본 템플릿은 MADR.
- **adr-log** — ADR 목록(인덱스) 자동 생성.
- 도구 없이 **파일 복사 + 번호 수동 부여**로 시작해도 아무 문제 없다. 형식보다 **쓰는 습관**이 본체.

### 자주 하는 실수
- **사후에 몰아 쓰기** — 결정한 순간에 써야 맥락이 살아있다. 3개월 뒤 회고로 쓰면 "결과 정당화"가 된다.
- **부결 대안을 안 적기** — "왜 Kafka 대신 SQS인가"에서 값진 건 **탈락한 쪽의 이유**다. 안 적으면 6개월마다 같은 논쟁이 재발한다.
- **길게 쓰기** — 2페이지를 넘어가면 설계 문서지 ADR이 아니다.
- **상태 미갱신** — 이미 안 쓰는 결정이 Accepted로 남아 있으면 로그 전체의 신뢰가 무너진다.
- **모든 걸 ADR로** — 신호 대 잡음비가 무너지면 아무도 안 읽는다.

### 2026년 맥락
저장소를 통째로 읽는 **AI 코딩 에이전트**가 일상이 되면서, ADR은 사람뿐 아니라 **도구에게 "왜"를 전달하는 통로**로 재조명되고 있다. `CLAUDE.md` 같은 규칙 파일이 "무엇을 지켜라"라면, ADR은 **"그 규칙이 왜 생겼는지"** 를 담는다 — 제약이 사라졌는지 판단하려면 결국 당시 맥락이 필요하다.

## 왜 중요한가
- **결정의 수명 > 사람의 기억(과 재직 기간).** 팀은 바뀌어도 결정의 결과는 시스템에 남는다.
- **되돌릴 때 필요한 건 결정이 아니라 당시의 제약**이다. "그때 Redis를 고른 이유가 X였는데, X가 이제 없다" → 안전하게 뒤집을 수 있다. 맥락이 없으면 뒤집는 것 자체가 도박이 된다.
- **온보딩 비용과 반복 논쟁을 줄인다** — 같은 질문("이거 왜 이렇게 했어요?")에 매번 사람이 답하지 않아도 된다.
- **결정을 리뷰 가능하게** 만든다 — PR에 ADR이 들어오면 코드가 아니라 **판단**을 두고 토론할 수 있다.
