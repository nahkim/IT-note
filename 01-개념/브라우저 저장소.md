# 브라우저 저장소 (Web Storage / IndexedDB / Cookie)

## 한 줄 정의
브라우저가 **사용자 기기에 데이터를 남기는 여러 창고** — 쿠키·localStorage·sessionStorage·IndexedDB·Cache Storage. 용량·수명·서버 전송 여부·보안 특성이 각각 다르다.

## 자세히

### 한눈에 비교
| | 쿠키 (Cookie) | localStorage | sessionStorage | IndexedDB | Cache Storage |
|---|---|---|---|---|---|
| 용량 | 약 4KB/개 | 약 5~10MB | 약 5~10MB | 수백 MB~GB (할당량 기반) | 할당량 기반 |
| 수명 | 만료일까지 | **영구**(지우기 전까지) | **탭이 닫히면 소멸** | 영구 | 영구 |
| 서버 전송 | ✅ **매 요청에 자동 첨부** | ❌ | ❌ | ❌ | ❌ |
| API | 문자열 파싱 | 동기, 키-값(문자열) | 동기, 키-값 | 비동기, 인덱스·트랜잭션 | 비동기, Request/Response |
| 주 용도 | 세션·인증·추적 | 설정·테마·작은 상태 | 탭 단위 임시 상태 | 오프라인 데이터·대용량·바이너리 | 정적 자산·응답 캐시 |

- 모두 **출처(origin)별로 격리**된다 ([[동일 출처 정책]]).
- localStorage/sessionStorage는 **동기 API** — 큰 데이터를 다루면 **메인 스레드를 막는다**([[이벤트 루프]]). 그래서 규모가 커지면 IndexedDB로 간다.
- **Cache Storage**는 [[서비스 워커]]가 요청/응답 쌍을 저장하는 전용 창고(HTTP 캐시와는 별개).

### 보안 — 무엇을 넣으면 안 되나
- **localStorage에 토큰(JWT)을 넣는 것은 [[XSS]]에 취약하다.** 스크립트가 언제든 읽어갈 수 있다. `HttpOnly` 같은 보호 수단이 **없다**.
- 반대로 쿠키는 **`HttpOnly`(JS 접근 차단) · `Secure`(HTTPS만) · `SameSite`(교차 사이트 전송 제한)** 를 걸 수 있다 → 세션·인증에는 여전히 쿠키가 기본기.
- 어느 저장소든 **사용자가 직접 열어보고 고칠 수 있다.** 권한·가격·검증 결과 같은 **신뢰가 필요한 값은 절대 클라이언트에 두지 않는다.**
- 개인정보를 남길 때는 **저장 최소화**와 삭제 경로를 함께 설계 ([[웹사이트 보안]]).

### 알아둘 함정
- **용량 한도는 표준이 아니다** — 브라우저·모드마다 다르고, 저장 공간이 부족하면 **오래된 출처부터 정리(eviction)** 될 수 있다. "지워지지 않는다"고 가정하면 안 된다.
- **시크릿/프라이빗 모드**에선 세션 종료와 함께 대부분 날아간다.
- Safari의 **ITP**는 스크립트로 심은 저장소·쿠키의 수명을 공격적으로 제한한다(7일 등) → "로그인이 자꾸 풀린다"의 원인.
- **파티셔닝** — 서드파티 컨텍스트의 저장소는 **최상위 사이트별로 분리**되는 추세(Firefox Total Cookie Protection 등). 임베드된 위젯이 사이트마다 다른 저장소를 보게 된다.
- 개발자 도구의 **Application 패널**에서 전부 확인·삭제할 수 있다 ([[개발자 도구]]).

## 왜 중요한가
- **"어디에 저장할 것인가"는 곧 보안 결정**이다 — 토큰을 어디 두느냐로 XSS·CSRF 노출 면적이 달라진다 ([[쿠키 세션 JWT]]).
- 오프라인 지원·성능 최적화(PWA)의 재료. 반대로 잘못 쓰면 **오래된 데이터가 남아 생기는 버그**의 온상이 된다.
