# 딥링크 (Deep Link)

## 한 줄 정의
**링크 하나로 앱의 특정 화면까지 곧장 열어주는 것.** 앱을 "실행"하는 게 아니라 **앱 안의 주소로 이동**시키는 것이 요점이다 — 웹의 `example.com/products/42`가 목록이 아니라 그 상품 페이지를 여는 것과 똑같은 일을, 설치된 앱에 대해 하는 것.

> 기술적으로는 **"이 URL을 누가 처리할 것인가"를 OS가 결정하는 문제**다. 그래서 모든 논의가 결국 **"그 URL의 주인이 정말 이 앱이 맞나"**(소유권 검증)로 수렴한다.

## 자세히

### 두 가지 방식 — 이것만 구분하면 절반은 끝난다

```
① 커스텀 스킴      myapp://product/42      ← 앱만 아는 주소. 웹 브라우저는 못 연다
② 검증된 웹 링크   https://example.com/product/42
                                            ← 평범한 https URL인데, OS가 "이 도메인의 주인이
                                               이 앱"임을 확인해 두었기 때문에 앱이 열린다
```

②를 iOS는 **Universal Links**, Android는 **App Links**라고 부른다. 이름만 다르고 발상은 같다: **도메인에 파일 하나를 올려 앱과 도메인을 서로 묶는다.**

> ⚠️ **"딥링크란 커스텀 URL 스킴을 OS에 등록하는 것"이라는 설명은 절반만 맞다.** 그건 **①에 해당하는 옛 방식**이고, 지금 외부에 뿌리는 링크의 기본은 **②(평범한 `https` URL + 도메인 소유권 검증)** 다. ②에도 "OS에 등록"이 있긴 하지만, 등록하는 대상이 **스킴이 아니라 도메인**이고 **OS가 그 도메인에 파일을 확인하러 간다**는 점이 결정적으로 다르다. 이 차이가 곧 하이재킹 가능 여부와 미설치 폴백 여부를 가른다.

### ① 커스텀 스킴 (`myapp://`)
- **등록** — iOS는 `Info.plist`의 `CFBundleURLTypes`, Android는 매니페스트의 `<intent-filter>`에 `<data android:scheme="myapp">`.
- **가장 쉽고, 가장 약하다.**
  - ⚠️ **소유권 검증이 전혀 없다.** `myapp://`를 다른 앱이 똑같이 등록하는 걸 막는 장치가 OS에 없다 → **스킴 하이재킹**. 악성 앱이 같은 스킴을 선점하면 링크(그리고 거기 실린 값)가 그쪽으로 간다.
  - ⚠️ **앱이 없으면 아무 일도 안 일어난다.** 브라우저는 "주소가 유효하지 않습니다" 류의 에러를 낼 뿐, 스토어로 유도해 주지 않는다.
- 그래서 지금은 **앱 내부/기기 내부 호출용**(설치가 이미 확인된 상황, 데스크톱 앱, 개발용)으로 밀려났다.
- Android 한정 우회책으로 `intent://...#Intent;S.browser_fallback_url=...;end` 문법이 있다 — 앱이 없으면 지정한 웹 URL로 떨어진다(Chrome 계열 전용).

### ② Universal Links (iOS)
| 항목 | 내용 |
|---|---|
| 앱 쪽 | **Associated Domains** 권한에 `applinks:example.com` 추가 |
| 서버 쪽 | `https://example.com/.well-known/apple-app-site-association` |
| 파일 | **확장자 없음**, `Content-Type: application/json`, **리다이렉트 금지**, 내용에 `appID`(= `TEAMID.com.example.app`)와 경로 패턴 |
| 반영 시점 | iOS가 **설치·업데이트 때** 받아가고 **Apple CDN이 캐시** → 변경이 전체에 퍼지는 데 **24~48시간** |

**앱이 없으면 그냥 웹페이지가 열린다** — 이 무결점 폴백이 커스텀 스킴 대비 결정적 장점이다.

⚠️ **의도적으로 안 열리는 경우들** (버그가 아니라 설계다)
- **Safari 주소창에 직접 입력**한 URL → 앱으로 안 간다.
- **JS·meta refresh 자동 리다이렉트** → 안 간다. **사용자의 클릭(제스처)** 이 있어야 한다. (서버 301/302는 동작하지만, **최종 URL이 AASA에 등록된 경로 패턴과 맞아야** 한다.)
- **같은 도메인 안에서의 이동** → Safari에 머문다.

### ② App Links (Android)
| 항목 | 내용 |
|---|---|
| 앱 쪽 | `<intent-filter android:autoVerify="true">` + `android:scheme="https"` |
| 서버 쪽 | `https://example.com/.well-known/assetlinks.json` |
| 파일 | `package_name` + **서명 인증서의 SHA-256 지문** |
| 검증 | 설치 시 시스템이 자동 대조. 여러 host 중 **검증된 host만** 앱이 기본 처리 |

⚠️ **Android 12(API 31)부터 실패가 조용해졌다.** 예전에는 검증이 안 되면 "브라우저로 열까 앱으로 열까" 선택 창이 떠서 설정 오류가 눈에 보였는데, **지금은 선택 창 없이 그냥 브라우저로 간다.** 사용자에게도 개발자에게도 아무 신호가 없다.
- 확인은 ADB로: `adb shell pm get-app-links <package>` (상태 확인) / `pm verify-app-links` (재검증).
- ⚠️ **가장 흔한 실패 원인은 지문**이다. **Play 앱 서명**을 쓰면 실제 배포본은 Google이 재서명하므로, `assetlinks.json`에는 **업로드 키가 아니라 Play Console의 앱 서명 키 지문**을 넣어야 한다.

### 세 방식 비교
| | 커스텀 스킴 | Universal Links (iOS) | App Links (Android) |
|---|---|---|---|
| 형태 | `myapp://…` | `https://…` | `https://…` |
| 도메인 소유권 검증 | ❌ 없음 | ✅ AASA | ✅ assetlinks.json |
| 앱 미설치 시 | 에러/무반응 | **웹페이지로 폴백** | **웹페이지로 폴백** |
| 하이재킹 위험 | **높음** | 낮음 | 낮음 |
| 설정 난이도 | 낮음 | 서버 파일 + 권한 | 서버 파일 + 서명 지문 |
| 지금의 용도 | 앱 내부·데스크톱·개발 | **외부에 뿌리는 링크의 기본** | **외부에 뿌리는 링크의 기본** |

### 지연 딥링크 (Deferred Deep Link) — 진짜 어려운 쪽
**앱이 없는 사람**이 링크를 눌렀을 때: 스토어로 → 설치 → **첫 실행 시 원래 누른 그 상품 화면**으로. 마케팅·초대·추천 링크가 원하는 동작이 바로 이것이다.

문제는 **OS가 "설치 전에 무엇을 눌렀는지"를 앱에 넘겨주지 않는다**는 점. 그래서 서드파티 SDK가 우회로 복원한다 — Android는 **Play Install Referrer**(공식 경로), iOS는 클립보드·확률적 매칭 등(프라이버시 정책상 제약이 크다).

⚠️ **Firebase Dynamic Links(FDL)는 2025-08-25에 완전히 종료됐다.** 신규 생성은 물론 **기존 링크도 404**다. 아직 FDL 링크가 남아 있다면 이미 죽은 링크다. Google이 FAQ에서 제시한 대체제는 **Adjust · Airbridge · AppsFlyer · Bitly · Branch · Kochava · Singular** 7곳. 단순 공유·열기 목적이라면 굳이 SDK를 붙이지 말고 **Universal/App Links + 자체 랜딩 페이지**로 충분한 경우가 많다.

### 데스크톱 딥링크
데스크톱은 사정이 달라서 **커스텀 스킴(프로토콜 핸들러)이 여전히 주력**이다. `slack://`, `vscode://`, `zoommtg://` 같은 것들.
- **macOS** — `Info.plist`의 `CFBundleURLTypes`에 등록. 실행 중인 앱에 **`open-url` 이벤트**로 전달된다.
- **Windows / Linux** — 별도 이벤트가 없다. **새 프로세스가 뜨면서 명령줄 인자로** URL이 들어온다 → **단일 인스턴스(single instance) 처리**로 기존 창에 넘겨주는 코드를 직접 짜야 한다. 이 플랫폼 차이가 데스크톱 딥링크 버그의 대부분이다.
- 프레임워크: Electron은 `app.setAsDefaultProtocolClient()`, [[Tauri]]는 `deep-link` 플러그인(+ single-instance 플러그인 연동)이 이 차이를 감싸준다.

### 보안 — 딥링크는 "외부 입력"이다
- **들어온 파라미터를 믿지 말 것.** 딥링크는 누구나 만들어 보낼 수 있는 입력이다. 검증 없이 화면을 전환하거나 값을 처리하면 인증 우회·계정 탈취로 이어진다(안드로이드 딥링크 취약점의 단골 패턴).
- **OAuth 리다이렉트가 대표적인 위험 지점.** 커스텀 스킴 리다이렉트는 다른 앱이 가로챌 수 있어서, **RFC 8252(OAuth 2.0 for Native Apps)** 는 ⓐ 검증된 https(= Universal/App Links)를 우선 권장하고, ⓑ private-use 스킴을 쓰더라도 **[[PKCE]]를 필수**로 요구한다. 임베디드 웹뷰는 금지. → [[OAuth]]
- **링크 자체에 비밀을 싣지 말 것.** URL은 로그·리퍼러·클립보드·공유 이력에 그대로 남는다.

### 🔍 안 될 때 보는 순서
1. **어느 방식인지부터 확정** — 커스텀 스킴인가, 검증 링크인가. 증상이 완전히 다르다.
2. `curl -I` 로 **AASA / assetlinks.json이 200 + 올바른 Content-Type + 리다이렉트 없이** 내려오는지.
3. **Android** — `adb shell pm get-app-links <pkg>` 로 검증 상태. 대개 **서명 지문**(Play 앱 서명 키인지).
4. **iOS** — 캐시를 의심(**24~48시간**). 앱 삭제 후 재설치로 강제 갱신.
5. **어떻게 눌렀는지** — 주소창 직접 입력·JS 자동 리다이렉트·같은 도메인 내 이동은 **원래 안 열린다**.
6. 그래도 안 되면 **미설치 폴백 시나리오**를 다시 확인 — 사용자는 "앱이 안 열린다"고 하지만 실제로는 앱이 안 깔린 경우가 많다.

## 왜 중요한가
- **웹과 앱을 잇는 유일한 실용적 접착제**다. 결제 복귀, 로그인 콜백([[OAuth]]), 알림 탭, 초대·추천, QR 스캔([[와이파이 QR 코드]]처럼 QR에 딥링크를 싣는 경우가 많다) — 사용자 여정의 이음매마다 딥링크가 있다.
- **"URL의 주인이 누구인가"를 증명하는 문제**라, [[HTTP와 HTTPS]]·도메인 소유권 검증([[DNS]]·`.well-known`)과 곧장 연결된다. 웹 표준의 신뢰 모델이 앱까지 확장된 사례다.
- **조용히 실패하는 대표적인 기능**이다. Android 12의 폴백 변경, iOS의 CDN 캐시, Play 재서명 지문 — 셋 다 "코드는 맞는데 안 되는" 상황을 만든다. 실패 지점을 미리 알아야 시간을 안 버린다.
- 인증 흐름과 붙어 있어 **보안 경계**이기도 하다. [[PKCE]]가 왜 필수가 됐는지의 실제 배경이 커스텀 스킴 가로채기다.
