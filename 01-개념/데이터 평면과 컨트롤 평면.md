# 🧩 데이터 평면과 컨트롤 평면 (요청이 가는 길 vs 우리가 가는 길)

> 🔒 **주소는 자리표시자다.** `CF_DOMAIN`(CDN) · `ALB_IP`(로드밸런서) · `WEB_IP`(앱 서버) · `BASTION_IP`(베스천)

## 한 줄 요약
같은 시스템인데 길이 **두 갈래**다. 사용자 요청이 흐르는 **데이터 평면(data plane)** 과, 우리가 배포·접속·점검하러 가는 **컨트롤 평면(control plane)** 은 **겹치지 않는 별개의 경로**다. 이걸 한 덩어리로 보면 "SSH로 들어간 서버에 앱이 안 보인다" 같은 곳에서 몇 시간을 태운다 — **내가 들어간 문이 요청이 지나가는 문이 아니기 때문**이다.

## 핵심 내용

### 1. 두 길은 출발점도 끝점도 다르다

```
  데이터 평면 (사용자 요청)                컨트롤 평면 (운영자)
  ─────────────────────────                ──────────────────────
  [사용자 브라우저]                         [내 노트북 / CI 서버]
        │ https                                   │ ssh :22
        ▼                                         ▼
  [CDN  CF_DOMAIN]                          [베스천 BASTION_IP]
        │                                         │ ssh (배포 스크립트)
        ▼                                         ▼
  [LB   ALB_IP]  ──────────┐         ┌──────────  (같은 서버에 닿지만
        │                  ▼         ▼              들어가는 문이 다르다)
        └──────────▶ [앱 서버 WEB_IP]
                      :3001 (앱 포트)  ← 데이터 평면이 두드리는 문
                      :22   (sshd)     ← 컨트롤 평면이 두드리는 문
```

> 🔑 **두 평면이 만나는 지점은 "서버"뿐이지, "경로"가 아니다.** 베스천은 컨트롤 평면에만 있으므로 **요청은 베스천을 한 번도 지나지 않는다.** 베스천에 들어가 앱 디렉터리를 찾아도 없는 게 정상이다.

### 2. 왜 헷갈리나 — "서버 목록"이 경로를 말해주지 않는다

| 흔한 오해 | 실제 |
|---|---|
| "인프라에 서버가 3대니까 요청이 3대를 거치겠지" | 베스천은 경로 밖. 요청은 2대만 거친다 |
| "SSH로 들어갈 수 있으면 요청도 그리로 오겠지" | 접속 가능 ≠ 경로 위. 반대도 성립 |
| "nginx가 떠 있으니 요청은 nginx를 거치겠지" | 설정이 비어 있으면 **떠 있어도 경로 밖** |
| "공인 IP가 붙었으니 외부에서 앱에 닿겠지" | 보안그룹이 LB만 허용하면 못 닿는다 |

> ⚠️ **"떠 있다 ≠ 경로 위에 있다."** 구성도나 프로세스 목록이 아니라 **실제 연결**로 확인한다.
> ```bash
> ss -tnp state established '( sport = :3001 )'   # 앱 포트에 실제로 붙은 상대 = 바로 앞 장비
> ```
> → [[X-Forwarded-For 와 신뢰할 프록시 수]] (앞단 장비 수를 재는 법)

### 3. 보안 요구가 서로 다르다 — 그래서 나눈다

애초에 두 평면을 나누는 **이유**가 노출 범위를 따로 조이기 위해서다.

| | 데이터 평면 | 컨트롤 평면 |
|---|---|---|
| 들어오는 쪽 | **전 세계** (익명 사용자) | **소수의 운영자·CI** |
| 열어야 할 포트 | 앱 포트 — 단, **LB에게만** | `:22` — 단, **베스천에만** |
| 인증 | 앱의 로그인 | SSH 키 / IAM |
| 끊기면 | 서비스 장애 | 배포 불가 (서비스는 계속 돈다) |
| 기록 | 액세스 로그 | 접속·배포 감사 로그 |

- **데이터 평면의 포트는 LB에게만 연다.** 앱 서버에 공인 IP가 붙어 있어도 앱 포트가 차단돼 있으면 "샛길"이 없다 — 이게 IP 위조 방어의 전제이기도 하다.
- **컨트롤 평면은 문을 하나로 모은다.** 사설 서버마다 `:22`를 열지 않고 베스천 한 대만 노출한다. → [[베스천 서버]]
- 이런 분리를 전통적으로 **대역 외 관리(out-of-band management)** 라고 부른다. 서비스 트래픽과 **다른 망/다른 경로**로 관리한다는 뜻이다.

### 4. 🚨 어느 평면에도 없는 것 = 순수 공격면

실제로 자주 나오는 패턴 — **설치만 하고 안 쓰는 서비스**.

```
 앱 서버에 nginx 가 :80 으로 떠 있다
   ├─ 데이터 평면? ✗  설정이 기본값이라 proxy_pass 가 없다. LB는 앱 포트로 직행
   └─ 컨트롤 평면? ✗  배포도 점검도 쓰지 않는다
   → 어느 쪽도 아니면서 공인 IP로 기본 환영 페이지만 띄우고 있다
```

이런 건 **기능이 0이고 위험만 있다.** 버전이 노출되고, 패치 대상이 하나 늘고, 설정 실수 한 번이면 경로가 생긴다.

> 🔑 **새 서비스를 보면 "어느 평면에 속하나"를 먼저 묻는다.** 둘 다 아니면 **끄거나 지운다.** → [[웹사이트 보안]]

### 5. 설정값이 "길"에 묶여 있다

경로가 바뀌면 같이 바뀌어야 하는 값들이 있다. 구조 변경 PR에서 빠뜨리기 쉬운 것들.

| 값 | 무엇에 묶여 있나 |
|---|---|
| 신뢰할 프록시 수 (`trust proxy`) | **데이터 평면의 장비 수** — CDN/WAF 추가·제거 시 같이 변경 |
| CORS·쿠키 도메인 | 데이터 평면의 **입구 도메인** |
| 보안그룹 인바운드 | 두 평면 각각의 허용 출발지 |
| 배포 스크립트의 대상 목록 | **컨트롤 평면**의 끝점(서버가 늘면 추가) |
| 헬스체크 경로 | LB가 보는 것이므로 데이터 평면 |

> ⚠️ 서버를 한 대 늘렸는데 **배포 스크립트에만 추가하고 LB 타겟에는 안 넣으면**, 컨트롤 평면에는 있고 데이터 평면에는 없는 유령 서버가 된다(배포는 되는데 트래픽은 안 옴). 반대 경우는 **구버전 코드로 서비스**하는 더 나쁜 상황이 된다.

## 기억할 문장 / 핵심 포인트
> **"내가 들어간 문과 요청이 들어오는 문은 다른 문이다."** 베스천에 앱이 없는 건 고장이 아니라 설계다.
> **떠 있다 ≠ 경로 위에 있다.** 프로세스 목록이 아니라 연결(`ss`)로 확인한다.
> **어느 평면에도 없는 서비스는 기능 0, 위험 1.** 끄는 게 정답이다.
> **두 평면은 노출 요구가 정반대다** — 하나는 전 세계에, 하나는 운영자에게만. 그래서 애초에 나눈다.
> **구조가 바뀌면 "길에 묶인 설정"이 같이 바뀐다** — 프록시 홉 수·보안그룹·배포 대상 목록.
