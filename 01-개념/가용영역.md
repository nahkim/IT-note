# 🧩 가용영역 (AZ) — 서버를 두 대로 나눈 게 이중화가 아니다

> 🔒 영역 이름은 예시다. `ap-northeast-2a/2b/2c` 는 서울 리전의 AZ.

## 한 줄 요약
**리전(Region)** 은 도시, **가용영역(AZ)** 은 그 안의 **물리적으로 분리된 데이터센터**다. 서버를 두 대로 늘리는 이유는 "한 대가 죽어도 버티려고"인데, **두 대가 같은 AZ에 있으면 전원·네트워크·화재를 공유**하므로 정전 한 번에 둘 다 멈춘다. **대수를 늘리는 것과 영역을 나누는 것은 다른 일이다.**

## 핵심 내용

### 1. 리전 · AZ · 서브넷

```
 리전 ap-northeast-2 (서울)
 ├─ AZ  ap-northeast-2a   ← 독립 건물·전원·냉각·네트워크
 │   └─ 서브넷 172.31.16.0/20
 ├─ AZ  ap-northeast-2b
 │   └─ 서브넷 172.31.32.0/20
 └─ AZ  ap-northeast-2c
     └─ 서브넷 172.31.48.0/20
```

| 단위 | 분리 수준 | 사이 지연 |
|---|---|---|
| **리전** | 완전히 다른 지역(수백~수천 km) | 수십~수백 ms |
| **AZ** | 같은 지역의 **다른 건물**. 전원·냉각·네트워크 독립 | **1~2ms 수준** (전용 회선) |
| 서브넷 | AZ 안의 IP 대역 — **서브넷 하나는 AZ 하나에 속한다** | — |

> 🔑 **AZ는 "거의 공짜로 쓸 수 있는 이중화"다.** 지연이 거의 없어서 같은 서비스를 걸쳐 둬도 성능 손해가 없는데, 장애 도메인은 완전히 분리된다. **안 쓸 이유가 없는데 자주 빠뜨린다.**

### 2. 인스턴스가 어느 AZ에 있는지는 **서브넷이 결정한다**

EC2를 만들 때 AZ를 직접 고르는 게 아니라 **서브넷을 고른다.** 그래서 "대충 기본 서브넷"으로 두 대를 만들면 **둘 다 같은 AZ**가 되기 쉽다.

```bash
# 내 인스턴스들이 어느 AZ에 흩어져 있나 — 가장 먼저 볼 것
aws ec2 describe-instances \
  --query 'Reservations[].Instances[].{Name:Tags[?Key==`Name`]|[0].Value,
           AZ:Placement.AvailabilityZone, Type:InstanceType, State:State.Name}' \
  --output table

# 서버 안에서 자기 AZ 확인 (IMDSv2)
TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token \
        -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
     http://169.254.169.254/latest/meta-data/placement/availability-zone
```

> ⚠️ **AZ 이름(`2a`, `2c`)은 계정마다 다른 물리 AZ를 가리킨다.** 내 계정의 `2a`와 남의 계정의 `2a`는 다른 건물일 수 있다(AWS가 계정별로 섞어 배정). 계정 간 비교가 필요하면 **AZ ID**(`apne2-az1` 같은 값)를 쓴다.

### 3. 🚨 흔한 반쪽 구성 — "LB는 2개 AZ, 서버는 1개 AZ"

실제로 자주 발견되는 모양이다.

```
        [ALB]  ← 서브넷 2개(2a, 2c)에 걸쳐 생성됨. 겉보기엔 멀티 AZ ✅
         │ │
         ▼ ▼
      web1  web2   ← 둘 다 ap-northeast-2c 😱
      ──────────
      2c 가 죽으면 → 둘 다 동시에 사라진다. ALB만 살아남아 502를 돌려준다
```

- **ALB는 최소 2개 AZ의 서브넷을 요구**하므로, LB 자체는 자동으로 멀티 AZ가 된다. **그래서 "멀티 AZ 같아 보이는" 착시가 생긴다.**
- 하지만 **실제 가용성은 타겟(뒷단 서버)이 어디에 있느냐로 결정된다.** 앞단만 나뉘고 뒷단이 한 영역이면 **이중화의 절반만 동작**한다 — 프로세스 장애·배포 실패에는 강하지만 **영역 장애에는 무방비**다.

> 🔑 **"서버 N대"가 아니라 "장애 도메인 N개"로 세야 한다.** 같은 AZ의 두 대는 **장애 도메인 1개**다. 인스턴스 장애엔 2중, AZ 장애엔 1중.

**교차 영역 로드밸런싱(cross-zone)과 헷갈리지 말 것**
- ALB는 **로드밸런서 수준에서 cross-zone이 항상 켜져 있고 끌 수 없다** — AZ와 무관하게 모든 타겟에 고르게 분배한다는 뜻이다. (타겟 그룹 수준에서는 끌 수 있고, 기본값은 `use_load_balancer_configuration`)
- 이건 **"트래픽을 어떻게 나누나"** 의 이야기지 **"타겟이 어디 있나"** 의 이야기가 아니다. cross-zone이 켜져 있어도 **타겟이 전부 한 AZ면 그 AZ가 죽을 때 같이 죽는다.**

### 4. 어디까지 나눠야 하나

| 계층 | 멀티 AZ 방법 | 비고 |
|---|---|---|
| 로드밸런서 | 서브넷을 2개 이상 AZ로 지정 | ALB는 **필수**. 자동으로 충족됨 |
| 앱 서버 | 인스턴스를 **다른 AZ 서브넷**에 배치 | Auto Scaling Group을 쓰면 알아서 분산 |
| DB (RDS) | **Multi-AZ 배포** 옵션 | 대기 인스턴스를 다른 AZ에 두고 자동 장애조치 |
| 캐시 (Redis) | 복제 그룹 + Multi-AZ | |
| 파일 (S3) | 기본적으로 리전 내 다중 AZ 복제 | 따로 할 일 없음 |
| **베스천** | 보통 1대 | 죽어도 **서비스는 안 멈춘다**(컨트롤 평면) → [[데이터 평면과 컨트롤 평면]] |

> 💡 **전부 나눌 필요는 없다.** "죽으면 서비스가 멈추나?"로 가른다. 베스천·젠킨스는 멈춰도 배포만 막히므로 1대로 두고, 대신 **빨리 복구할 수 있게** 해두는 쪽이 합리적이다.

### 5. 비용과 트레이드오프

- **AZ 간 데이터 전송은 유료다.** 앱↔DB가 다른 AZ면 모든 쿼리에 요금이 붙는다(소규모면 미미하지만 트래픽이 크면 체감된다).
- 그래서 "성능·비용을 위해 같은 AZ에 몰기"가 **의도적인 선택일 수도** 있다. 문제는 **의도한 적 없이 그렇게 된** 경우다.
- 실무 균형점: **앱 서버는 AZ 분산, DB는 Multi-AZ(동기 복제)**. 앱↔DB 지연은 1~2ms라 대부분 문제되지 않는다.

> ⚠️ 같은 AZ에 몰아둔 게 **의도라면 문서에 남긴다.** 안 그러면 다음 사람이 "버그"로 보고 고치거나, 아무도 모른 채 장애를 맞는다.

## 기억할 문장 / 핵심 포인트
> **대수를 늘리는 것 ≠ 영역을 나누는 것.** 같은 AZ의 두 대는 장애 도메인 하나다.
> **ALB가 멀티 AZ인 건 착시를 만든다** — 가용성은 **타겟이 어디 있느냐**로 결정된다.
> **cross-zone 로드밸런싱은 "분배 방식"이지 "배치"가 아니다.** 켜져 있어도 타겟이 한 AZ면 소용없다.
> **AZ는 거의 공짜 이중화다** — 지연 1~2ms에 장애 도메인이 완전히 분리된다.
> **AZ 이름은 계정마다 다른 물리 영역을 가리킨다.** 계정 간 비교에는 AZ ID를 쓴다.
> **전부 나눌 필요는 없다** — "죽으면 서비스가 멈추나"로 가른다.

## 내 생각 / 적용할 점
- 인프라 점검 첫 질문: **"서버 몇 대?"가 아니라 "AZ 몇 개?"**. `describe-instances` 로 AZ 컬럼부터 보기
- 지금 두 대가 같은 AZ라면 — 한 대를 다른 AZ로 옮기는 건 **새로 만들어 LB 타겟에 넣고 기존 것을 빼는** 수순. 무중단으로 가능
- Auto Scaling Group을 쓰면 AZ 분산이 **기본 동작**이 된다. 수동으로 EC2를 만드는 한 계속 실수한다
- 같은 AZ가 의도였다면 **그 이유를 문서에 남기기** (비용? 지연?)
