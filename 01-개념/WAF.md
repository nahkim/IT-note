# WAF (웹 방화벽, Web Application Firewall)

## 한 줄 정의
**웹 애플리케이션 앞에 서서 오가는 HTTP(S) 요청·응답의 "내용"을 읽고 공격 패턴을 걸러내는 L7 방화벽.** 일반 방화벽이 *누가 어느 포트로 들어오는가*를 본다면, WAF는 **요청 본문에 `' OR 1=1--`이 적혀 있는가**를 본다. 앱 코드를 고치지 않고도 공격을 막아준다는 게 매력이자, 동시에 **앱을 고치지 않았다는 사실 자체가 한계**다.

## 자세히

### 어디에 서 있나
```
[사용자]
   │  HTTPS
   ▼
[CDN / 엣지]  ── 클라우드 WAF가 보통 여기 (Cloudflare·AWS WAF·Akamai)
   ▼
[로드 밸런서 / 리버스 프록시]  ── 어플라이언스·nginx 모듈형 WAF가 여기
   ▼
[애플리케이션]  ── RASP는 여기 "안"에 들어간다
   ▼
[DB]
```
핵심 전제: **WAF는 평문 HTTP를 봐야 한다** → 어딘가에서 **TLS를 종료**해야 하고, 그래서 WAF는 거의 항상 [[리버스 프록시]]·[[CDN]]·[[로드 밸런서]] 자리에 함께 놓인다. → [[HTTP와 HTTPS]]

### 일반 방화벽·IPS와 뭐가 다른가
| | 보는 계층 | 판단 근거 | 막는 것 |
|---|---|---|---|
| **네트워크 방화벽** | L3/L4 | IP·포트·프로토콜 | "이 IP는 3306 포트에 못 붙는다" |
| **IPS/IDS** | L3~L7(범용) | 네트워크 트래픽 시그니처 | 웜·스캐닝·알려진 익스플로잇 |
| **WAF** | **L7(HTTP 전용)** | **URL·헤더·쿠키·파라미터·본문** | [[XSS]]·SQL 인젝션·경로 탐색·[[CSRF]] 보조·파일 업로드 공격 |
| **RASP** | 앱 런타임 내부 | 실제 함수 호출·쿼리 실행 맥락 | "이 쿼리가 정말 인젝션으로 실행되는가" |

즉 WAF는 **80/443 포트는 열어 둔 채, 그 안을 들여다보는 장치**다. 방화벽이 "문을 잠그는 것"이라면 WAF는 "문으로 들어오는 사람의 가방을 여는 것".

### 두 가지 탐지 철학
| | **네거티브 모델**(블랙리스트) | **포지티브 모델**(화이트리스트) |
|---|---|---|
| 기본 동작 | **기본 허용**, 나쁜 패턴만 차단 | **기본 차단**, 정의된 정상만 허용 |
| 근거 | 공격 시그니처·룰셋 | 스키마·정상 트래픽 학습 결과 |
| 장점 | 바로 붙여 쓸 수 있다 | **제로데이에도 강함** |
| 단점 | **모르는 공격은 못 막는다**, 변형으로 우회 | 정상 요청이 바뀔 때마다 갱신, 초기 구축 비용 큼 |

현실의 제품은 대부분 **네거티브 기반 + 부분적 포지티브**다. API 쪽에서는 **OpenAPI 스펙을 그대로 포지티브 모델로 쓰는 방식**(스펙에 없는 필드·타입은 거부)이 자리를 잡았다. → [[REST API]] · [[API 게이트웨이]]

### 룰은 어디서 오나 — OWASP Core Rule Set
오픈소스 WAF의 사실상 표준 룰셋. 2026년 기준 **CRS 4.x**(4.26.x 대)가 현행이다.

- **패러노이아 레벨(PL 1~4)** — 룰의 공격성 단계. PL3을 켜면 PL1·2·3이 모두 켜진다. **올릴수록 탐지력↑ 오탐↑.** 대부분의 운영 서비스는 **PL1에서 시작**해 튜닝하며 올린다.
- **이상 점수 누적(anomaly scoring)** — 룰 하나 걸렸다고 바로 막지 않는다. 매칭될 때마다 심각도만큼 점수를 더하고(**CRITICAL 5 / ERROR 4 / WARNING 3 / NOTICE 2**), 누적 점수가 임계치(**기본 inbound 5, outbound 4**)를 넘을 때 차단. → 단일 룰의 [[오탐]]이 곧바로 장애가 되지 않게 하는 장치.

**엔진 쪽 지형(중요한 변화)**
| 엔진 | 상태 |
|---|---|
| **ModSecurity** | 2002년부터 업계 표준이던 원조. **2024년 1월 Trustwave가 OWASP로 이관**, **2024년 7월 1일 Trustwave 상용 지원 종료(EOL)**. OWASP 프로젝트로 유지되지만 사실상 유지보수 중심(C++). |
| **Coraza** | **Go로 새로 쓴 OWASP 정식 프로젝트.** SecLang(ModSecurity 룰 문법) 호환이라 **기존 룰 파일을 그대로 읽는다.** CRS v4가 지원 엔진으로 명시. 메모리 안전성이 채택 논리. |
| 상용/클라우드 | AWS WAF·Cloudflare·Akamai·F5·Imperva 등. CRS를 변형해 관리형 룰로 제공하는 곳이 많다. |

### 배포 형태
- **클라우드/엣지형** — DNS만 바꾸면 끝. 운영 부담이 가장 적어 기본 선택지. 단, **오리진 IP가 노출되면 통째로 우회**된다(아래 참고).
- **리버스 프록시 어플라이언스/가상장비** — 사내 DMZ에 인라인 배치. 국내 공공·금융에서 흔한 형태.
- **웹서버 모듈형** — nginx/Apache에 ModSecurity·Coraza 연동. 세밀하지만 룰 관리가 온전히 내 몫.
- **쿠버네티스 인그레스·사이드카** — 인그레스 컨트롤러에 내장하거나 서비스 메시에 얹는다. → [[쿠버네티스]]

### 운영의 본질 — 오탐과의 싸움
WAF 도입의 90%는 룰 튜닝이다. 정상 트래픽이 공격처럼 보이는 경우가 널렸기 때문이다.

- 마크다운 에디터·게시판 글에 `<script>`·SQL 문자열이 **정상 콘텐츠로** 들어온다.
- 개발자 문서·쿼리 빌더·관리자 도구의 요청은 거의 전부 공격 시그니처와 겹친다.
- Base64·JSON 중첩·파일 업로드가 룰을 우연히 만족시킨다.

**그래서 순서가 정해져 있다:**
1. **탐지(모니터링) 모드로 배포** — 아무것도 막지 않고 로그만 쌓는다. ([[CSP]]의 `Report-Only`와 같은 발상)
2. 2~4주 로그를 보며 **(룰 ID × 경로 × 파라미터) 단위로 예외** 설정. 룰 전체를 끄지 않는다.
3. 오탐이 잦아들면 **차단 모드 전환**, 이후 PL·임계치를 단계적으로 조인다.
4. 룰셋 업데이트 때마다 **정상 요청 회귀 테스트**를 돌린다.

> ⚠️ **차단형에서 오탐은 경보가 아니라 장애다.** 정상 결제 요청을 막는 WAF는 공격보다 비싼 사고를 낸다. → [[오탐]]

### 우회 — WAF가 못 하는 일
WAF는 **애플리케이션 바깥에서 바이트만** 본다. 앱이 그 바이트를 어떻게 해석할지는 모른다. 여기서 틈이 생긴다.

- **인코딩·난독화** — 다중 URL 인코딩, 유니코드 정규화, 주석 삽입(`/*!50000SELECT*/`), 대소문자 변형.
- **파서 불일치** — WAF와 앱의 JSON·멀티파트·charset 해석이 다르면 그 차이가 그대로 통로가 된다. HTTP 파라미터 오염(HPP), 요청 스머글링도 같은 계열.
- **검사 크기 제한** — 본문 검사 한도를 넘는 대용량 요청은 검사되지 않고 통과하도록 설정된 경우가 많다.
- **오리진 직접 접근** — 엣지 WAF를 붙여 놓고 **오리진 서버 IP가 노출**되면 공격자는 WAF를 건너뛰고 직접 때린다. → 오리진 방화벽에서 **엣지 IP 대역만 허용**해야 완성된다.
- **인증·인가·로직 취약점은 애초에 대상이 아니다** — 권한 없는 사용자가 정상 문법으로 남의 데이터를 요청하면 WAF에겐 정상 트래픽이다. → [[인증과 인가]] · [[OWASP Top 10]](Broken Access Control)

**그래서 WAF의 올바른 위치**는 *"취약점을 없애는 장치"*가 아니라 **가상 패치(virtual patching)** — 취약점이 발견되고 실제 코드 수정이 배포되기까지의 **시간을 벌어주는 임시 방어막**, 그리고 대량 자동화 공격을 걷어내는 **1차 필터**다. 입력 검증·파라미터라이즈드 쿼리·출력 인코딩을 대체하지 않는다. → [[웹사이트 보안]]

### 요즘 WAF가 실제로 파는 것 — WAAP
시그니처 매칭만으로는 상품이 안 되어, 현재 제품들은 **WAAP(Web Application and API Protection)**라는 묶음으로 간다:

- **봇 관리** — 크리덴셜 스터핑·스크래핑·재고 매크로 차단(레이트리밋·챌린지·핑거프린팅)
- **L7 DDoS 완화**
- **API 보안** — 스펙 기반 검증, 엔드포인트 자동 발견, 엔드포인트별 레이트리밋
- **클라이언트 사이드 보호** — 결제 페이지 스크립트 변조(Magecart) 탐지 → [[CSP]]와 역할이 겹친다
- **계정 탈취 방어** — 유출 자격증명 대조

**RASP와의 관계**: RASP는 앱 런타임 안에서 실제 실행 맥락을 보므로 **오탐이 적고 정밀하지만**, 언어·런타임마다 에이전트가 필요하고 성능 부담이 있다. 둘은 대체재가 아니라 **바깥 필터(WAF) + 안쪽 검증(RASP)** 조합으로 쓴다.

### 컴플라이언스 — 안 쓰면 안 되는 경우
**PCI DSS 4.0 요구사항 6.4.2**는 공개 웹 애플리케이션에 대해 **웹 공격을 상시 탐지·차단하는 자동화 기술(=WAF 또는 동등 솔루션)** 배치를 **2025년 3월 31일부터 의무**화했다(기존 6.4.1의 "수동 취약점 점검 또는 자동 방어 중 택1"을 대체). 카드 결제를 다루면 **선택이 아니라 필수**다. → [[ISMS]]

## 왜 중요한가
- **코드를 못 고치는 상황에서 유일하게 남는 수단.** 레거시·외주 개발·벤더 제품처럼 수정이 불가능한 앱 앞에서 WAF는 실질적인 유일 방어선이다.
- **0-day 대응 시간을 산다.** 취약점 공개 → 패치 배포 사이의 며칠을 룰 한 줄로 버틸 수 있다(가상 패치).
- **대량 자동화 공격을 걷어낸다.** 인터넷에 열린 서버가 받는 공격 트래픽의 대부분은 스캐너·봇이고, 이건 WAF가 값싸게 처리한다. 사람이 볼 것만 남기는 필터.
- **하지만 "WAF 샀으니 안전하다"가 가장 흔한 오해**다. 우회 경로가 구조적으로 존재하고([[오탐]]을 피하려 느슨하게 튜닝할수록 더), 인가·로직 취약점은 아예 시야 밖이다. **defense in depth의 한 겹**으로만 계산해야 한다.
- 컴플라이언스(PCI DSS 6.4.2)가 사실상의 도입 강제 장치가 되면서, **기술 선택이 아니라 기본 인프라**가 되었다.
