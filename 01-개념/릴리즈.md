# 릴리즈 (Release)

## 한 줄 정의
특정 버전의 소프트웨어를 빌드·검증·패키징해 **사용자에게 배포 가능한 상태로 내놓는 것**(또는 그 결과물). "이 버전을 세상에 낸다."

## 자세히

### 빌드 vs 릴리즈
- **빌드(build)** — 소스 → 실행 가능한 산출물. 하루에도 수십 번.
- **릴리즈(release)** — 그중 **검증을 통과한 빌드**를 버전 찍어 **공개**하는 것. 릴리즈는 빌드의 부분집합.

### 릴리즈 채널 (안정성 ↔ 신선도 트레이드오프)
- **Canary / Nightly** — 매일, 최소 검증, 가장 실험적.
- **Dev → Beta** — 점점 다듬어짐(Beta는 대략 주 1회).
- **RC(Release Candidate)** — 정식 후보.
- **Stable** — 엄격한 테스트 후 정식 배포.
→ Chrome·Windows Insider의 Canary/Dev/Beta/Stable이 대표 예.

### 버전 표기 — 시맨틱 버저닝(SemVer)
`MAJOR.MINOR.PATCH` (예: `2.4.1`)
- **MAJOR** — 하위 호환이 깨지는 변경
- **MINOR** — 호환되는 기능 추가
- **PATCH** — 호환되는 버그 수정

### Draft vs Published (GitHub Releases 기준)
릴리즈에는 **"만들어는 뒀지만 아직 안 낸" 중간 상태**가 있다.

| | **Draft (초안)** | **Published (게시됨)** |
|---|---|---|
| 누가 보나 | 저장소 **push(쓰기) 권한자만** | 저장소를 볼 수 있는 **모든 사람** |
| 공개 URL·다운로드 | ❌ (에셋도 공개 다운로드 불가) | ✅ |
| **Git 태그** | ❌ **아직 안 생김** — 게시할 때 생성 | ✅ 태그 존재 |
| `releases/latest` 후보 | ❌ 제외 | ✅ (prerelease 아닌 것 중) |
| 수정 | 자유롭게 고치고 다시 저장 | 이미 나간 뒤라 수습 비용 큼 |
| 전환 | **"릴리즈 게시" 버튼** → Published | (되돌리려면 삭제) |

> ⚠️ **"작성자만 보인다"는 오해.** Draft는 **쓰기 권한이 있는 협업자 전원**에게 보인다. 비공개 보관소가 아니므로 미공개 정보·키를 초안에 넣어두면 안 된다.

**Draft ≠ Prerelease** — 자주 헷갈린다.
- **Draft**: 아직 **안 나갔다**(비공개).
- **Prerelease**: **나갔지만** "프로덕션용 아님(베타·RC)" 딱지가 붙은 것 → 공개돼 있고 다운로드도 되지만 `latest`로는 안 잡힌다.
- 조합도 가능: "draft + prerelease" = 아직 안 낸 베타.

**왜 Draft를 쓰나 (배포 전 확인용)**
- 여러 OS의 설치본을 **다 붙일 때까지** 사용자에게 반쪽짜리 릴리즈가 보이지 않게 한다 ([[CI-CD]] 매트릭스 빌드는 완료 시점이 제각각).
- 릴리즈 노트·체크섬·서명 파일을 검토한 뒤 **한 번에 공개**.
- 태그가 게시 시점에 생기므로, 취소해도 **저장소에 태그 쓰레기가 남지 않는다** ([[Git 태그]]).

**자동화에서 주의할 점**
- 워크플로 이벤트가 다르다: 초안을 만들면 `release: created`, **게시해야** `release: published`가 발생. 스토어 업로드·공지·업데이터 반영 같은 **후속 작업은 `published`에 걸어야** 한다.
- **자동 업데이터는 Draft를 못 본다.** `releases/latest`가 초안을 건너뛰므로, CI가 초안까지만 만들어두고 게시를 안 하면 앱에 업데이트가 안 뜬다 — "빌드는 성공했는데 왜 업데이트가 안 오지?"의 단골 원인. ([[Tauri]] `tauri-action`은 `releaseDraft` 기본값이 `false`, 검토 절차를 두려면 `true`로 두고 **사람이 게시**하는 흐름을 쓴다.)

### 릴리즈 아티팩트 & 프로세스
- **아티팩트** — 바이너리·컨테이너 이미지·패키지(npm/PyPI)·설치본 + **릴리즈 노트/체인지로그**.
- **프로세스** — 빌드 → 테스트 → 패키징 → 서명 → 배포. [[CI-CD]]로 자동화하고 [[Git]] 태그로 버전을 고정한다. 문제 시 **롤백·핫픽스**도 릴리즈 전략의 일부.

## 왜 중요한가
- 사용자에게 도달하는 **관문**. 채널·버저닝을 잘 설계해야 **안정성과 빠른 반영을 동시에** 잡는다.
- 데스크톱/모바일 [[클라이언트 앱]]은 **자동 업데이터**로 새 릴리즈를 배포한다([[Tauri]] 업데이터 등).

## 관련 개념
- [[CI-CD]] — 릴리즈 파이프라인 자동화, `release: published` 이벤트로 후속 작업 연결
- [[Git]] · [[Git 태그]] — 태그·브랜치로 릴리즈 버전 관리 (Draft는 게시해야 태그가 생김)
- [[툴체인]] — 릴리즈 산출물을 만드는 빌드 도구
- [[클라이언트 앱]] · [[Tauri]] — 릴리즈 채널·자동 업데이트 대상
- [[Tauri 데스크톱 앱 빌드]] — CI 매트릭스로 OS별 설치본을 만들어 릴리즈에 붙이는 실제 흐름
- [[무중단 배포]] — 서버 쪽의 "언제 사용자에게 노출할까" (Draft/게시와 같은 발상)
