# WebAssembly (Wasm)

## 한 줄 정의
브라우저(및 그 밖의 런타임)에서 **거의 네이티브 속도로 실행되는 이진(binary) 명령 포맷** — C/C++/Rust/Go 등으로 짠 코드를 웹에서 돌리기 위한 컴파일 대상.

## 자세히

### 무엇인가
- JavaScript를 **대체**하는 게 아니라 **보완**한다. 브라우저의 같은 [[브라우저 엔진|JS 엔진]] 안에서, 같은 샌드박스 안에서 돈다.
- **이진 포맷**이라 파싱이 매우 빠르다(텍스트 JS 파싱 대비 훨씬 유리) → 큰 코드베이스의 **시작 시간**에서 이득.
- **DOM에 직접 접근하지 못한다.** UI 조작은 JS를 통해야 한다 → 그래서 실무 구조는 항상 **하이브리드**: JS가 DOM·라우팅·이벤트·API를, Wasm이 계산이 무거운 부분을 맡는다.
- 브라우저 밖으로도 나갔다 — **WASI**(WebAssembly System Interface)로 서버·엣지·플러그인 런타임에서도 쓰인다(안전한 샌드박스 + 빠른 시작이 [[서버리스]]와 잘 맞는다).

### 어디에 쓰나 (실제 사례)
- **Figma** — 디자인 렌더링 엔진, **Photoshop 웹** — C++ 코드베이스를 그대로 웹으로, **Google Earth** — 3D 렌더링.
- 게임·시뮬레이션, 영상/이미지 처리, 암호화, 압축, 물리 엔진, 브라우저 내 AI 추론([[온디바이스]]), 기존 C/C++ 라이브러리 재사용(예: PDF·오디오 코덱).

### 성능 — 과장 없이
- 계산 집약 작업에서 JS 대비 **대략 1.5~20배** 빠르다고 보고된다(작업 성격·최적화에 크게 의존). SIMD를 쓰면 격차가 더 벌어진다.
- 반대로 **DOM을 많이 만지거나 JS↔Wasm 경계를 자주 넘나드는 코드는 오히려 느려질 수 있다** — 경계 통과와 메모리 복사 비용이 있기 때문.
- 판단 기준: "**JS의 성능이 실제 병목인 계산 덩어리**가 있는가?" 아니라면 도입 이득보다 빌드·디버깅 복잡도가 크다.

### 만들 때
- 언어: **Rust**(wasm-pack)가 2026년 기준 신규 코드의 사실상 표준, C/C++(Emscripten), Go, C#(Blazor), Python(Pyodide).
- 디버깅은 소스맵·DWARF 지원이 좋아졌지만 여전히 JS보다 번거롭고, **번들 크기**(런타임·GC 포함)를 항상 확인해야 한다.

## 왜 중요한가
- "웹은 문서 플랫폼"이라는 한계를 넘어, **데스크톱급 애플리케이션이 브라우저에서 도는** 시대를 연 기술.
- 설치 없이 배포되고([[클라이언트 앱]]), 샌드박스 안에서 안전하게 남의 코드를 실행할 수 있다는 성질 덕에 **플러그인 시스템·엣지 런타임**의 기반으로도 확산 중.
