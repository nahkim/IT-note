# 베스천 서버 (Bastion Host)

## 한 줄 정의
**사설망으로 들어가는 문을 딱 하나만 남기고, 그 문만 집중적으로 단단하게 만든 서버.** 사내·클라우드 내부 서버들은 공인 IP를 아예 갖지 않고, 관리자는 반드시 이 한 대를 거쳐 들어간다.

> 이름이 설계를 그대로 말한다. **bastion = 성곽에서 바깥으로 튀어나온 요새(稜堡)**. 성벽 전체를 두껍게 하는 대신, **적이 반드시 지나야 하는 한 지점**을 만들고 거기에 병력을 몰아주는 것. 1990년 Marcus Ranum이 방화벽 글에서 쓴 비유가 그대로 굳었다.

## 자세히

### 그림

```
      인터넷
         │  (22번 포트, 허용 IP만)
         ▼
   ┌──────────────┐
   │  베스천 서버   │  ← 공인 IP는 여기 하나뿐. 감시·기록·하드닝 집중
   └──────┬───────┘
          │ 사설망 내부에서만 SSH 허용
   ┌──────┴───────────────────────────────┐
   ▼              ▼              ▼         ▼
 [웹 서버]      [API 서버]      [DB]    [배치 서버]   ← 전부 공인 IP 없음
```

**핵심은 "공격면을 줄이는 게 아니라 한 점으로 모은다"** 는 것. 서버가 20대든 200대든 **인터넷에 노출된 SSH 포트는 하나**가 된다. 그러면 거기에만 MFA·세션 기록·침입 탐지·패치를 몰아줄 수 있다.

### 베스천 vs 점프 서버 — 같은 말처럼 쓰지만
실무에선 거의 구분 없이 쓰이고, 그래도 되는 경우가 대부분이다. 굳이 나누면:

| | **베스천 호스트** | **점프 서버** |
|---|---|---|
| 강조점 | **외부에 노출된 채 버티는** 하드닝된 요새 | **구역과 구역 사이를 건너는** 경유점 |
| 위치 | DMZ·공개 경계 | 내부망 사이(예: 사무망 → 운영망, IT → OT) |
| 노출 | 인터넷에 직접 | 보통 내부에서만 |

> 🔑 한 문장: **베스천은 "밖에서 들어오는 문"**, **점프 서버는 "안에서 더 안쪽으로 가는 문"**. 클라우드에서는 한 대가 둘 다 한다.

### 어떻게 지나가나 — ProxyJump가 정답
```bash
# ❌ 나쁜 방법: 베스천에 ssh 한 뒤 거기서 또 ssh
#    → 내 개인키를 베스천에 복사하거나 에이전트를 포워딩하게 된다

# ✅ ProxyJump (-J) — OpenSSH 7.3(2016)부터
ssh -J user@bastion user@10.0.1.23

# ~/.ssh/config 에 박아두면 그냥 `ssh web-1`
Host bastion
    HostName bastion.example.com
    User ops
    IdentityFile ~/.ssh/id_ed25519

Host web-1
    HostName 10.0.1.23
    User deploy
    ProxyJump bastion       # 구버전 호환: ProxyCommand ssh -W %h:%p bastion
```

**ProxyJump가 왜 안전한가** — 베스천은 **암호화된 바이트를 중계만** 한다. 인증 협상은 내 PC와 최종 서버 사이에서 end-to-end로 일어나고, **내 개인키는 내 기기를 떠나지 않는다.**

⚠️ **그래서 `ForwardAgent yes`(에이전트 포워딩)를 쓰지 말 것.** 에이전트 소켓을 베스천에 넘겨주는 것이라, **베스천이 뚫리면 공격자가 그 소켓으로 내 신원을 빌려** 다른 서버에 로그인한다. 베스천은 정의상 "가장 많이 공격받는 서버"인데 거기에 내 만능 열쇠를 꽂아두는 셈. → [[SSH 공개키 인증]]

파일 전송·포트 포워딩도 그대로 얹힌다. 사설 DB에 로컬 클라이언트로 붙는 그 흐름이 베스천의 일상적 쓰임이다. → [[터널링]]
```bash
ssh -J user@bastion -L 5432:db.internal:5432 user@10.0.1.23
```

### 베스천을 베스천답게 만드는 것 — 체크리스트
문을 하나로 모으는 건 **그 문이 단단할 때만** 이득이다. 아니면 그냥 **단일 실패 지점이자 단일 침투 지점**이 된다.

- **최소 구성** — 그 서버에서 아무 일도 하지 않는다. 앱·DB·에이전트를 올리지 않는다. 설치된 패키지가 곧 공격면.
- **인바운드는 22번 + 출발지 IP 제한**(사무실·VPN 대역). 전 세계에 열어두면 베스천의 절반이 무의미해진다.
- **비밀번호 로그인 금지** — `PasswordAuthentication no`, 키 또는 **SSH 인증서(CA 서명)** 만. 인증서를 쓰면 서버마다 `authorized_keys`를 뿌릴 필요가 없고 **만료**를 걸 수 있다.
- **MFA** — PAM + TOTP 등. 키 하나가 털려도 한 겹 더 남는다. → [[인증과 인가]]
- **내부 서버는 베스천에서 오는 SSH만 허용** — 보안그룹·방화벽으로 강제. 이걸 안 하면 우회 경로가 남아 베스천은 장식이 된다.
- **세션 기록과 로그 반출** — 누가 언제 어디로 들어가 무엇을 했는지. **로그는 베스천 밖으로 즉시 보낸다**(침입자가 지울 수 있으므로).
- **짧은 수명** — 자동 패치, 또는 아예 **매번 새로 띄우고 버리는**(ephemeral) 베스천. 쓸 때만 올리고 끝나면 내린다.
- **이중화** — 베스천이 죽으면 전 서버에 못 들어간다. 장애 시 복구 경로(콘솔 접근 등)를 미리 정해 둘 것. → [[런북]]

### ⚠️ 흔한 함정
- **"베스천을 두었으니 안전하다"** — 내부 서버에 공인 IP나 다른 인입 경로가 남아 있으면 **아무것도 지켜지지 않는다.** 베스천은 *유일한* 문일 때만 문이다.
- **베스천 위에서 작업하기** — 소스 코드를 clone 하고 `kubectl`을 깔고 자격증명을 두는 순간, 요새가 **자격증명 보관함**으로 바뀐다. 거기가 털리면 전부 털린다. → [[환경 변수]]
- **공용 계정 하나를 모두가 공유** — 기록이 남아도 *누가* 했는지 모른다. 베스천의 핵심 가치(감사)가 사라진다.
- **에이전트 포워딩**(위 ⚠️).
- **포트를 22에서 2222로 옮기면 안전해진다는 착각** — 스캔 소음은 줄지만 보안은 그대로다.
- **키 회수 절차 부재** — 퇴사·단말 분실 때 `authorized_keys`에서 지워야 할 곳이 수십 군데면 결국 안 지운다. 인증서·중앙 브로커가 답.

### 2026년의 흐름 — 베스천을 "없애는" 쪽
요즘 설계는 **SSH 포트를 아예 열지 않는 방향**으로 간다. 서버에 설치된 에이전트가 **아웃바운드로 관리 평면에 붙어 있고**, 접속은 그 통로로 역방향으로 들어간다. → 사실상 [[터널링]]의 리버스 패턴 + 신원 기반 인가.

| 방식 | 인증 | 인바운드 포트 | 비고 |
|---|---|---|---|
| **고전 베스천** | SSH 키·인증서 + MFA | **22 열림** | 어디서나 되고, 운영 책임이 내게 |
| **AWS SSM Session Manager** | **IAM** | **없음** | 에이전트가 아웃바운드로 연결, 세션 로깅 내장 |
| **EC2 Instance Connect Endpoint** | IAM | 없음 | 사설 서브넷 인스턴스에 SSH |
| **Azure Bastion / GCP IAP TCP forwarding** | 클라우드 IAM | 없음 | 매니지드 관문 |
| **Teleport·Cloudflare Access 등** | SSO·OIDC + 단기 인증서 | 없음 | 멀티클라우드·온프레미스 혼재 환경 |

> 공통점은 하나 — **"네트워크 위치가 곧 권한"이라는 전제를 버린다.** 베스천은 *"이 IP에서 왔으니 통과"* 라는 경계 모델의 유산이고, 제로 트러스트는 *"누구인지·어떤 기기인지 매번 확인"* 으로 옮겨 간다. 세션은 짧고, 권한은 좁고, 전부 기록된다.

**그렇다고 베스천이 죽은 건 아니다.** 온프레미스, 특정 클라우드에 묶이지 않은 환경, 에이전트를 깔 수 없는 레거시·네트워크 장비·OT 설비에서는 여전히 가장 현실적인 답이다. → [[온프레미스]]

## 왜 중요한가
- **"DB에 어떻게 접속하지"의 표준 답**이다. 운영 DB에 공인 IP를 주는 것과 베스천 뒤에 두고 포트 포워딩으로 붙는 것의 차이는, 사고가 났을 때 **노출 범위가 전부냐 한 대냐**로 갈린다.
- **감사(audit)의 출발점.** ISMS·ISO 같은 인증에서 "운영 서버 접근 통제와 기록"은 거의 반드시 묻는 항목이고, 접근 경로가 하나로 모여 있어야 답할 수 있다. → [[ISMS]]
- **"문을 하나로 모은다"는 패턴 자체가 재사용된다.** [[API 게이트웨이]]가 API에 대해, [[리버스 프록시]]가 HTTP에 대해 하는 일이 베스천이 SSH에 대해 하는 일과 같다 — **단일 진입점 + 그 지점에 통제 집중.**
- **클라우드 비용·운영의 단골 주제.** 항상 켜 둘지, 쓸 때만 띄울지, 아예 매니지드로 갈지는 보안·비용·편의의 실제 트레이드오프다. → [[트레이드오프]]

> ✅ **웹 교차검증 완료** — **"bastion host" 용어가 1990년 Marcus J. Ranum의 방화벽 글에서 "네트워크 보안의 결정적 강점(critical strong point)"으로 정의되었고, 군사 요새의 稜堡(bastion)에서 온 비유**이며 DMZ·방화벽 바깥에서 신뢰할 수 없는 네트워크를 상대하는 하드닝 서버라는 점을 Wikipedia 및 복수 해설로 확인(원문 연도를 1993으로 적는 출처도 있음). **ProxyJump(`-J`)는 OpenSSH 7.3(2016)에서 도입되어 `ProxyCommand ssh -W %h:%p`를 대체**했고, **에이전트 포워딩(`ForwardAgent yes`)은 점프 호스트가 침해되면 포워딩된 에이전트로 사용자를 사칭할 수 있어 ProxyJump가 권장 대안**(개인키가 로컬을 떠나지 않음)이라는 점을 OpenSSH Cookbook 및 복수 가이드로 확인. 2026년 베스천 하드닝 관행(**최소 패키지, 자동 업데이트, SSH 키 필수 + PAM/TOTP MFA 선택, 출발지 IP 제한, 하위 서버는 베스천에서만 SSH 허용**)을 복수 2026년 실무 가이드로 확인. 대안으로 **AWS SSM Session Manager(IAM 인증·인바운드 포트 불필요·전 세션 로깅)**, **EC2 Instance Connect**, **Azure Bastion·Google Cloud IAP** 같은 매니지드 관문, **Teleport·Cloudflare Access** 등 신원 인지 프록시로 "베스천을 네트워크 경계 개념에서 제거"하는 제로 트러스트 이행 경로가 통용된다는 점을 AWS·Netskope·Teleport 등 복수 출처로 확인.
