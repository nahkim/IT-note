# Tauri vs Wails — 웹 UI + OS 웹뷰, 백엔드가 Rust냐 Go냐

## 한 줄 요약
둘 다 **"웹 기술로 UI + OS 내장 웹뷰로 렌더링 + Chromium 미번들"** 이라는 **같은 아키텍처**의 경량 데스크톱 프레임워크다. 가장 큰 갈림길은 **백엔드 언어**: **[[Tauri]] = Rust**, **[[Wails]] = Go**. 여기서 성능 성향·학습 곡선·생태계·성숙도가 갈린다.

## 공통점 (왜 자주 비교되나)
- **웹 UI + OS 웹뷰** — WebView2(Win)·WKWebView(mac)·WebKitGTK(Linux)를 재사용. Chromium을 통째로 안 넣어 **설치본이 수 MB~십수 MB**로 작다. (둘 다 Electron 경량 대안)
- **프론트엔드 자유** — React·Vue·Svelte·순수 JS 등 빌드 결과물만 있으면 붙는다.
- **프론트↔백엔드 브리지** — JS에서 백엔드 함수를 호출(Tauri: `invoke('command')`, Wails: 자동 생성 **바인딩**).
- **플랫폼별 웹뷰 차이라는 같은 약점** — WebKit vs Chromium 렌더링·CSS 미묘한 차이. (Electron이 일관성에서 앞서는 지점)

## 차이 (핵심)

### 🦀 Tauri — 백엔드 Rust
- **성능·메모리**: GC가 없는 Rust → 메모리 사용이 예측 가능하고 무거운 런타임이 없다.
- **모바일**: **Tauri 2.0(안정)** 부터 **iOS/Android** 정식 지원 → 데스크톱+모바일 한 코드베이스.
- **보안**: 명시적 **권한(Permissions) 시스템**으로 앱이 쓸 시스템 API를 선언.
- **비용**: **Rust 학습 곡선**이 진입장벽. 커뮤니티·생태계가 활발하고 상대적으로 규모가 크다.

### 🐹 Wails — 백엔드 Go
- **개발 편의**: **Go의 낮은 진입장벽**과 빠른 컴파일, 단일 실행 파일. Go 생태계(서버·CLI·네트워킹) 재사용에 유리.
- **성능·메모리**: Go는 **GC 언어** → 대체로 충분히 빠르고 가볍지만, 메모리 성향은 Rust와 다르다.
- **모바일·멀티윈도우**: **v2는 데스크톱 전용**. iOS/Android·멀티윈도우·플러그인은 **v3(알파)** 에서 도입 중 → 프로덕션은 아직 v2(데스크톱) 기준.
- **성숙도**: 안정판 기준 기능 범위가 Tauri보다 좁은 편(특히 모바일).

## 비교표

| 항목 | 🦀 Tauri | 🐹 Wails |
|---|---|---|
| 백엔드 언어 | Rust (GC 없음) | Go (GC 있음) |
| UI 렌더링 | OS 웹뷰 (공통) | OS 웹뷰 (공통) |
| 앱 용량 | 수 MB~십수 MB | 수 MB~십수 MB |
| 브리지 | `invoke('command')` | 자동 생성 바인딩 |
| 모바일(iOS/Android) | **2.0 안정 지원** | v3(알파)에서 도입 중 |
| 멀티 윈도우 | 지원 | v2 제한적 → v3에서 강화 |
| 학습 곡선 | 높음(Rust) | 낮음(Go) |
| 생태계·성숙도 | 더 크고 활발 | 성장 중, 안정판은 데스크톱 중심 |
| 보안 모델 | 권한 시스템 명시 | — |

## 언제 무엇을
- **모바일까지 한 코드베이스로, 최소 런타임·강한 보안 모델** → **Tauri** (특히 v2). Rust 감수 가능할 때.
- **팀이 Go에 익숙 / Go 백엔드 자산 재사용 / 빠르게 데스크톱 앱** → **Wails**. 모바일이 당장 필요 없다면 v2로 충분.
- **모든 OS에서 픽셀 단위로 동일한 렌더링·성숙한 생태계가 최우선** → 둘 다 아니고 **Electron**(용량·메모리는 포기).
