# 배포 도구 지형 — Tomcat · Jenkins · ArgoCD는 경쟁자가 아니다

## 한 줄 요약
**이 셋은 비교 대상이 아니라 서로 다른 층이다.** **Tomcat = 코드가 실제로 도는 런타임**, **Jenkins = 코드를 빌드·테스트하는 CI**, **ArgoCD = 만들어진 결과물을 클러스터에 반영하는 CD**. "Jenkins와 ArgoCD 중 뭘 쓰지?"는 *"망치와 못 중 뭘 쓰지?"* 에 가까운 질문이고, 실제로는 **같이 쓴다.** → [[CI-CD]]

## 전체 지도

```
 ① 소스        ② CI (빌드·테스트)      ③ 아티팩트          ④ CD (배포)         ⑤ 런타임
┌────────┐   ┌──────────────────┐   ┌─────────────┐   ┌──────────────┐   ┌─────────────┐
│  Git   │──▶│ Jenkins          │──▶│ 컨테이너 이미지 │──▶│ ArgoCD·Flux  │──▶│ 쿠버네티스   │
│ GitHub │   │ GitHub Actions   │   │ (또는 WAR·JAR)│   │ (GitOps)     │   │ 또는 VM+WAS │
└────────┘   │ GitLab CI        │   │ 레지스트리     │   │ 또는 스크립트  │   │ Tomcat 등   │
             └──────────────────┘   └─────────────┘   └──────────────┘   └─────────────┘
                  "만든다"                "보관한다"          "반영한다"         "돌린다"
```

> 🔑 **각 층의 질문이 다르다** — ②는 *"이 커밋이 빌드·테스트를 통과하나"*, ④는 *"지금 운영에 떠 있는 게 Git에 적힌 그것과 같은가"*, ⑤는 *"HTTP 요청을 누가 받아 처리하나"*. 층을 섞으면 도구 선택이 꼬인다.

## ⑤ 런타임 층 — Tomcat과 WAS

### 무엇인가
**Tomcat은 Java 서블릿 컨테이너**다. HTTP 요청을 받아 Java 웹 애플리케이션(서블릿)에 넘기고 응답을 돌려준다. 역사적으로 Java 웹앱은 **WAR 파일**로 패키징해 **별도로 설치한 Tomcat에 배포**했다.

**WAS(Web Application Server)** 라는 말은 더 넓다. Tomcat은 서블릿·JSP만 하는 **경량 컨테이너**이고, WebLogic·WildFly·JEUS 같은 **풀 Jakarta EE 서버**는 트랜잭션·메시징·EJB까지 품는다. 한국 금융·공공에서는 WebLogic·JEUS가 여전히 현역이다.

### 결정적 변화 — "WAS에 배포"에서 "WAS를 들고 다니는 앱"으로
Spring Boot가 바꿔놓은 지점이다.

```
예전:  [Tomcat 설치·운영]  ◀── app1.war, app2.war, app3.war 를 올림
       → 서버 한 대에 여러 앱, Tomcat 버전·설정은 운영팀 소관

지금:  java -jar app.jar   ← 앱 안에 Tomcat이 내장(embedded)되어 있음
       → 앱 하나 = 프로세스 하나. 그대로 컨테이너 이미지에 넣는다
```

**Tomcat이 사라진 게 아니라 위치가 바뀌었다.** Spring Boot 기본 내장 서버가 바로 Tomcat이다. 다만 이제 **운영팀이 관리하는 미들웨어가 아니라 앱의 라이브러리**다. 그래서 "Tomcat 안 쓴다"는 말은 대개 *"스탠드얼론 Tomcat을 안 쓴다"* 는 뜻.

### 장단점 · 언제
| | 스탠드얼론 Tomcat/WAS (WAR) | 내장 서버 (실행 가능 JAR) |
|---|---|---|
| 장점 | 서버 설정·튜닝 **중앙 관리**, 한 서버에 여러 앱, 기존 운영 체계·인증 솔루션과 궁합 | **앱=프로세스** 단순함, 컨테이너·[[쿠버네티스]]와 자연스러움, 앱마다 버전 독립 |
| 단점 | 앱끼리 **JVM·라이브러리 충돌**, 버전 올리기 어려움, 컨테이너화가 어색 | 메모리를 앱마다 따로 먹음, 미들웨어 설정이 앱에 흩어짐 |
| 쓸 때 | 레거시 Java EE, 사내 표준 WAS, 폐쇄망·전자정부 프레임워크 | **신규 프로젝트 기본값**, 컨테이너 배포 |

- ⚠️ **Tomcat 10부터 패키지가 `javax.servlet` → `jakarta.servlet`로 바뀌었다.** 구버전 앱을 10+에 그대로 올리면 깨진다. 레거시 업그레이드의 가장 큰 벽.
- 성능은 WAR든 JAR든 **사실상 같다.** WAR의 가치는 속도가 아니라 **중앙 관리**다.
- 비슷한 선택지: **Jetty**(더 가볍고 임베디드 친화), **Undertow**, **Netty**(Spring WebFlux 등 논블로킹).
- 앞단에는 보통 [[리버스 프록시]](nginx)와 [[로드 밸런서]]가 선다.

> 📌 **2026 기준 기본값** — 신규는 **Spring Boot 내장 Tomcat + 컨테이너 이미지**. 스탠드얼론 WAS는 *"이미 있어서"* 유지하는 경우가 대부분이고, 새로 고르는 일은 드물다.

## ② CI 층 — Jenkins와 그 대안들

### 무엇인가
**푸시·PR을 방아쇠로 빌드·테스트·패키징을 자동 실행**하는 서버. Jenkins는 2011년부터 이 자리를 지켜온 사실상의 원조이자, **플러그인 1800여 개로 무엇이든 되는** 범용 자동화 서버다.

### 선택지 비교
| | **Jenkins** | **GitHub Actions** | **GitLab CI** | **Tekton·Argo Workflows** |
|---|---|---|---|---|
| 형태 | 직접 설치·운영 | SaaS(러너는 선택) | GitLab 내장 | 쿠버네티스 네이티브 |
| 장점 | **무엇이든 가능**, 폐쇄망 OK, 특수 빌드(임베디드·GPU·온프레미스 하드웨어) | 코드 **바로 옆**, 설정이 YAML 한 장, 생태계(마켓플레이스) 거대 | 저장소·이슈·레지스트리·CD가 **한 제품 안에** | 파이프라인이 **k8s 리소스**, 확장성 |
| 단점 | **운영 부담**(서버·플러그인·보안 패치), 플러그인 충돌·기술부채, 느린 UI | GitHub 종속, 대규모에서 **비용**, 셀프호스티드 러너 보안 주의 | GitLab을 써야 의미 | 진입장벽 높고 UI 빈약 |
| 쓸 때 | 폐쇄망·규제 환경, 기존 자산이 많을 때, 특이한 빌드 환경 | **신규 프로젝트 기본값** | 이미 GitLab 사용 중 | k8s 플랫폼팀이 직접 꾸릴 때 |

### 지금 어떤 걸 쓰나 (2026)
- **GitHub Actions가 선두.** 조직 채택률 1위, GitHub 저장소 기준으로는 CI 파이프라인의 대다수를 차지한다. *"가장 좋은 CI는 소스 코드에 가장 가까운 CI"* 라는 명제가 승부를 갈랐다.
- **Jenkins는 점유율이 매년 내려가지만 죽지 않았다.** 여전히 Fortune 500 다수의 파이프라인 중추이고, **금융·통신·제조의 폐쇄망**에서는 대체재가 마땅치 않다. "레거시"가 아니라 **"그 환경에서는 여전히 정답"** 으로 읽는 게 정확하다.
- **한 조직이 두 개 이상 쓰는 게 흔하다**(약 1/3이 2개, 10% 가까이가 3개 이상). 신규는 Actions, 기존 대형 파이프라인은 Jenkins로 **공존**하는 그림.
- ⚠️ **셀프호스티드 러너는 보안 설계가 필수**다. 포크 PR이 러너에서 임의 코드를 실행할 수 있는 구조를 그냥 두면 사고가 난다. → [[셀프호스티드 러너]]

## ④ CD 층 — ArgoCD와 GitOps

### 무엇인가
**GitOps = "운영 상태의 정답은 Git에 있다"**. ArgoCD는 쿠버네티스 안에 상주하면서 **Git 저장소의 매니페스트와 클러스터의 실제 상태를 끊임없이 비교(diff)** 하고, 어긋나면 알리거나 되돌린다(sync).

```
푸시(push) 방식                      풀(pull) 방식 = GitOps
CI가 kubectl apply 로 밀어 넣음       클러스터 안의 ArgoCD가 Git을 당겨와 맞춤
 └ CI에 클러스터 자격증명이 있어야 함     └ 자격증명이 클러스터 밖으로 안 나간다
 └ 누가 손으로 바꿔도 아무도 모름         └ 손으로 바꾸면 "OutOfSync"로 드러난다
```

**핵심 이득은 자동화가 아니라 `드리프트 가시화`와 `감사 가능성`이다.** 지금 운영에 떠 있는 게 무엇인지 **Git 로그로 증명**되고, 롤백이 `git revert`가 된다. → [[형상관리]] · [[무중단 배포]]

### 선택지 비교
| | **ArgoCD** | **Flux** | **(비교) CI가 직접 배포** |
|---|---|---|---|
| 특징 | **웹 UI**가 강력(앱 트리·diff·동기화 버튼), 멀티클러스터 | CLI·컨트롤러 중심, 모듈형·가벼움 | `kubectl`·`helm`·스크립트 |
| 장점 | 개발자가 **눈으로 보고 이해**함, 생태계·SSO·RBAC 성숙 | 리소스 소비 적고 조립이 자유로움, 자동화 친화 | 단순, 배울 게 없음 |
| 단점 | 컴포넌트가 무겁고 운영 대상이 하나 늘어남 | UI가 없어 가시성은 직접 붙여야 | **드리프트 추적 불가**, 자격증명 노출, 규모가 커지면 붕괴 |
| 쓸 때 | **k8s를 쓰고 팀이 여럿이면 기본값** | 플랫폼팀이 직접 조립·경량 선호 | 서버 몇 대 수준의 소규모 |

- **점진적 배포(카나리·블루그린)** 는 ArgoCD 자체가 아니라 **Argo Rollouts**(또는 Flagger)가 맡는다. → [[무중단 배포]]
- 매니페스트 생성은 **Helm·Kustomize**가 담당한다. ArgoCD는 그걸 렌더링해 적용하는 쪽.
- ⚠️ **시크릿을 Git에 평문으로 넣지 말 것.** Sealed Secrets·External Secrets·SOPS 같은 장치가 따로 필요하다. GitOps의 가장 흔한 사고 지점. → [[환경 변수]]
- ⚠️ **쿠버네티스가 없으면 GitOps 도구도 의미가 거의 없다.** VM 몇 대라면 [[Ansible]]이나 배포 스크립트가 맞다.

### 지금 어떤 걸 쓰나 (2026)
- **ArgoCD가 사실상의 표준.** GitOps 사용 조직의 절반 이상이 ArgoCD를 쓰고, Flux는 한 자릿수~10% 남짓. GitHub 스타 격차도 두 배 이상 벌어졌다.
- **Flux는 죽지 않았다** — 주요 후원사(Weaveworks) 폐업 후에도 CNCF 아래에서 유지되고 있고, 경량·모듈성을 중시하는 플랫폼팀에서 선택된다.
- **Spinnaker는 사실상 밀려났다.** 무겁고 운영 비용이 크다는 평가가 굳었다.
- **GitOps 자체의 채택률이 임계점을 넘었다** — 쿠버네티스를 쓰는 조직에서는 "할까 말까"가 아니라 "어떤 도구로"의 문제가 됐다.

## 🎯 지금 새로 시작한다면 — 상황별 기본 조합

| 상황 | CI | CD | 런타임 | 비고 |
|---|---|---|---|---|
| **소규모 서비스, 서버 1~3대** | GitHub Actions | Actions에서 바로 `ssh`·`docker compose` | 컨테이너 + 내장 Tomcat | **ArgoCD·k8s는 과잉.** 단순함이 이긴다 |
| **쿠버네티스 쓰는 중규모 팀** | GitHub Actions / GitLab CI | **ArgoCD** | 컨테이너 | 가장 흔한 2026년 표준 조합 |
| **대규모·멀티클러스터** | Actions + 일부 Jenkins | ArgoCD + **Argo Rollouts** | 컨테이너 | 점진적 배포·멀티테넌시까지 |
| **금융·공공·폐쇄망** | **Jenkins**(사내 설치) | Jenkins 파이프라인 또는 ArgoCD | **스탠드얼론 WAS**(WebLogic·JEUS·Tomcat) | 망분리·인증 요건이 도구를 결정한다 → [[ISMS]] |
| **레거시 Java 유지보수** | Jenkins | WAR 배포 스크립트 | Tomcat/WAS | 바꾸는 것보다 **안 바꾸는 비용**이 쌀 수 있다 |

> 💡 **고르는 순서는 거꾸로다.** 런타임(k8s인가 VM인가)이 정해지면 CD가 거의 자동으로 결정되고, CD가 정해지면 CI는 "소스가 어디 있느냐"로 결정된다. 도구부터 고르면 반드시 꼬인다.

## ⚠️ 흔한 오해
- **"Jenkins vs ArgoCD"** — 범주 오류. Jenkins는 빌드, ArgoCD는 반영. 굳이 겹치는 지점은 *"Jenkins가 `kubectl apply`까지 하느냐"* 뿐이고, 그걸 떼어내는 게 GitOps다.
- **"ArgoCD를 쓰면 CI가 필요 없다"** — ArgoCD는 **빌드하지 않는다.** 이미지를 만드는 건 여전히 CI의 일.
- **"Tomcat은 레거시다"** — 위치가 바뀌었을 뿐 Spring Boot 앱 안에서 그대로 돌고 있다.
- **"도구를 바꾸면 배포가 빨라진다"** — 병목은 대개 **테스트 시간·승인 절차·배포 단위 크기**에 있다. 도구는 그다음. → [[무중단 배포]] · [[피처 플래그]]
- **"GitOps면 손으로 못 고친다"** — 고칠 수는 있다. 다만 **드러난다**(OutOfSync). 그게 핵심 가치다.

> ✅ **웹 교차검증 완료** — **CI 점유(2026)**: GitHub Actions가 조직 채택률 1위(약 33%), Jenkins 약 28%, GitLab CI 약 19%이며 **Jenkins는 전년 대비 하락세지만 Fortune 500 다수에서 여전히 핵심**, GitHub 저장소 기준으로는 Actions가 압도적, **조직의 약 1/3이 CI 도구를 2개 이상 병행**한다는 점을 JetBrains/TeamCity 2026 CI 도구 데이터 분석 및 복수 2026 비교 글로 확인. **GitOps**: Argo CD가 GitOps 시장의 과반(약 50~60%)이고 Flux는 약 11% 수준, GitHub 스타 격차(약 23.1K vs 8.2K), **Flux 주 후원사 Weaveworks 폐업 후에도 CNCF 아래 유지**되고 있으며 **GitOps를 주 배포 수단으로 쓰는 기업이 60%를 넘겼다**는 점을 The New Stack 설문 기사 및 2026 ArgoCD/Flux 비교 분석으로 확인. **Tomcat**: 현재도 활발히 유지보수되는 세계에서 가장 많이 쓰이는 Java 서블릿 컨테이너이고, **Spring Boot는 Tomcat을 내장해 `java -jar`로 단독 실행**하며 스탠드얼론은 WAR를 올리는 전통적 방식, **WAR와 JAR의 성능 차이는 사실상 없고 WAR의 이점은 중앙 관리**, **Tomcat 10+부터 `javax.servlet` → `jakarta.servlet` 전환으로 구버전 앱 호환성이 깨진다**는 점을 Baeldung 등 복수 Spring Boot/Tomcat 배포 가이드로 확인.
