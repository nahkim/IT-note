# RBAC vs ABAC — 권한을 무엇으로 결정할 것인가

## 한 줄 요약
둘 다 **인가(authorization)**, 즉 "이 사람이 이걸 해도 되나"를 판단하는 방식이다. 차이는 **판단의 근거** 하나: **[[RBAC]]은 미리 정해 둔 역할**로, **[[ABAC]]은 요청 시점의 속성·맥락**으로 결정한다.

## 공통점
- **인증(AuthN)이 끝난 다음** 단계다. "누구인지"는 이미 알고 있고, "무엇을 해도 되는지"만 다룬다. → [[인증과 인가]]
- 목표는 같다: **[[최소 권한 원칙]]** 을 지키면서 관리 가능한 형태로 권한을 운영하기.
- 둘 다 **권한을 코드에 흩뿌리지 않고 한곳에 모으는** 방향이다. `if (user.id === 3)` 같은 하드코딩에서 벗어나려는 시도라는 점에서 한 가족.

## 핵심 차이 — "미리 정해 둔 표" vs "그때 계산하는 규칙"
- **[[RBAC]]** — `사용자 → 역할 → 권한`. 권한이 **사전에 나열**돼 있고, 요청이 오면 **조회**한다. 조직도처럼 **정적**이다.
- **[[ABAC]]** — `속성 + 정책 → 판단`. 권한이 어디에도 나열돼 있지 않고, 요청마다 **계산**된다. 시간·위치·기기 같은 **동적 맥락**이 들어온다.

한 문장으로: **RBAC은 "너는 편집자니까 된다", ABAC은 "지금 상황이 조건에 맞으니까 된다".**

## 비교표
| 기준 | RBAC (역할 기반) | ABAC (속성 기반) |
|---|---|---|
| 판단 근거 | **역할** (미리 부여) | **속성**(주체·자원·행위·**환경**) |
| 결정 시점 | 사실상 사전에 확정 | **요청 시점에 평가** |
| 세밀함 | 거칠다(역할 단위) | 매우 세밀(조건 조합) |
| 동적 맥락(시간·위치·기기) | ❌ 표현 불가 | ✅ 핵심 기능 |
| 설계 난이도 | 낮음, 직관적 | 높음(정책 설계·속성 정비) |
| 확장 시 문제 | **역할 폭발**(예외마다 역할 증식) | **정책 복잡도**·디버깅 난이도 |
| 감사(누가 뭘 볼 수 있나) | ✅ 목록으로 뽑기 쉬움 | ❌ 사전 나열이 어려움 |
| 성능 | 조회 중심, 가볍다 | 매 요청 평가 + 속성 조회(캐싱 필요) |
| 전제 조건 | 역할 체계가 정리돼 있을 것 | **속성 데이터가 정확할 것**(HR·자산 정보) |
| 대표 구현 | [[쿠버네티스]] Role/RoleBinding, AWS IAM 역할, DB GRANT | OPA/Rego, AWS Cedar, IAM `Condition`·태그, Azure ABAC 조건 |

## 언제 무엇을
- **RBAC** — 사내 어드민, 백오피스, 인프라 접근처럼 **직무가 안정적이고 사람 수가 권한 수보다 많은** 곳. 규제 감사에서 "권한 목록을 내놔라"는 요구가 있는 곳. **기본값은 여전히 RBAC이다.**
- **ABAC** — **제로 트러스트**(기기·위치·시간 반영), 데이터 등급별 통제, 멀티테넌시에서 "자기 테넌트 자원만"처럼 **자원 속성과 사용자 속성을 맞춰 보는** 규칙, 예외 조건이 계속 늘어 역할이 폭발하기 시작한 곳.
- **판단 신호 하나** — 새 요구사항이 올 때마다 `편집자-야간제외-서울지사` 같은 역할을 또 만들고 있다면, 그건 ABAC으로 넘어갈 때가 됐다는 뜻이다.

## 현실의 답은 대개 "둘 다"
실무에서 순수 RBAC이나 순수 ABAC은 드물다. **계층으로 겹쳐 쓴다.**

1. **RBAC으로 큰 틀** — 관리자/편집자/뷰어처럼 굵은 권한을 역할로 깐다. 관리·감사가 쉬운 부분을 최대한 여기서 처리.
2. **ABAC으로 조건을 덧입힘** — "단, 대외비 문서는 업무시간·사내망에서만", "단, 자기 부서 자원만". 역할을 늘리는 대신 조건을 건다.
3. **자원 공유 구조가 깊다면 ReBAC** — 문서·폴더·조직처럼 **소유·공유 관계**를 따라가야 하는 경우엔 관계 그래프 기반이 더 자연스럽다(Google Zanzibar 계열: OpenFGA·SpiceDB). B2B SaaS에서 **RBAC(거친 권한) + ReBAC(자원 단위 권한)** 조합이 흔하다.

> 정리하면 — **역할은 "기본형", 속성은 "조건절", 관계는 "소유 구조"**. 셋은 대체재라기보다 서로 다른 질문에 답한다.

## 자주 하는 오해
- **"ABAC이 상위 호환이다"** — 아니다. ABAC은 사전 권한 목록을 잃는다. 감사·인수인계가 중요한 조직에서는 그게 치명적 손실일 수 있다.
- **"RBAC은 낡았다"** — 아니다. [[쿠버네티스]]·클라우드 IAM의 기본 뼈대는 지금도 RBAC이다. ABAC은 그 위에 얹는 조건이지 대체가 아니다.
- **"ABAC 도입 = 정책 엔진 도입"** — 엔진보다 **속성 데이터 정비**가 먼저다. 부서 정보가 틀린 채로 정책만 정교해지면 정교하게 틀린 권한이 나온다.
