# 📝 소규모 AWS 웹서비스 전형 구성 (조립도 · 점검 순서)

> 🔒 **주소는 전부 자리표시자다.** `CF_DOMAIN`(CDN) · `ALB_IP`(로드밸런서) · `WEB1_IP`/`WEB2_IP`(앱 서버) · `BASTION_IP`(베스천) · `DB_ENDPOINT`(RDS)

## 한 줄 요약
**CDN + 로드밸런서 + 앱 서버 두 대 + RDS + 베스천 한 대.** 국내 스타트업·중소 규모에서 압도적으로 많이 나오는 모양이고, **여기서 발견되는 문제도 거의 정해져 있다.** 이 노트는 개별 개념 노트들을 **한 장의 조립도로 묶고**, 처음 인프라를 받았을 때 **무엇을 어떤 순서로 재는지**를 정리한 것이다.

## 핵심 내용

### 1. 조립도 — 두 평면을 겹쳐 그린다

```
   데이터 평면 (사용자 요청)              컨트롤 평면 (배포·운영)
 ══════════════════════════            ══════════════════════════
   [사용자]                               [내 노트북]  [CI(Jenkins)]
      │ https                                  │ ssh :22    │
      ▼                                        └─────┬──────┘
   [CDN  CF_DOMAIN]  ← 중간 장비 ①                   ▼
      │                                        [베스천 BASTION_IP]
      ▼                                         · sshd :22
   [ALB  ALB_IP]     ← 중간 장비 ②               · CI 서버 겸용
      │                                         · DB 터널 중계
      ├──────────────┐                                │ ssh (배포)
      ▼              ▼                                │
 ┌────────────┐ ┌────────────┐  ◀───────────────────┘
 │ WEB1_IP    │ │ WEB2_IP    │
 │  admin-api │ │  admin-api │   :3001   ← ALB 가 직접 붙는 포트
 │  app-api   │ │  app-api   │   :3000
 │  monitor   │ │  monitor   │   (포트 없음·배치)
 └─────┬──────┘ └─────┬──────┘   pm2 가 세 개를 띄운다
       └───────┬──────┘
               ▼
   [RDS DB_ENDPOINT:5432]  · [Redis] · [S3]
     ▲
     └── 베스천 경유 터널로 로컬에서도 접근 (localhost:15432)
```

> 🔑 **두 평면이 만나는 건 "서버"지 "경로"가 아니다.** 요청은 베스천을 한 번도 지나지 않는다. → [[데이터 평면과 컨트롤 평면]]

### 2. 각 장비가 무엇이고 어느 평면인가

| 장비 | 역할 | 평면 | 죽으면 |
|---|---|---|---|
| CDN (CloudFront) | 정적 화면 + API 입구를 **한 도메인**으로 통합 | 데이터 | 서비스 중단 |
| ALB | 앱 서버 두 대에 분배 · 헬스체크 | 데이터 | 서비스 중단 |
| 앱 서버 ×2 | pm2 로 API 프로세스들 기동 | 데이터 | 한 대면 버팀 |
| RDS | 운영 DB (SSL 필수) | 데이터 | 서비스 중단 |
| **베스천** | SSH 관문 · CI · DB 터널 중계 | **컨트롤** | **배포만 막힘** |

- **화면과 API가 같은 도메인**이면 프론트는 `/api/...` 상대경로만 쓰면 된다 → CORS 문제가 통째로 사라진다. CDN을 쓰는 큰 이유 중 하나.
- **베스천을 이중화하지 않아도 되는 이유**가 이 표에 있다 — 죽어도 서비스는 돈다. → [[베스천 서버]]

### 3. 🚨 이 구성에서 반복해서 나오는 문제 6가지

실측해보면 거의 항상 이 중 몇 개가 걸려 있다. **각 항목의 자세한 내용은 링크된 노트에.**

| # | 증상 | 왜 생기나 | 상세 |
|---|---|---|---|
| ① | 접속기록 IP가 전부 같거나, 위조가 통과 | 앞단 장비 수와 `trust proxy` N 불일치 | [[X-Forwarded-For 와 신뢰할 프록시 수]] |
| ② | ①의 방어가 무력화 | **앱 포트가 외부에 열려** 있어 "짧은 길"이 존재 | 〃 |
| ③ | 서버 두 대인데 영역 장애에 같이 죽음 | 둘 다 **같은 AZ** (ALB만 멀티 AZ라 착시) | [[가용영역]] |
| ④ | 안 쓰는 nginx가 `:80` 으로 환영 페이지 노출 | 설치 스크립트가 **설치만 하고 설정은 안 함** | [[데이터 평면과 컨트롤 평면]] §4 |
| ⑤ | 설정 바꿨는데 절반만 반영 | env가 **서버에만** 있는데 한 대만 고침 | [[pm2]] §3·§5 |
| ⑥ | DB 터널이 끊겼는데 모름 | 포트는 `docker-proxy`가 여니까 **계속 열려 있음** | [[베스천 경유 접속과 상시 DB 터널]] §6-1 |

> 💡 ①~③ 은 **서로 엮여 있다.** "중간 장비 2대"라는 사실 하나가 `trust proxy` 값을 정하고, 그 값이 안전하려면 앱 포트가 닫혀 있어야 하고, 그 두 대가 다른 AZ에 있어야 비로소 이중화가 완성된다.

### 4. 인프라를 처음 받았을 때 — 재는 순서

구성도 문서를 믿지 않는다. **구성도는 과거의 의도고, 연결은 현재의 사실이다.**

```bash
# ── 1. 서버가 몇 대, 어느 영역에 있나 (가장 먼저)
aws ec2 describe-instances --query 'Reservations[].Instances[].{
  Name:Tags[?Key==`Name`]|[0].Value, AZ:Placement.AvailabilityZone,
  Private:PrivateIpAddress, Public:PublicIpAddress, Type:InstanceType}' --output table
#   → AZ 컬럼이 전부 같으면 ③번 확정

# ── 2. 앱 서버에 들어가서, 요청이 실제로 어디서 오나
ssh -J ec2-user@BASTION_IP ec2-user@WEB1_IP
ss -tnp state established '( sport = :3001 )'
#   → 찍히는 상대 IP = 바로 앞 장비. 몇 종류인지 = ALB 노드 수
#   → 중간에 nginx가 있으면 127.0.0.1 이 보인다. 없으면 ④번 의심

# ── 3. 뭐가 떠 있나 / 뭐가 포트를 잡고 있나
pm2 ls                              # 프로세스·재시작 횟수
ss -tlnp                            # LISTEN 중인 포트 전부 (안 쓰는 게 섞여 있다)
sudo nginx -T 2>/dev/null | grep -c proxy_pass   # 0 이면 nginx는 경로 밖

# ── 4. 밖에서 앱 포트에 닿나 (내 노트북에서)
nc -z -w 5 WEB1_PUBLIC_IP 3001      # 닿으면 ②번 — 심각
nc -z -w 5 WEB1_PUBLIC_IP 80        # 닿으면 ④번

# ── 5. 설정이 어디 있나
cat /home/ec2-user/<프로젝트>/env/<서비스>.env   # 저장소엔 없다
pm2 describe <서비스> | grep -A20 env            # 실제로 들고 있는 값
#   → 두 대 모두 확인. 다르면 ⑤번
```

**⏱ 30분이면 여기까지 나온다.** 그 뒤에 코드를 본다.

### 5. 이 구성에서 다음에 올릴 것

지금 상태로도 돌지만, 규모가 커지면 순서대로 걸린다.

| 다음 수 | 해결하는 문제 | 비용 |
|---|---|---|
| 앱 서버를 **다른 AZ**로 분산 | 영역 장애 | 거의 없음 (재배치) |
| **Auto Scaling Group** 도입 | 수동 EC2 생성 = AZ 실수 반복 | 중 |
| RDS **Multi-AZ** | DB 단일 장애점 | 인스턴스 2배 |
| 베스천 → **SSM Session Manager** | 베스천·키·`:22` 노출 전부 제거 | 낮음(IAM 작업) |
| env → **Parameter Store / Secrets Manager** | "서버가 유일한 원본" 문제 | 낮음 |
| EC2 → **컨테이너(ECS)** | pm2·배포 스크립트·서버 관리 소멸 | 높음 |

> 💡 **비용 대비 효과가 가장 좋은 건 위 두 개**(AZ 분산, ASG)다. 둘 다 코드 변경이 0이다.

## 기억할 문장 / 핵심 포인트
> **조립도부터 그린다 — "서버 목록"이 아니라 "경로 두 개".** 어디서 출발해 어디서 끝나는가.
> **구성도는 과거의 의도, 연결은 현재의 사실.** `ss` 로 재고 나서 믿는다.
> **중간 장비 수 하나가 세 가지를 동시에 결정한다** — `trust proxy` 값, 앱 포트 차단 필요성, 이중화 설계.
> **"떠 있다 ≠ 경로 위에 있다", "포트 열림 ≠ 살아 있음".** 둘 다 같은 종류의 착각이다.
> **이 구성의 개선은 AZ 분산부터.** 코드 변경 0에 장애 도메인이 둘로 늘어난다.
