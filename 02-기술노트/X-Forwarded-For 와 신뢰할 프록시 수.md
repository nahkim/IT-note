# 📝 X-Forwarded-For 와 신뢰할 프록시 수 (`trust proxy` 홉 계산)

> 🔒 **주소는 전부 자리표시자다.** 실제 값은 커밋하지 않는다.
> `CF_DOMAIN`(CDN 도메인) · `ALB_IP`(로드밸런서 사설 IP) · `WEB_IP`(앱 서버 사설 IP) · `VIEWER_IP`(진짜 사용자)

## 한 줄 요약
앱 앞에 CDN·로드밸런서가 끼면 TCP 상대는 **마지막 장비**라서, 진짜 사용자 IP는 `X-Forwarded-For`(XFF) 헤더에서 꺼내야 한다. 그런데 XFF는 **사용자가 위조해서 보낼 수 있는** 헤더다. 그래서 프레임워크는 "**오른쪽부터 N개까지만 내 장비니까 믿고, 그 다음 칸을 사용자로 본다**"는 식으로 자른다. 이 N이 **앞단 장비 수와 정확히 같아야** 한다 — 적으면 장비 IP가 사용자로 기록되고, **많으면 위조 값이 그대로 들어온다.**

## 핵심 내용

### 1. 왜 소켓 IP를 못 쓰나

```
 [사용자 VIEWER_IP]
      │ https
      ▼
 [CDN  CF_DOMAIN]        ← 중간 장비 ①
      │
      ▼
 [LB   ALB_IP]           ← 중간 장비 ②
      │
      ▼
 [앱   WEB_IP:3001]      ← 여기서 본 TCP 상대는 ALB_IP 다
```

앱이 보는 `socket.remoteAddress` 는 **항상 바로 앞 장비**다. 사용자 IP는 사라진 게 아니라, 각 장비가 **지나가면서 헤더에 적어 둔다.**

### 2. XFF 는 "왼쪽이 원본, 오른쪽이 최근"

각 프록시는 **자기가 본 TCP 상대를 오른쪽에 덧붙인다.**

| 지점 | `X-Forwarded-For` 값 |
|---|---|
| 사용자가 보냄 (위조 가능) | `fake` |
| CDN 통과 후 | `fake, VIEWER_IP` |
| LB 통과 후 | `fake, VIEWER_IP, CF_EGRESS_IP` |

- **오른쪽 끝**은 LB가 적은 값 → 내 장비가 적었으니 **믿을 수 있다.**
- **왼쪽 끝**은 사용자가 적은 값 → **아무 의미 없다.** 공격자가 `XFF: 8.8.8.8` 을 붙여 보내면 그게 그대로 맨 앞에 남는다.

> 🔑 **"왼쪽이 진짜 클라이언트"는 틀린 상식이다.** 왼쪽은 *가장 오래된 값*이지 *가장 믿을 만한 값*이 아니다. 신뢰는 **오른쪽에서부터** 쌓인다. → [[HTTP 헤더]]

### 3. 그래서 "오른쪽부터 N개"를 자른다

Express 계열의 `trust proxy` 에 **숫자**를 주면 이렇게 동작한다.

> **Number** — Use the address that is at most `n` number of hops away from the Express application. `req.socket.remoteAddress` is the first hop, and the rest are looked for in the `X-Forwarded-For` header **right to left**.
> — Express 공식 문서

실제 계산은 **주소 목록을 가까운 순으로 늘어놓고 앞에서 N개를 신뢰하는 것**이다.

```
 가까운 순 목록 = [ socket(ALB_IP), CF_EGRESS_IP, VIEWER_IP, fake ]
                    └─── 신뢰 2개 ───┘  ▲
                                        └ 첫 번째 "안 믿는" 주소 = 클라이언트
```

| N | 결과 | 판정 |
|---|---|---|
| `1` | `CF_EGRESS_IP` | ❌ CDN 주소가 사용자로 기록된다 |
| **`2`** | **`VIEWER_IP`** | ✅ 중간 장비가 2대니까 2 |
| `3` | `fake` | 🚨 **사용자가 보낸 값이 그대로 들어온다** |

> 🔑 **N = 내 앞에 있는 장비 수.** 사용자 수도, 헤더 칸 수도 아니다. 앞단 구성이 바뀌면(CDN을 빼거나 WAF를 끼우거나) **N도 같이 바꿔야** 접속기록의 IP가 계속 맞는다.

**환경변수로 빼는 패턴**
```bash
# .env — 코드가 app.set('trust proxy', Number(TRUST_PROXY_HOPS)) 로 읽는다
TRUST_PROXY_HOPS=2
```
환경별로 앞단이 다르기 때문이다(로컬 0, 스테이지 1, 운영 2 같은 식). → [[환경 변수]]

### 4. 🚨 N을 크게 잡으면 왜 뚫리나 — "길이가 다른 길"

Express 문서가 직접 경고하는 지점이다.

> Warning: it is important to ensure there are **not multiple, different-length paths** to the application such that the client can be **less than the configured number of hops away**, otherwise it may be possible for the client to **provide any value**.

즉 **홉 세기 방식은 "모든 요청이 반드시 N개 장비를 거친다"를 전제**로 한다. 이 전제가 깨지는 순간 끝이다.

```
 정상 경로 : 사용자 → CDN → LB → 앱      (장비 2개, N=2 가 맞음)
 샛길      : 공격자 ─────────────→ 앱:3001  (장비 0개!)
             XFF: "8.8.8.8, 1.1.1.1" 을 직접 붙여 보냄
             → 목록 = [socket(공격자), 1.1.1.1, 8.8.8.8]
             → 2개 믿고 건너뛰면 req.ip = 8.8.8.8  ← 완전 위조 성공
```

**그래서 세트로 확인해야 하는 두 가지**
1. 앱 포트(예: `:3001`)가 **외부에서 직접 안 열려 있을 것** — 보안그룹에서 LB만 허용
2. 그 조건 아래에서 N = 앞단 장비 수

> ⚠️ 1번이 무너지면 2번이 **방어가 아니라 통로**가 된다. 앱 서버에 공인 IP가 붙어 있다면 반드시 포트 차단 여부를 확인할 것.

### 5. 앞단 장비 수를 "세지 말고 재라"

구성도를 보고 세면 틀린다. 쓰지 않는 장비가 껴 있거나, **있는 줄 알았던 장비가 실제로는 경로 밖**인 경우가 흔하다.

**실측 방법 — 앱 서버에서 연결을 직접 본다**
```bash
# 1) 앱 포트로 들어오는 연결의 상대 주소 = 바로 앞 장비 (여러 번 새로고침하며)
ss -tnp state established '( sport = :3001 )'
#   → 여기 찍히는 IP 들이 LB 노드. 이게 "마지막 한 대"다.

# 2) 앱이 실제로 받은 헤더를 찍어 본다 (칸 수 = 앞단 장비 수)
#    로그에 XFF 원문을 한 번 남기고 → 쉼표 개수 + 1 이 칸 수
```

**실제로 이렇게 틀렸던 사례**
- 서버에 **nginx가 `:80` 으로 떠 있어서** 리버스 프록시인 줄 알았는데, 설정이 **기본값 그대로**라 `proxy_pass` 가 한 줄도 없었다. LB가 nginx를 거치지 않고 **앱 포트에 직접** 붙고 있었다 → 장비 수는 2지 3이 아니다. → [[리버스 프록시]]
- 설치 스크립트가 `nginx.sh` 라고 있었지만 **설치만 하고 설정은 하지 않는** 스크립트였다.

> 🔑 **"떠 있다 ≠ 경로 위에 있다."** 프로세스 목록이 아니라 **연결(`ss`/`netstat`)** 로 확인한다. → [[로드 밸런서]]

### 6. 바꾼 뒤 — 반영되게 하기

- 값은 보통 서버의 `.env` 파일에 있고 **저장소에는 없다**(환경별로 다르므로).
- 프로세스 매니저는 **기동할 때만** env를 읽는다 → 파일만 고치면 안 바뀐다. `pm2 restart`(또는 `--update-env`) 필요. → [[프로세스와 스레드]]
- **서버가 여러 대면 전부** 고쳐야 한다. 한 대만 고치면 LB가 돌리는 요청의 **절반만** IP가 맞는 기묘한 상태가 된다.

## 기억할 문장 / 핵심 포인트
> **`X-Forwarded-For` 는 오른쪽부터 믿는다.** 왼쪽 끝은 사용자가 쓴 글씨다.
> **N은 "앞단 장비 수"다.** 적으면 장비 IP가 기록되고, **많으면 위조가 통과한다** — 틀린 방향이 양쪽 다 있다.
> **홉 세기는 "모든 요청이 같은 길로 온다"는 전제 위에 선다.** 앱 포트가 외부에 열려 있으면 그 전제가 깨지고, N은 방어가 아니라 공격자가 건너뛸 칸 수가 된다.
> **장비 수는 세는 게 아니라 재는 것.** 떠 있는 nginx가 경로 위에 있다는 보장은 없다.
> **앞단 구성이 바뀌면 N도 같이 바뀐다.** CDN 추가·WAF 삽입·LB 제거는 전부 N을 건드리는 변경이다.

## 내 생각 / 적용할 점
- IP 기반 **레이트리밋·차단·접속기록**이 전부 이 한 숫자에 걸려 있다. 틀리면 "전 세계가 한 명으로 보이거나", "공격자가 매번 다른 사람으로 보인다"
- 앱 포트 외부 차단은 **N 설정의 전제조건**이다 — 둘을 같은 체크리스트에 넣기
- 표준은 `Forwarded` 헤더(RFC 7239)인데 현실은 XFF가 압도적. 그래도 새로 만들 때는 표준 쪽을 먼저 보기
- 앞단 변경(CDN·WAF 추가)을 할 때 **N을 같이 리뷰**하는 절차가 없으면 조용히 틀어진다
