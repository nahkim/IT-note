# 📝 대댓글(답댓글) 모델링 — property 방식

## 한 줄 요약
답댓글을 부모 안에 **중첩(nesting)해 넣지 않고**, 모든 댓글을 **평평한 한 줄**로 두되 각 댓글에 **"내가 트리의 어디에 있나"를 알려주는 속성(property)** 을 붙여 표현하는 방식. 관계를 **구조가 아니라 속성**에 담는다. → [[계층형 데이터 모델링|인접 리스트]]를 댓글에 적용한 실전판.

## 핵심 내용
1. **최소 property는 `parentId` 하나** — 부모 댓글 id. 원댓글이면 `null`. (자기 자신을 가리키는 self-reference)
2. **실무 표준은 4종 property** — `parentId`(부모) · `groupId`(스레드 묶음) · `depth`(깊이 0·1·2…) · `sortNo`(그룹 내 순서). 조회는 `group`으로 모아 `sortNo`로 정렬하고 `depth`만큼 들여쓰기.
3. **대댓글은 보통 depth를 1(~2)단계로 제한** — 인스타·유튜브식. 그러면 **재귀가 필요 없어** property 방식이 가장 단순·효율적인 선택이 된다. (무한 depth면 [[재귀|재귀 CTE]] 필요)

## 그림으로 이해하기

**① 관계는 화살표가 아니라 `parentId` 속성에 담긴다**
```
   원댓글                    답댓글이 부모를 '가리킨다'
 ┌──────────────┐
 │ id: 1        │
 │ parentId:null│◀─────────┐  parentId = 1
 └──────────────┘          │
                    ┌───────┴──────┐
                    │ id: 2        │
                    │ parentId: 1  │◀─────────┐  parentId = 2
                    └──────────────┘          │
                                       ┌───────┴──────┐
                                       │ id: 3        │
                                       │ parentId: 2  │
                                       └──────────────┘
```

**② 저장은 '평면 표' → 화면은 '들여쓰기 스레드'**
```
[DB에 저장된 평평한 표]
┌────┬──────────┬───────┬───────┬────────┬────────────────┐
│ id │ parentId │ group │ depth │ sortNo │ content        │
├────┼──────────┼───────┼───────┼────────┼────────────────┤
│ 1  │   null   │   1   │   0   │   1    │ 좋은 글이네요    │
│ 2  │    1     │   1   │   1   │   2    │ 저도 동감이요    │
│ 3  │    2     │   1   │   2   │   3    │ ㄷㄷ            │
│ 4  │   null   │   2   │   0   │   1    │ 질문 있습니다    │
└────┴──────────┴───────┴───────┴────────┴────────────────┘
        │
        │  WHERE post_id=? ORDER BY group, sortNo
        │  → group 으로 스레드 모으고, depth 만큼 들여쓰기
        ▼
[화면 렌더링]
💬 좋은 글이네요            ← group 1, depth 0
   ↳ 저도 동감이요         ← group 1, depth 1
      ↳ ㄷㄷ               ← group 1, depth 2
💬 질문 있습니다            ← group 2, depth 0
```

**③ 대안 — '중첩(nested) 방식'과의 대비**
```
 property 방식(평면+속성)        │   중첩 방식(트리를 그대로)
 ─────────────────────────      │   ─────────────────────────
 [1]  [2]  [3]  [4]  ← 다 평면   │   {                       ← 문서 하나에
  ▲    │                        │     id:1,                    통째로 중첩
  └────┘ parentId로 연결        │     replies:[
                                │       { id:2, replies:[ {id:3} ] }
 RDB에 자연스러움               │     ]
 부분 갱신·정렬 쉬움            │   }
                                │   NoSQL 문서 DB에 자연스러움
                                │   한 번에 통째로 읽기 좋음
```

## 코드 / 예시
```sql
-- 스키마: 관계를 parent_id 컬럼(=property)에 담는다
CREATE TABLE comment (
  id         BIGINT PRIMARY KEY,
  post_id    BIGINT,            -- 어느 게시글의 댓글인지
  parent_id  BIGINT NULL,       -- ★ 부모 댓글 id (원댓글이면 NULL) = self-reference
  group_id   BIGINT,            -- 스레드 묶음(보통 원댓글 id)
  depth      INT DEFAULT 0,     -- 0=댓글, 1=답댓글, 2=답답댓글…
  sort_no    INT,               -- 그룹 안에서의 정렬 순서
  content    TEXT,
  created_at TIMESTAMP
);
-- 조회 성능: 자주 거는 컬럼에 인덱스
CREATE INDEX idx_comment_thread ON comment (post_id, group_id, sort_no);

-- 한 게시글의 모든 댓글/답댓글을 스레드 순서대로
SELECT * FROM comment
WHERE post_id = 42
ORDER BY group_id, sort_no;     -- group 으로 묶고, 순서대로 → depth로 들여쓰기 렌더

-- 새 답댓글 달기 (2번 댓글에 대한 답글)
--   parent_id = 2,  group_id = (2번의 group),  depth = (2번의 depth)+1
INSERT INTO comment (id, post_id, parent_id, group_id, depth, sort_no, content)
VALUES (5, 42, 2, 1, 2, 4, '맞아요');

-- (참고) depth 무제한이면 하위 트리 전체 조회는 재귀 CTE
WITH RECURSIVE thread AS (
  SELECT * FROM comment WHERE id = 1
  UNION ALL
  SELECT c.* FROM comment c JOIN thread t ON c.parent_id = t.id
) SELECT * FROM thread;
```

## 기억할 문장 / 핵심 포인트
> **관계를 '구조(중첩)'가 아니라 '속성(parentId)'에 담는다.** 평면 테이블뿐인 [[관계형 데이터베이스와 SQL|RDB]]에 트리를 태우는 가장 단순한 방법.
> 이 방식의 정식 이름은 [[계층형 데이터 모델링|인접 리스트(Adjacency List)]] — 대댓글은 그걸 실무에 적용한 대표 사례.
> **실무 대댓글은 depth를 1(~2)로 제한** → `group + parent + depth + sortNo` property 4개면 충분하고, 재귀도 필요 없다. "일단 이걸로 시작하고, 무한 트리·초고성능이 필요해지면 경로 열거/클로저 테이블을 얹는다."
