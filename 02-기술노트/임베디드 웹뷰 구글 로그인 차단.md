# 📝 임베디드 웹뷰 구글 로그인 차단 — 그리고 루프백 브리지

## 한 줄 요약
> Tauri 데스크톱 앱(= OS 웹뷰)에서 구글 로그인을 누르면 **"브라우저가 자바스크립트를 지원하지 않습니다"** 화면이 떴다. JS 문제가 전혀 아니고 **구글의 임베디드 웹뷰 차단**이었다. 해결은 **로그인만 시스템 브라우저로 내보내고 결과를 루프백(`127.0.0.1`)으로 돌려받는 것** — 즉 [[딥링크와 루프백]]의 §7.3.

핵심 교훈은 따로 있다. **"내 컴퓨터에서는 되는데"가 "정상"이라는 증거가 아니었다.** 내 웹뷰에는 몇 달 전 쿠키가 남아 있어 차단 지점을 **지나가지 않고 있었을** 뿐이다.

## 핵심 내용

### 1. 증상 — JS 얘기가 나오지만 JS 문제가 아니다
동료 맥에서 앱 창 안에 구글이 그린 페이지가 떴다.

```
Google
로그인할 수 없음
사용 중인 브라우저가 자바스크립트를 지원하지 않거나
자바스크립트가 사용 중지되어 있습니다.
```

구글은 임베디드 웹뷰 OAuth를 정책상 막는다(에러 코드로는 `disallowed_useragent`). 그런데 **항상 그 코드로 나오지 않는다.** gaia(구글 로그인 서버)가 환경을 판단해 **non-JS 폴백 페이지**를 내주는 경우가 많고, 그게 위 문구다.

> **같은 차단의 다른 얼굴이다.** 이 문구를 보고 "웹뷰 JS 설정이 꺼졌나" 하고 뒤지면 하루를 버린다.

근거가 되는 규칙은 **RFC 8252 (OAuth 2.0 for Native Apps)** — *native apps MUST NOT use embedded user-agents*. 앱이 웹뷰를 소유하므로 키 입력·쿠키·DOM을 다 볼 수 있어서 "구글만 비밀번호를 본다"는 전제가 깨진다. → [[딥링크와 루프백]]

### 2. 오진 — 쿠키 가설과 그 반증
제일 먼저 세운 가설은 **"내 웹뷰에만 구글 세션 쿠키가 남아 있어서"** 였다. 논리는 이렇다.

- 구글의 차단은 **로그인 화면을 그릴 때** 발동한다.
- 이미 로그인된 상태면 구글은 화면을 안 그리고 **조용히 302로 콜백에 돌려보낸다.**
- 즉 쿠키가 있으면 **차단 지점을 지나가지 않는다.** → "나만 됨"이 설명된다.

여기서 중요한 사실 하나. **웹뷰는 Safari와 쿠키를 공유하지 않는다.** macOS WKWebView는 앱 전용 저장소를 쓴다.

```
~/Library/HTTPStorages/<bundle-id>.binarycookies   ← 쿠키
~/Library/WebKit/<bundle-id>/WebsiteData/          ← localStorage 등
```

그래서 사용자가 Safari에서 구글에 로그인돼 있어도 **앱 안에서는 맨바닥**이고, 신규 설치는 반드시 차단 지점을 밟는다.

**검증하려고 위 두 경로를 백업 폴더로 옮기고 앱을 다시 띄웠다. 그리고 가설은 틀렸다** — 쿠키가 빈 상태에서도 내 맥은 구글 로그인 화면이 정상적으로 그려지고 로그인까지 됐다. 즉 차이는 쿠키가 아니라 **머신·계정 쪽에 실재**한다.

남은 후보(끝내 특정하지 않음):
- **UA 차이** — 시스템 WebKit을 쓰므로 macOS 버전에 따라 UA 문자열이 다르다. 앱이 엔진 버전을 고정할 방법은 없다.
- **계정이 요구하는 인증 단계** — 2단계 인증·패스키(WebAuthn)는 임베디드 웹뷰가 못 쓰는 브라우저 API를 요구한다. 이쪽이 더 유력하다고 봤다.

> **셋 다 우리가 고칠 수 없는 구글 쪽 판정이다.** 그래서 "원인을 특정한 뒤 고친다"가 아니라 **"판정 지점 자체를 안 지나가게 만든다"** 로 방향을 잡았다. 결과적으로 원인 규명 없이 해결됐다.

### 3. 검증 방법의 결함 — 이게 진짜 교훈
두 달 전 같은 걸 확인하는 스파이크를 했고 **"통과"로 판정**했다. 그 판정이 틀렸다. **그 웹뷰에 이미 구글 세션이 있어서 대화형 화면을 그릴 일이 없었을 뿐**이다.

> **로그인 통과 여부를 확인할 때는 반드시 쿠키가 빈 상태에서 해야 한다.** (신규 설치 / 데이터 스토어 삭제 / 새 OS 사용자 계정)

일반화하면: **"지나가지 않은 것"을 "통과한 것"으로 읽지 말 것.** 경로를 밟았는지부터 확인해야 한다.

### 4. 해결 — 시스템 브라우저 + PKCE + 루프백
로그인만 바깥으로 내보내고 결과를 되돌려 받는다. 서버 측 [[OIDC]]는 한 글자도 안 건드리고, **"끝난 뒤 앱으로 돌려주는 구간"만** 새로 붙였다.

```
앱                       시스템 브라우저          백엔드            Google
 │ 127.0.0.1:0 바인드 → 빈 포트 확보
 │ verifier·state 생성, challenge = SHA256(verifier)
 │ 열기 ─▶ /auth/login?challenge=..&port=..&state=..
 │                          │────────────────▶│──────────▶│
 │                          │   기존 OIDC 흐름·검증 그대로
 │                          │◀────────────────│◀──────────│
 │                          │  콜백에서 desktop 감지
 │                          │  → 세션 대신 일회용 code 발급 (60초 TTL)
 │                          │◀─ 302 http://127.0.0.1:<port>/auth?code=..&state=..
 │◀── 브라우저가 로컬로 이동 ─┘
 │    앱의 리스너가 수신
 │
 │ 웹뷰를 /auth/exchange?code=..&verifier=.. 로 이동
 │                                        │ challenge 대조 → code 소각
 │                                        │ → Set-Cookie: session + 302 /
 │ 웹뷰가 로그인된 화면 진입 ◀─────────────┘
```

**여기서 제일 자주 막히는 이해 지점** — "서버가 `127.0.0.1`에 접속하는 거 아니냐?"

아니다. 서버가 하는 일은 헤더 한 줄이다.

```
HTTP/1.1 302 Found
Location: http://127.0.0.1:51734/auth?code=xxx&state=yyy
```

**이 302를 실행하는 주체는 서버가 아니라 사용자 기기의 브라우저다.** 그래서 `127.0.0.1`은 그 기기의 루프백이고, 거기엔 앱이 띄운 리스너가 있다. 서버는 그 뒷단을 모른다.

딸려오는 장점: 앱이 NAT·VPN 뒤에 있어도 상관없다. 마지막 배달을 브라우저가 **로컬에서** 해주기 때문이다. `gcloud auth login`·`gh auth login`·AWS CLI가 전부 이 방식이다.

### 5. 세션 쿠키를 앱이 만지지 않는 이유
받은 `code`로 세션을 만드는 일을 **앱이 하지 않는다.** 앱은 code만 받아 **웹뷰를 exchange URL로 이동**시키고, 그 응답의 `Set-Cookie`가 웹뷰 쿠키 저장소에 자연스럽게 저장되게 한다.

> 앱이 쿠키 값을 읽어 주입하는 방식이었다면 **HttpOnly를 포기해야 했다.** → [[쿠키 세션 JWT]]

### 6. 딥링크 대신 루프백을 고른 이유
초안은 커스텀 스킴(`myapp://`) 딥링크였는데 구현 시점에 루프백으로 바꿨다.

| | 커스텀 스킴 딥링크 | 루프백 |
| --- | --- | --- |
| 스킴 선점 | macOS는 막아주지 않음 — 다른 앱이 가로챌 수 있음 | 해당 없음 |
| 개발 모드 | `tauri dev`에서 불안정하다는 보고 다수 | 정상 |
| OS 등록 | Info.plist + deep-link 플러그인 필요 | 불필요 |
| 대가 | — | 빈 포트 하나, 브라우저에 localhost 페이지가 잠깐 |

부수 효과로 **코드가 단순해졌다.** 딥링크는 OS가 전역 핸들러로 배달하므로 "지금 진행 중인 로그인"을 전역 상태로 들고 있어야 한다. 루프백은 **각 시도가 자기 리스너·verifier를 소유**하므로 전역 상태가 아예 없어지고, 로그인을 두 번 눌러도 서로 안 꼬인다.

### 7. 루프백으로 바꾸면서 새로 생긴 것들
공짜가 아니다. 딥링크엔 없던 함정이 따라온다.

- **포트를 클라이언트가 보내므로 서버가 범위를 검증해야 한다.** 호스트는 코드에 박힌 리터럴이지만 포트를 그대로 끼우면 **우리 도메인이 오픈 리디렉터**가 된다.
- **`state` 난수 대조.** 없으면 포트를 훑는 로컬 프로세스가 가짜 콜백으로 verifier를 소모시켜 로그인을 실패시킬 수 있다.
- **포트 0으로 바인드에 성공한 뒤에야 번호를 서버에 알린다.** 고정 포트면 선점당했을 때 로그인이 막히거나 **그 프로세스가 code를 받는다.**
- **`0.0.0.0`이 아니라 `127.0.0.1`에 바인드.** LAN에 열리지 않고, macOS 방화벽의 "수신 연결 허용" 팝업도 안 뜬다. 로그인 도중의 그 팝업은 사용자가 해석할 수 없다.
- **URL에 `localhost` 말고 리터럴 `127.0.0.1`.** macOS에서 `localhost`가 `::1`(IPv6)로 먼저 풀리면 IPv4에 듣는 앱에 안 닿고, 증상은 **"로그인 다 했는데 앱이 무반응"** 이다.
- **`SO_REUSEPORT`/`SO_REUSEADDR`를 켜지 말 것.** 켜면 다른 프로세스가 같은 포트에 겹쳐 들을 수 있어 포트를 잡았다는 사실이 보장을 못 해준다.
- **accept에는 타임아웃이 없다.** 논블로킹 + 폴링으로 제한 시간을 걸지 않으면 사용자가 브라우저를 닫고 그만둔 경우 스레드와 포트가 영원히 남는다.

그리고 **[[PKCE]]는 선택이 아니다.** 루프백 포트는 같은 기기의 다른 프로세스가 노릴 수 있는 표면이라, code를 가로채도 verifier 없이는 세션이 안 나와야 한다.

### 8. 안 고른 길
- **UA 스푸핑** — 웹뷰 UA를 데스크톱 브라우저로 바꾸면 우회된다. 정책 위반이고, **탐지가 조여지는 순간 전원이 로그인 불가인 상태에서 급히 브리지를 만들게 된다.** 게다가 gaia는 UA만 보지 않는다(패스키/WebAuthn 지원 여부 같은 JS 표면도 본다).
- **클라이언트용 구글 로그인 플러그인** — 데스크톱에서 `clientSecret`을 요구하는 경우가 있다. 배포물(.dmg)에 secret을 박는 건 RFC 8252가 네이티브 앱을 public client로 다루라는 이유 그 자체다. 게다가 토큰을 손에 쥐여줄 뿐 **세션 쿠키를 웹뷰에 심는 어려운 부분은 대신해주지 않는다.**

### 9. 관찰 가능성 — 이게 없으면 원격지에서 못 고친다
브리지는 **브라우저·앱·백엔드 세 곳에 걸쳐 있다.** 어디서 끊겼는지 모르면 손을 못 댄다.

서버 로그만으로 구간이 갈린다(루프백 구간은 네트워크를 안 타므로 서버에 흔적이 없고, **그 "없음"이 곧 단서**다).

| 서버 로그 모양 | 끊긴 곳 |
| --- | --- |
| "로그인 시작"도 없음 | 브라우저가 서비스에 못 닿음 (VPN·프록시) |
| "시작"만 있고 "코드 발급" 없음 | 구글/동의 구간 |
| "코드 발급"은 있는데 "완료" 없음 | **루프백에서 끊김** |
| "교환 실패" | TTL 초과 또는 verifier 불일치 |

앱 쪽에서 같이 챙긴 것들:
- **`eprintln!`은 Finder로 실행하면 사라진다.** stderr가 어디에도 안 닿는다. 릴리스는 devtools도 꺼져 있어 웹뷰 `console.*`도 볼 수 없다 → **로그 파일이 필수**다.
- `console.*`를 **감싸서** 파일로 넘긴다. 호출부를 하나씩 고치면 새 로그가 또 새고, 무엇보다 **내가 안 쓴 예외**(`error`·`unhandledrejection`)를 못 잡는다.
- 로그 파일은 **사용자가 그대로 첨부해 보내는 물건**이다. 인자를 통째로 직렬화하지 말 것(Error는 message만, 객체는 타입만).
- 로그를 남겨도 **사용자가 전달 못 하면 없는 것과 같다.** `~/Library`는 Finder 기본 숨김이라 경로를 알려줘도 도달하지 못한다 → **앱 메뉴에 "로그 파일 열기"** 를 넣는다.
- **실패를 삼키지 말 것.** 리스너가 조용히 타임아웃하면 앱은 "로그인 대기 중"을 띄운 채 5분을 버티고, 사용자에겐 **버튼이 안 먹은 것과 구분되지 않는다.**
- 서버가 준 실패 사유를 **아는 값만 통과**시켜 화면에 쓴다. 외부 문자열을 그대로 URL·HTML에 넣지 않는다.
- 교환 실패 사유를 **만료/재사용/불일치로 나눠 알려주지 않는다** — 대입 공격에 힌트가 된다.

## 기억할 문장 / 핵심 포인트
> **"내 컴퓨터에서는 됩니다"는 정상이라는 증거가 아니다.** 그 경로를 밟지 않았을 뿐일 수 있다.

> 구글의 웹뷰 차단은 **로그인 화면을 그릴 때** 발동한다. 이미 로그인돼 있으면 화면이 안 그려지고, 그래서 차단도 안 걸린다.

> 웹뷰는 시스템 브라우저와 **쿠키를 공유하지 않는다.** 신규 설치는 언제나 맨바닥이다.

> "브라우저가 자바스크립트를 지원하지 않습니다"는 **JS 문제가 아니라 임베디드 웹뷰 차단의 다른 얼굴**이다.

> 302의 `Location: http://127.0.0.1:...`을 **실행하는 주체는 서버가 아니라 사용자의 브라우저**다.

> 원인을 끝내 특정하지 못해도 **판정 지점을 지나가지 않게 만들면** 해결된다.

## 내 생각 / 적용할 점
- **"된다"를 확인할 때는 그 경로를 실제로 밟았는지부터 본다.** 로그인은 쿠키 비우고, 캐시는 콜드 상태에서, 재시도 로직은 실패를 주입해서. 안 그러면 두 달 뒤에 같은 걸 다시 겪는다.
- **원인 규명과 해결은 분리해서 생각한다.** 원인이 상대방(구글·OS·외부 API) 안에 있으면 아무리 파도 우리가 못 고친다. 그럴 땐 "왜?"보다 **"그 판정을 안 받으려면?"** 이 빠르다.
- **표준이 있으면 표준을 먼저 본다.** RFC 8252는 이 문제의 답을 처음부터 다 적어놨다. 자체 설계로 반나절 고민한 게 §7.3 한 줄이었다.
- **원격지에서 재현 안 되는 버그는 로그가 전부다.** 그리고 로그는 **사용자가 전달할 수 있어야** 비로소 로그다 — 메뉴 버튼 하나가 로그 파일 자체만큼 중요하다.
- 편의를 위한 변경(딥링크→루프백)이 **새 공격 표면**을 들여올 수 있다. 오픈 리디렉터가 그랬다. 바꿀 때마다 "없던 입력이 생겼나"를 묻자.
