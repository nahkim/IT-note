# 📝 GPU 8장에 CPU 2개가 필요한 이유

## 한 줄 요약
GPU 8장은 **PCIe 레인·CPU 코어·메모리 대역폭**을 한 소켓이 감당할 수 없는 양으로 요구한다. 그래서 **CPU 2소켓에 GPU를 4+4로 나눠 붙이고**, 각 소켓이 자기 쪽 GPU·NIC·RAM만 담당하게 하는 게(NUMA 정렬) 8-GPU 서버의 표준 구성이다. "CPU 2개"는 연산력이 아니라 **입출력(I/O)과 토폴로지** 때문이다.

## 핵심 내용

### 1. 실제 장비가 그렇게 생겼다
| 장비 | GPU | CPU | 호스트 RAM |
|---|---|---|---|
| **NVIDIA DGX H100** | H100 **8장** (HBM 640GB) | **Intel Xeon Platinum 8480C ×2** (합 112코어) | **2TB** |
| NVIDIA DGX A100 | A100 8장 | AMD EPYC 7742 ×2 (합 128코어) | 1~2TB |
| Supermicro HGX 8-GPU (8U) | 8장 | EPYC/Xeon **2소켓** | 최대 수 TB |

→ 벤더가 "취향"으로 2개를 넣은 게 아니라, 8-GPU 베이스보드를 물리적으로 먹여 살리려면 2소켓이 필요하다.

### 2. 이유 ① PCIe 레인이 모자란다 (가장 결정적)
- GPU 1장은 **PCIe x16**을 요구한다 → GPU 8장 = **128레인**.
- 여기에 8-GPU 노드는 GPU마다 400Gb NIC를 1:1로 붙인다(ConnectX-7 등, 8~10장) → **+128레인**, NVMe 스토리지까지 더하면 **200레인 이상**.
- 그런데 **소켓 1개가 주는 레인은 80~128개**(Xeon 4세대 80레인, EPYC Genoa 128레인 수준, 세대별로 다름).

```
필요:  GPU 8×16 + NIC 8×16 + NVMe  ≈ 250+ 레인
공급:  1소켓 = 80~128 레인   →  부족
       2소켓 = 160~256 레인  →  성립  (+ PCIe 스위치로 팬아웃)
```

- 레인이 부족하면 GPU를 x8·x4로 낮춰 꽂아야 하고, 그러면 CPU↔GPU 전송(H2D/D2H)과 [[NIC]] 대역폭이 그대로 깎인다.

### 3. 이유 ② CPU는 GPU에게 "밥을 먹이는 손"이다
- **데이터 로딩·디코딩(JPEG/영상)·전처리·증강·토크나이즈·배치 구성**은 전부 CPU가 한다. GPU는 그걸 받아 행렬곱만 돌린다. → [[GPU vs CPU]]
- 통상 권고치: **GPU 1장당 최소 2코어**, 전처리가 무거우면 **4~8코어**, 데이터 파이프라인이 CPU 집약이면 그 이상.
- GPU 8장 × 8코어 = **64코어** + OS·드라이버·NCCL·스토리지 I/O 몫 → 여유 있는 2소켓(64~112코어) 구성이 자연스럽다.
- CPU가 못 따라가면 **GPU 스타베이션(GPU starvation)** — `nvidia-smi`에서 활용률이 90%를 못 넘고 톱니처럼 출렁인다. 수억 원짜리 GPU가 데이터를 기다리며 노는 것이 최악의 낭비. → [[nvidia-smi]]

### 4. 이유 ③ NUMA — 4장씩 나눠 붙여야 지연이 안 늘어난다
- 소켓마다 **자기 메모리 컨트롤러 + 로컬 RAM + 자기 PCIe 루트**를 갖는다(NUMA 노드).
- GPU 4장을 소켓0, 4장을 소켓1에 붙이면 각 GPU는 **같은 소켓의 로컬 RAM에서 바로 DMA**한다.
- 반대로 8장을 한 소켓에 몰면, 절반은 **UPI/Infinity Fabric(소켓 간 링크)을 한 번 더 건너** 원격 메모리를 읽는다 → 지연↑, 실효 대역폭↓, 소켓 간 링크가 병목.
- NIC도 **자기가 서비스할 GPU와 같은 소켓**에 꽂는다(GPUDirect RDMA가 소켓을 안 건너게). 그래서 "GPU 4 + NIC 4"가 소켓당 한 세트.

```
 [소켓0] ── RAM0        [소켓1] ── RAM1
    │  x16 ×4              │  x16 ×4
  GPU0~3 + NIC0~3      GPU4~7 + NIC4~7
    └──── NVLink/NVSwitch (GPU끼리는 CPU 우회) ────┘
```

### 5. 이유 ④ 메모리 용량·대역폭도 소켓 수에 비례
- 메모리 채널·DIMM 슬롯은 **소켓에 붙어 있다**(소켓당 8~12채널). 2소켓이어야 채널 수와 슬롯 수가 두 배.
- GPU HBM 총량이 640GB면 호스트 RAM은 보통 **그 2~3배(1~2TB)**를 권장한다(데이터셋 캐시·체크포인트·페이지 캐시). 1소켓으론 용량도 대역폭도 부족.

### 6. 그럼 왜 하필 "2개"인가
- **8 = 4+4**가 딱 맞는다. NVLink/NVSwitch 도메인과 PCIe 스위치가 **4장 단위**로 묶이므로, 소켓 2개와 1:1 대응된다.
- 소켓 3~4개는 소켓 간 링크 토폴로지가 급격히 복잡해지고(홉 증가), CPU 라이선스·전력·비용은 늘지만 GPU 서버가 얻는 이득은 적다. → **2소켓이 스윗스팟**.
- 부수 효과: **전력·발열이 보드 한쪽에 몰리지 않는다**(8U GPU 서버의 냉각 설계 전제).

### 7. 주의 — "8장이면 무조건 CPU 2개"는 아니다
- **추론 전용·경량 워크로드**는 1소켓 + PCIe 스위치로 GPU 8장을 붙이는 구성도 있다. GPU끼리만 통신하고 CPU 전처리가 가벼우면(예: [[vLLM]]로 서빙, 배치 전처리 없음) 1소켓으로도 충분할 수 있다.
- 반대로 **HGX 4-GPU에 2소켓**을 붙이는 구성도 있다 — CPU 집약 워크로드에서 **CPU:GPU 비율을 높이려고** 일부러 그렇게 한다.
- 기준은 개수가 아니라 **① 필요한 PCIe 레인 ② GPU당 필요한 코어 수 ③ NIC/NVMe 대역폭 ④ NUMA 정렬 가능 여부**.

## 기억할 문장 / 핵심 포인트
> **GPU는 계산기, CPU는 그 계산기에 데이터를 밀어 넣는 손이자 I/O 관문이다.** 8장을 붙이려면 손도 두 개, 관문도 두 개 필요하다.

> CPU 2소켓의 진짜 이유는 "연산이 부족해서"가 아니라 **레인·대역폭·NUMA 지역성** 때문이다.

## 코드 / 예시
```bash
# GPU–CPU 소켓(NUMA) 배치 확인 — 어느 GPU가 어느 소켓에 붙었나
nvidia-smi topo -m
#        GPU0 GPU1 ... CPU Affinity  NUMA Affinity
# GPU0   X    NV18     0-27,112-139   0
# GPU4   SYS  ...      28-55,140-167  1     ← SYS = 소켓 건너감(느림)

lscpu | grep -i numa          # NUMA 노드 수 = 대체로 소켓 수
numactl --hardware            # 노드별 CPU·메모리 분포

# 학습 프로세스를 GPU와 같은 소켓에 고정(스타베이션·원격 접근 방지)
numactl --cpunodebind=0 --membind=0 python train.py
```
